### 66. TASK-3301 "Enterprise Provider Intelligence Platform" 세부 해석 확인
- 현황: CTO 정책 3301-①~④가 이번 TASK의 범위였습니다.
  - **외부 가격 공지**(정책 3301-① — `PRICE_SOURCE_URL`의 JSON 가격표를 읽어 우리

    남습니다)
  - **파싱 실패는 "변경 없음"이 아닙니다** — `unreachable`·`unparsable`·`partial`을
    가르고 **일부만 읽어도 경고**하며 못 읽은 항목을 목록으로 남깁니다(아홉을
    읽었다고 성공이라 하면 못 읽은 하나가 조용히 사라집니다). `unconfigured`는
    실패가 아니므로 경보 제목이 다릅니다. 어댑터는 **재시도하지 않고**(예약
    점검이 다시 부릅니다) 실패를 빈 목록으로 바꾸지 않으며 토큰을 기록에 남기지
    않습니다
  - **2단계 승인**(정책 3301-② — `시스템 생성 → ADMIN 승인 → 다른 ADMIN 최종
    승인 → 적용`. `CONFIRMED` 단계를 신설하고 **운영에서만** 강제합니다: 사람이
    낸 제안은 제안자·승인자가 이미 둘이지만, 시스템 제안은 승인자 한 명이 곧
    전부입니다. **최종 승인자는 1차 승인자와 달라야** 합니다 — 같은 사람이 두 번
    누르는 절차는 확인을 늘리지 않고 "두 사람이 봤다"는 잘못된 안심만 만듭니다)
  - **예약 취소는 삭제가 아닙니다**(정책 3301-③ — `CANCELLED` 상태. **발효 전
    예약만** 취소할 수 있고 사유가 필요하며, 취소해도 목록에 남고 계산에서만
    빠집니다. 이미 발효된 단가는 취소할 수 없습니다 — 취소하면 그 뒤에 기록된
    비용이 어떤 단가로 계산됐는지 설명할 수 없게 됩니다)
  - **감지 주기는 Provider별만**(정책 3301-④ — 기본 6시간. **프로젝트별 설정은
    거부하고 사유를 남깁니다**: 단가는 Provider와의 계약이지 프로젝트의 속성이
    아니고, 프로젝트마다 주기가 다르면 "언제 마지막으로 봤는가"에 답이 여러 개가
    됩니다. **수동 실행은 주기를 무시**합니다 — 사람이 지금 보라고 누른 것입니다.
    `price_detection_runs`로 **0건도 건너뛴 것도** 기록합니다)
  - 라이브(**실 PostgreSQL + 실 Redis + 실 S3 + Vision 계약 스텁 + 가격 공지 계약
    스텁**): 공지 정상/형식 붕괴/HTTP 503/타임아웃/일부 해석을 각각 `ok`·
    `unparsable`·`unreachable`·`unreachable`·`partial`로 판정하고 **전부 사람
    확인을 요구** · 공지가 새 단가를 알리자 `published` 제안 생성 · 운영에서 1차
    승인 후 적용 **400**, 같은 사람의 최종 승인 **400**, 다른 ADMIN의 최종 승인 후
    적용 성공 · 예약 취소 사유 없음 400 · 취소 후 `CANCELLED`로 남고 예약만 사라짐 ·
    되살리기 400 · 이미 발효된 단가 취소 400 · Provider별 주기(12h/6h)와 프로젝트별
    설정 거부 · 예약 점검 2회차 주기 미도래 · 건너뛴 실행도 기록
  - **자체 발견 결함 3건**: ① 같은 항목에 두 근거가 잡힐 때 **약한 근거(기록
    불일치)가 강한 근거(공지)를 밀어냈습니다** — 처리 순서를 바꿔 공지를 남깁니다
    ② 공지 기반 제안의 근거에는 `sampleIds`가 없는데 화면이 표본 기반 모양으로
    읽어 **페이지 전체가 깨졌습니다**(라이브에서 발견) — DTO를 출처별 선택 필드의
    합집합으로 바로잡고 화면을 갈랐습니다 ③ 공지 제안의 제안자가 다시 "제안 알 수
    없음"으로 보였습니다 — 출처가 늘어도 같은 규칙이 적용되도록 고쳤습니다
- 하지 않은 것: 공지 형식 자동 적응(스키마 변화 학습), 공지의 발효 시각 자동 예약,
  Provider별 공지 주소 분리(지금은 한 주소에 모든 단가), 2단계 승인의 역할 분리
  (승인자 자격을 ADMIN 안에서 더 나누기), 취소된 예약의 재제출 자동화
- 질문: ① **공지 주소를 Provider별로 나눌지** — 지금은 한 주소가 모든 단가를
  담는 계약입니다. Provider마다 형식이 다르면 어댑터를 나눠야 하는데, 그때 실패
  판정도 Provider별로 갈립니다(하나가 죽어도 나머지는 읽힙니다) ② **공지가 밝힌
  발효 시각을 예약에 자동으로 채울지** — 지금은 근거로만 남기고 사람이 다시
  입력합니다. 자동으로 채우면 편하지만, 공지를 잘못 읽은 시각이 그대로 예약이
  됩니다 ③ **최종 승인자의 자격** — 지금은 "다른 ADMIN"이면 누구나 됩니다. 특정
  역할(예: 재무 담당)로 좁힐지 ④ **공지 실패가 며칠 이어질 때** — 지금은 같은
  경보가 쿨다운마다 반복됩니다. 며칠 이상 이어지면 등급을 올릴지(경보 승격은
  TASK-2401에서 쓴 적이 있습니다) ⑤ **Sprint 33 진행 방향** 및 다음 TASK 지정 요청.
