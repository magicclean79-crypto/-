### TASK-4603 — Job Reliability

**3-2. 왜 층을 따로 뒀는가 (지시 1~4 공통)**

지시는 넷이었지만 — 예외 처리, 로그, 자동 복구, 성능 계측 — 넷 다 같은
문제를 가지고 있었습니다. **호출 지점마다 손으로 붙이면 붙이는 것을 잊은
경로가 생깁니다.** 그리고 그 경로는 잘 돌 때는 티가 안 나고 **사고가 난
날에만** 드러납니다.

그래서 `packages/core/src/reliability/`(순수 판정)와
`apps/api/src/reliability/`(어댑터)에 **한 층**으로 모았습니다. 기존 경로는
이 층을 지나지 않으므로 예전 그대로이고, **새로 붙는 경로는 지나지 않을
수가 없습니다.**

**3-3. 예외 처리 강화 (지시 1)**

지금까지 이 저장소의 실패 처리는 경로마다 따로 있었습니다. OCR은 자기
타임아웃을, 알림은 자기 재시도를, 스모크는 자기 판정을 가지고 있었습니다.
각각은 정확한데 **한 가지 질문에 답할 수 없었습니다**:

> 지금 이 실패는 **다시 해 볼 만한 실패인가, 사람이 고쳐야 하는 실패인가.**

답이 없으면 두 가지 사고가 납니다. 고칠 수 없는 실패를 계속 재시도해 돈과
시간을 태우거나, 잠깐의 흔들림을 영구 실패로 적어 사람을 부릅니다.

| 종류 | 다시 시도 | 종류 | 다시 시도 |
| --- | --- | --- | --- |
| `network` · `timeout` | ✅ | `rejected`(4xx) · `unauthorized` | ❌ |
| `throttled`(429) · `upstream`(5xx) | ✅ | **`blocked`**(우리가 막음) | ❌ |
| `database` · `storage` | ✅ | `invalid-input` · **`unknown`** | ❌ |

**`unknown`은 재시도하지 않습니다.** 모르는 실패를 반복하면 어떤 실패인지
영영 모른 채로 돈만 씁니다. 재시도 규칙은 알림의 `isRetriable`(1401)과 **같은
규칙**입니다 — 두 곳에서 다른 결론이 나오면 "왜 이건 재시도했고 저건 안
했지"에 답할 수 없습니다.

**사용자 문장과 운영자 문장을 가릅니다.** 같은 실패라도 두 사람이 알아야
하는 것이 다릅니다: 사용자는 "무엇을 하면 되는가", 운영자는 "무엇이
일어났는가". 사용자 문장에 원문을 넣지 않는 이유는 **원문에 무엇이 들어
있는지 우리가 미리 알 수 없기 때문**입니다(키가 섞여 나온 로그를 저희는
이미 여러 번 봤습니다).

**전역 예외 필터는 `HttpException`을 그대로 통과시킵니다.** 지금까지 만든
400·403·404 응답의 본문과 상태 코드가 한 글자도 달라지지 않았습니다(§4-6
에서 실제로 재확인). 달라지는 것은 **분류되지 않은 오류 하나뿐**이고, 그때
원문 대신 사람이 할 수 있는 일과 `requestId`를 돌려줍니다 — `requestId`가
없으면 사용자는 "저 오류요"라고만 말할 수 있고 그걸로는 아무도 못 찾습니다.

**3-4. 상세 로그 (지시 2)**

등급은 **넷뿐**입니다: `debug` · `info` · `warn` · `error`. 더 두면 아무도
기준을 못 지키고, 기준이 없는 등급은 등급이 아닙니다.

| 결정 | 왜 |
| --- | --- |
| 한 줄의 **맨 앞**이 작업 id | 뒤에 두면 줄이 길어졌을 때 잘려서, 정작 묶어 보려고 만든 값이 안 보인다 |
| 비밀은 **이름으로** 가린다 | 값의 모양으로 가리면 새 Provider가 다른 모양의 키를 쓰는 날 조용히 새어 나간다 |
| 로그 기록 실패가 **작업을 실패시키지 않는다** | 로그를 남기다 서비스가 죽으면 그건 로그가 아니라 사고다 |
| 작업 문맥이 없으면 **DB에 쓰지 않는다** | 어느 작업의 것도 아닌 행은 나중에 아무도 해석하지 못한다 |

`key` · `token` · `secret` · `password` · `credential` · `authorization` ·
`cookie` · `webhook` · `dsn` · `url` 이 **이름에 들어간 값**은 `[가림]`이
됩니다. 깊이 6, 배열 50개, 문자열 2000자에서 자릅니다 — 로그 한 줄이
데이터베이스를 채우는 일이 실제로 있습니다.

**3-5. 자동 복구 (지시 3)**

열 장을 돌리다 일곱 번째에서 죽으면 앞의 여섯 장은 **이미 값을 치렀는데도
다시 삽니다.** 그래서 단계마다 체크포인트를 남기고 이어할 때 끝난 단계를
건너뜁니다.

다만 이어하기가 위험한 이유는, "이어한다"가 **하지 않은 일을 했다고 치는
것**과 종이 한 장 차이이기 때문입니다. 다섯 가지를 지켰습니다:

| 규칙 | 왜 |
| --- | --- |
| **끝난 단계만** 건너뛴다 | 진행 중이던 단계가 어디까지 갔는지 우리는 모른다 |
| **순서대로만** 건너뛴다 | 5번이 끝났다고 3번을 건너뛰면 3번은 영영 안 한다 |
| 입력이 달라지면 처음부터 | 바뀐 입력에 옛 결과를 붙이면 그 결과는 **어느 입력의 것도 아니다** |
| 24시간이 지나면 처음부터 | 그 사이에 무엇이 바뀌었는지 모른다 |
| **같은 행에 이어 쓴다** | 새 행을 만들면 "몇 번 만에 됐는가"가 흩어지고 앞의 시도가 없던 일이 된다 (§4-4에서 라이브로 잡음) |

작업 재시도는 알림 재시도(1401, 4회)보다 **적은 3회**입니다. **돈이 나가는
재시도는 공짜가 아닙니다** — 알림을 네 번 보내는 것과 LLM을 네 번 부르는
것은 비용이 다릅니다. 상한을 1~5로 둔 이유는, 없으면 누군가 100회를 적고
그 비용은 사고가 난 뒤에 알게 되기 때문입니다.

**3-6. 성능 계측 (지시 4)**

| 값 | 결정 |
| --- | --- |
| 단계별 시간 | "느리다"는 고칠 수 없고 **"어디가"** 가 있어야 고친다 |
| 토큰 | **모르면 `null`이고 0으로 채우지 않는다** — 채우면 합계가 실제보다 작아지고, 그 합계로 비용을 재면 청구서와 어긋난다 |
| 메모리 | **이 작업의 것이라고 말하지 않는다** (아래) |
| 전체 시간 | 처음부터 끝까지 |
| **안 잰 시간** | 전체 − 단계 합. **감추지 않는다** |

`process.memoryUsage()`는 **프로세스 전체** 값입니다. 이 작업이 도는 동안
다른 요청 열 개가 같이 돌았다면 그 증가분은 이 작업의 것이 아닙니다.
"이 작업이 쓴 메모리 12MB"라고 적어 두면 **아무도 그 사실을 다시 확인하지
않습니다.** 그래서 이름을 `processHeapDeltaBytes`로 두었습니다 — 그래도
남기는 이유는, 한 작업이 도는 동안 힙이 200MB 늘었다면 **그건 어느 작업의
것이든 봐야 할 신호**이기 때문입니다.

추세는 **표본 5건 미만이면 판정하지 않습니다**(`insufficient` — 빠르다는
뜻이 아닙니다). 한 번 느렸던 것을 "느린 단계"로 적으면 그날 네트워크가
흔들린 것이 **영구 결함으로 남습니다.** 평균이 아니라 **중앙값**으로 봅니다.

### 4-1. 라이브 결함 ① — 예산으로 막은 것을 "잠시 후 다시 시도"라고 말했다

예산 한도를 실제로 넘겨 놓고 배치를 돌렸더니 사용자 문장이 이랬습니다:

```
요청이 몰려 잠시 처리할 수 없습니다. 잠시 후 다시 시도해 주세요.
```

예산 초과는 **HTTP 429**로 나갑니다. 그 선택 자체는 옳습니다 —
클라이언트에게는 "지금은 안 된다"입니다. 그런데 상태 코드만 보면
`throttled`가 되고, `throttled`는 **재시도 대상**입니다.

**예산은 기다린다고 열리지 않습니다.** 그리고 재시도하면 **돈이 나가는
호출을 반복합니다.** 자동 복구 층이 비용을 아끼려고 만든 것인데 정반대로
쓰일 뻔했습니다.

우리 문구(`예산을 초과` · `차단했습니다` · `강제로 여는 방법은 없습니다` …)를
**상태 코드보다 먼저** 보게 고쳤습니다. 상대 서비스의 429 본문에 이 말이
들어 있을 리 없습니다. 수정 후:

```
failureKind: blocked · resumable: false
"이어해도 같은 결과가 나오는 실패입니다 — 원인을 먼저 고쳐 주세요."
```

동시에 **상대의 진짜 429는 그대로 `throttled`로 남는지** 검사하는 테스트를
같이 넣었습니다 — 한쪽을 고치다 다른 쪽을 망가뜨리는 것이 이 수정의 가장
큰 위험이었습니다.

### 4-2. 라이브 결함 ② — 던지지 않았다고 성공이 아니다

깨진 이미지 한 장을 섞어 3장을 돌렸더니:

```
3/3단계를 끝냈습니다.   ← 그런데 한 장은 글자가 하나도 없었다
```

`OcrService.runOcr`은 Provider 실패를 기록하고 **`status: "FAILED"`로
돌려줍니다.** 한 장이 실패했다고 요청 전체를 500으로 만들지 않으려는
의도이고, 그 판단은 옳습니다. 그런데 저희가 **던지지 않은 것을 성공으로
세었습니다.**

더 나쁜 것은 그다음입니다. 체크포인트가 그 장을 **끝난 것으로 표시**해서
이어하기로도 다시 시도되지 않습니다 — **자동 복구가 실패를 영구화**했습니다.

결과의 `status`를 보게 고쳤습니다. 수정 후:

```
3/3단계를 끝냈습니다. 결과를 얻지 못해 건너뛴 항목 1건이 있습니다: img-broken-4603.
```

전부 건너뛴 경우에는 **"결과를 얻은 항목이 하나도 없습니다"** 라고 말합니다 —
아무것도 못 얻은 실행이 성공으로 읽히면 안 됩니다.

### 4-3. 라이브 결함 ③ — Provider가 통째로 죽은 것을 "이 한 장의 문제"로 봤다

4-2를 고친 직후 Vision 스텁을 **통째로 내렸습니다.** 그랬더니 세 장이 전부
"건너뜀"이 되고 작업은 **성공**으로 끝났습니다.

건너뛰기는 "한 장 때문에 나머지 아홉 장을 못 하면 배치의 의미가 없다"는
판단이었는데, 상대가 죽은 날에는 그 판단이 **열 번 더 실패하고 그중 일부는
돈이 나가는** 결과가 됩니다.

기록된 사유를 분류해서 갈랐습니다:

| 원인 | 처리 |
| --- | --- |
| **공통 원인** (연결·시간 초과·상대 서버·정책) | **배치를 멈춘다** |
| **이 한 장의 문제** (파일 없음·형식) | 건너뛰되 **결과에 남긴다** |

수정 후 스텁을 내린 상태에서: `failureKind: network` · `resumable: true`.

### 4-4. 라이브 결함 ④ — 이어했더니 새 행이 생겨 앞의 실패가 영영 남았다

4-3의 상태에서 스텁을 살리고 `POST /jobs/:id/resume`을 눌렀더니 작업은
성공했는데 `job_runs`에 **새 행**이 생겼습니다. 앞의 실패는 `failed`로 영영
남고, "몇 번 만에 됐는가"는 두 행으로 흩어졌습니다.

원인은 **첫 단계에서 죽은 경우**입니다 — 끝난 단계가 0개이므로
`planResume`이 `fresh`를 돌려주고, `fresh`를 "새 작업"으로 읽었습니다.
`fresh`는 **"처음부터 다시 한다"** 이지 **"다른 작업이다"** 가 아닙니다.

입력 지문이 같으면 `resume`이든 `fresh`든 **같은 행에 이어 쓰게** 고쳤습니다.
수정 후 실측:

```
job_runs 행 수: 10 → 11 (이어하기로 늘지 않음)
상태: succeeded · 시도: 2
```

### 4-5. 라이브 검증 — 체크포인트가 실제로 돈을 아끼는가

이미 끝난 작업을 다시 이어했습니다.

```
ocr_records 건수: 48 → 48   (한 건도 다시 사지 않음)
```

### 4-8. 라이브 검증 — 성능 계측

3장 배치 1회:

```

**"단계 밖에서 22ms"** 를 적는 이유는, 안 적으면 단계 합(102ms)이 전체인

```

`ocr:3:img-x` 같은 단계 이름은 `ocr:*`로 묶습니다 — 안 묶으면 이미지마다
표본이 1건이라 **영원히 `insufficient`** 입니다.

## 8. 리스크·기술 부채

1. **이 층을 지나는 경로가 아직 하나입니다** — 묶음 OCR뿐입니다. 이미지
   분석·생성·발행은 예전 경로 그대로이고, **거기에는 체크포인트도 계측도
   없습니다.** 하나를 태워 본 이유는 태우지 않은 층은 만든 것이 아니기
   때문이고, 나머지를 한 번에 태우지 않은 이유는 이번에 라이브에서만 보이는
   결함이 4건 나왔기 때문입니다 (CTO_REQUEST #82 ①)
2. **토큰 사용량은 여전히 대부분 `null`입니다** — OCR 경로가 토큰을 돌려주지
   않습니다. 0으로 채우지 않았으므로 **합계가 없다고 말합니다**. 채우려면
   Provider 어댑터가 토큰을 올려 줘야 합니다 (#82 ②)
3. **메모리는 "이 작업의 것"이 아닙니다** — 프로세스 전체 값입니다. 작업별로
   재려면 `AsyncLocalStorage` 기반 샘플링이 필요하고, 그건 상시 오버헤드를
   지불하는 결정입니다 (#82 ③)
4. **`insufficient` 표본** — 이 환경의 트래픽이 적어 대부분의 단계가 5건에
   못 미칩니다. 지금 화면에 뜨는 `ok`는 `ocr:*` 하나뿐입니다
5. **재시도는 프로세스 안에서만 삽니다** — 프로세스가 죽으면 대기 중이던
   재시도가 사라집니다. 이어하기가 그 자리를 메우지만 **사람이 눌러야
   합니다.** 자동으로 이어하려면 큐가 필요합니다 (#82 ④)
6. **정책 4601-①②의 조건이 그대로입니다** — 사람이 줘야 하는 넷(Provider
   Credential · Network Allowlist · Validation Environment · Production Host
   Inventory)이 **열 스프린트 연속** 미준비이며, `POST
   /ops/validation-run/execute`는 여전히 **403**, `validation_runs`는 **0건**
   입니다 (#82 ⑤ · #80 ④ · #79 ④)
7. **TASK-4602 조사(#81)의 항목은 하나도 구현되지 않았습니다** — 이번 지시가
   다른 방향이었습니다. 발행 경로 부재·중복 방지 부재·품질 측정 부재는 그대로
   남아 있습니다
8. **`ops.controller.ts`는 여전히 라우트 69개입니다** — 이번에 더하지
   않았을 뿐 줄지도 않았습니다 (#81 조사 결과 7)
9. **Adaptive Card 실 Teams 확인 · `silent` 채널 · 담당자 표 DB 이전 ·
   순수 IPv6 라이브 확인**은 4601에서 그대로 이어집니다
10. **Live Verification은 CI에서 돌지 않습니다** — 이번 결함 4건이 전부
    라이브에서만 보였다는 사실이 이 부채의 값을 다시 보여 줍니다
11. **저장된 옛 기록의 별표 10건** · **운영 저장소가 아직 S3가 아님** ·
    **`.turbo/cache` 증가**는 그대로입니다
