## 3. 변경 사항 (이번 보고 주기)

### TASK-3301 — Enterprise Provider Intelligence Platform

**1. 외부 가격 공지를 읽습니다 — 그리고 못 읽으면 그렇게 말합니다 (정책 3301-①)**

TASK-3201의 감지는 **우리 기록과 우리 가격표의 불일치**까지만 볼 수 있었습니다
(비용은 우리가 우리 표로 계산하므로). `PRICE_SOURCE_URL`의 JSON 가격표를 대조해
비로소 **"Provider가 단가를 올렸다"**를 잡습니다. 공지 기반 제안은 출처가
`published`이고, 근거에 **공지 주소와 공지가 밝힌 발효 시각**이 남습니다.

> **파싱 실패를 "변경 없음"으로 처리하지 않습니다.** 조용히 지나가면 ⓐ 화면은
> "변경 없음"으로 보이고 ⓑ 사람은 확인했다고 믿고 ⓒ 단가는 낡은 채로 계속 돈이
> 나갑니다. **못 읽은 것과 바뀐 것이 없는 것은 완전히 다른 사실입니다.**

| 상태 | 뜻 | 사람 확인 |
| --- | --- | --- |
| `ok` | 전부 읽었다 | 불필요 |
| `partial` | **일부만** 읽었다 — 못 읽은 항목을 목록으로 남긴다 | **필요** |
| `unparsable` | 형식이 바뀌었거나 JSON이 아니다 | **필요** |
| `unreachable` | 닿지 못했다 (네트워크·HTTP·타임아웃) | **필요** |
| `unconfigured` | 주소가 없다 — **실패가 아니다** | 필요(제목이 다름) |

`partial`을 따로 둔 이유: 열 줄 중 아홉을 읽었다고 "성공"이라 하면 **못 읽은 한
줄이 조용히 사라집니다.** 읽은 것은 쓰고, 못 읽은 것은 말합니다.

어댑터는 **재시도하지 않고**(예약 점검이 주기적으로 다시 부릅니다) 실패를 빈
목록으로 바꾸지 않으며, 토큰(`PRICE_SOURCE_TOKEN`)은 헤더로만 보내고 판정 결과에
남기지 않습니다.

**2. 시스템 제안은 2단계 승인 (정책 3301-②)**

```
시스템 생성 → ADMIN 승인 → 다른 ADMIN 최종 승인 → 적용
   DETECTED  →   APPROVED  →      CONFIRMED       →  APPLIED
```

**운영에서만** 강제합니다. 사람이 낸 제안은 제안자와 승인자가 이미 둘이지만
(정책 3201-②가 같은 사람을 막습니다), 시스템이 만든 제안은 승인자 **한 명이 곧
전부**입니다 — TASK-3201 보고에서 리스크로 올렸던 바로 그 구멍입니다.

- `APPROVED → APPLIED`는 **400**이고, 문구가 "먼저 최종 승인(confirm)을 받아
  주세요"까지 말합니다.
- **최종 승인자는 1차 승인자와 달라야** 합니다(운영 차단·개발 경고). 같은 사람이
  두 번 누르는 절차는 단계만 늘 뿐 확인을 늘리지 않고, 오히려 **"두 사람이
  봤다"는 잘못된 안심**을 만듭니다.
- 개발에서는 그대로 적용할 수 있고, 더 보수적으로 가고 싶으면 개발에서도
  `confirm`을 쓸 수 있습니다 — **막지 않습니다.**

**3. 예약 취소는 삭제가 아닙니다 (정책 3301-③)**

`CANCELLED` 상태를 신설했습니다. 적용은 **실제로 있었던 일**이고, 그 결정을
지우면 "왜 그때 그 단가가 예약됐다가 사라졌는가"에 아무도 답할 수 없습니다.

- **발효 전 예약만** 취소할 수 있습니다. 이미 발효된 단가를 취소하면 그 시각
  이후에 기록된 비용이 어떤 단가로 계산됐는지 설명할 수 없게 됩니다 — 되돌리려면
  새 제안입니다(정책 3101-②와 같은 이유).
- **사유가 필요합니다** — 왜 없앴는지가 남지 않으면 이력이 반쪽입니다.
- 취소하면 **캐시도 즉시 무효화**합니다: 다음 발효 경계가 바뀌었으므로 그대로
  두면 취소된 단가를 그 시각에 반영하려 듭니다.

**4. 감지 주기는 Provider별로만 (정책 3301-④)**

기본 6시간, `PRICE_DETECT_INTERVAL_<PROVIDER>`로 조정합니다.
**프로젝트별 설정은 거부하고 사유를 남깁니다** — 단가는 Provider와의 계약이지
프로젝트의 속성이 아니고, 프로젝트마다 주기가 다르면 ⓐ "언제 마지막으로
봤는가"에 답이 여러 개가 되고 ⓑ 프로젝트가 늘 때마다 감지 부하가 곱해집니다.
조용히 무시하지 않는 이유: **무시하면 설정한 사람은 적용된 줄 압니다.**

**수동 실행은 주기를 무시합니다** — 사람이 "지금 보라"고 누른 것이므로 주기
미도래로 아무것도 하지 않으면 버튼이 거짓말이 됩니다. 예약 점검은 주기를 지킵니다.

`price_detection_runs`를 신설해 **0건도, 건너뛴 것도** 기록합니다. 이 기록이
없으면 **"감지 0건"과 "감지를 안 돌렸다"를 구분할 수 없습니다** — 조용한 것과
안 본 것은 다릅니다.

**5. 자체 발견 결함 3건**

> **①(라이브)** 같은 항목에 두 근거(공지·기록 불일치)가 함께 잡히면 중복 방지로
> 하나만 남는데, **약한 근거(기록)가 강한 근거(공지)를 밀어냈습니다.** 공지는
> Provider가 밝힌 단가와 발효 시각을 들고 있고 기록 불일치는 그 결과일 뿐입니다 —
> 처리 순서를 바꿔 공지가 남게 했습니다.
>
> **②(라이브)** 공지 기반 제안의 근거에는 `sampleIds`가 없는데 화면이 표본 기반
> 모양으로 읽어 **페이지 전체가 깨졌습니다**(`Cannot read properties of
> undefined`). DTO가 근거를 한 모양으로만 선언해 타입 검사도 잡지 못했습니다 —
> **출처별 선택 필드의 합집합**으로 바로잡고 화면을 갈랐습니다.
>
> **③(라이브 스크린샷)** 공지 제안의 제안자가 다시 **"제안 알 수 없음"**으로
> 보였습니다(TASK-3201에서 `detected`만 고쳤기 때문). 출처가 늘어도 같은 규칙이
> 적용되도록 `manual`만 예외로 두었습니다.

## 5. 아키텍처 변경 및 현황

```
감지 (두 근거) — 정책 3301-①
   예약 점검 pricing-detect ─┬─▶ 외부 공지 (PRICE_SOURCE_URL)
                             │      judgePriceSource → ok|partial|unparsable|
                             │                          unreachable|unconfigured
                             │      실패 = 사람 확인 요구 (price-source 경보)
                             │      **"변경 없음"으로 바꾸지 않는다**
                             └─▶ 우리 기록 (발효 시각 이후만)
        두 근거가 겹치면 → **공지가 남는다** (강한 근거)

승인 (사람) — 정책 3301-②
   DETECTED ─▶ APPROVED ─▶ CONFIRMED ─▶ APPLIED
                  │            ↑
                  └── 운영 + 시스템 제안이면 이 경로가 강제된다
                      (최종 승인자 ≠ 1차 승인자)

취소 — 정책 3301-③
   APPLIED(발효 전) ─▶ CANCELLED   (기록은 남고 계산에서만 빠진다)
   APPLIED(발효 후) ─▶ 400          (되돌리려면 새 제안)

주기 — 정책 3301-④
   resolveDetectionIntervals(env, providers)
        PRICE_DETECT_INTERVAL_<PROVIDER>  → 허용
        PRICE_DETECT_INTERVAL_PROJECT_*   → **거부 + 사유**
   price_detection_runs: 0건도, 건너뛴 것도 남긴다
```

① **못 한 일을 했다고 말하지 않습니다.** 공지 실패를 "변경 없음"으로 바꾸지
   않는 것이 이 TASK의 전부이고, `partial`을 따로 둔 것도 같은 이유입니다.
② **자동화가 셀 수 있는 사람 수를 정직하게 셉니다.** 시스템 제안은 승인자 한
   명이 곧 전부라는 사실을 인정하고 한 명을 더 요구했습니다.
③ **없애는 것도 기록입니다.** 취소를 삭제로 두면 이력이 거짓이 됩니다.
④ **설정은 계약의 단위를 따릅니다.** 단가는 Provider와의 계약이므로 주기도
   Provider 단위입니다 — 프로젝트 단위 설정은 거부하고 그 사실을 말합니다.
⑤ **근거의 강약을 코드가 압니다.** 공지와 기록이 같은 항목을 가리키면 공지가
   남습니다.

## 7. API 표면

**새 엔드포인트 2개** (ADMIN 전용):

- `POST /ops/pricing/:id/confirm` — **최종 승인**(2단계 승인, 정책 3301-②).
  1차 승인자와 같으면 운영에서 400입니다.
- `POST /ops/pricing/:id/cancel` — **예약 취소**(정책 3301-③). 사유 필수,
  발효 전만 가능. 레코드는 `CANCELLED`로 남습니다.

**기존 계약 확장**:

- `POST /ops/pricing/detect` — 응답에 **`source`**(공지 상태·`needsHumanCheck`·
  `unparsed`)·**`published`**(공지 대조 결과)·**`notDue`**(주기 미도래)가
  추가됐습니다. 수동 실행은 **주기를 무시**합니다.
- `GET /ops/pricing` — **`detection`**(Provider별 주기·마지막 실행·거부된 설정·
  최근 이력)이 추가됐습니다. 제안에 **`confirmedBy/At`·`needsSecondApproval`·
  `cancelledBy/At/Reason`**이 추가됐습니다.
- `PricingStageDto`에 **`CONFIRMED`·`CANCELLED`**, `PricingOriginDto`에
  **`published`** 추가.
- `PricingProposalDto.evidence`가 **출처별 선택 필드의 합집합**으로 바뀌었습니다
  (표본 기반: `sampleIds`·`from`·`to`·`relativeDiff` / 공지 기반: `url`·
  `publishedEffectiveFrom`) — 자체 발견 결함 ②의 수정입니다.
- `GET /ops/alerts` — 경보 종류 **`price-source`** 추가.
- `POST /ops/pricing/:id/approve` — 시스템 제안은 운영에서 승인 후 **적용이
  400**이 됩니다(먼저 `confirm`).

**환경 변수 4개 추가**: `PRICE_SOURCE_URL` · `PRICE_SOURCE_TOKEN`(비밀) ·
`PRICE_SOURCE_TIMEOUT_MS`(기본 5000) · `PRICE_DETECT_INTERVAL_<PROVIDER>`(기본
6h, **프로젝트별 금지**) · `ALERT_COOLDOWN_PRICE_SOURCE_MS`.

## 8. 리스크·기술 부채

1. **3301 해석 미확인** — 공지 주소 분리·발효 시각 자동 예약·최종 승인자 자격·
   공지 실패 장기화 (CTO_REQUEST #66)
2. **공지 형식은 우리가 정한 계약입니다** — 실제 Provider의 가격 페이지는
   HTML이거나 형식이 제각각입니다. 지금 구조는 **누군가 그 형식을 우리 JSON으로
   옮겨 주는 것**을 전제합니다(#66 ①)
3. **공지 주소가 하나입니다** — 한 Provider의 형식이 바뀌면 전체가 `unparsable`이
   되어 나머지 단가도 확인하지 못합니다(#66 ①)
4. **공지가 밝힌 발효 시각을 자동으로 예약하지 않습니다** — 사람이 다시
   입력합니다. 자동으로 채우면 편하지만 잘못 읽은 시각이 그대로 예약이 됩니다(#66 ②)
5. **최종 승인자는 "다른 ADMIN"이면 누구나** 됩니다 — 역할을 더 나누지
   않았습니다(#66 ③)
6. **공지 실패가 며칠 이어져도 경보 등급이 오르지 않습니다** — 같은 경고가
   쿨다운마다 반복될 뿐입니다(#66 ④)
7. **운영에는 ADMIN 계정이 최소 둘 필요합니다** — 시스템 제안은 이제 **셋**이
   아니라 둘이면 되지만(제안자가 시스템), 사람 제안과 합치면 여전히 둘이 최소입니다
8. **감지는 OCR 단가만 제안합니다** — LLM은 입력·출력 단가를 기록에서 가를 수
   없어 어긋남만 알립니다(TASK-3201에서 이어지는 한계). 다만 **공지 대조는
   LLM도 제안을 만듭니다**
9. **실패한 호출의 과금·무료 구간·환율은 여전히 우리 집계 밖입니다**
10. **실 Google Cloud Vision·실 LLM 호출은 미검증** — 실 키와 외부 네트워크 필요
11. **운영 저장소가 아직 S3가 아닙니다**(결정 2101-④) · **백업 성능 기준은 개발
    규모에서만 검증**(1901-④ 대기) · **GitHub Actions 실제 실행 미확인**
12. **디스크 할당량이 빠듯합니다** — 검증 중 여유가 1GB 수준입니다
