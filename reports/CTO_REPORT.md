## 3. 변경 사항 (이번 보고 주기)

### TASK-1701 — Enterprise Backup & Disaster Recovery

TASK-1601은 **"백업이 있고 복원된다"** 를 증명했습니다. 이번 주기는 그 다음
세 질문입니다:

> **덤프가 온전한가 · 같은 곳에만 있지 않은가 · 얼마를 잃고 얼마나 걸리는가**

**1. Backup Integrity — 복원 시점에 알면 늦다**

백업 직후 `pg_restore --list`로 목차를 읽고 SHA-256을 기록합니다.

- **복원하지 않고도 파일이 온전한지 알 수 있는 가장 싼 검사**입니다. 읽히지
  않는 덤프는 존재하지만 쓸 수 없는 파일이고, 그것을 "백업 있음"으로 세면
  복구 계획이 통째로 거짓이 됩니다.
- 목차가 비어 있으면 읽힌 것이 아닙니다 — 성공으로 세지 않습니다.
- 무결성 실패는 **복구 가능성을 좌우하는 항목**(critical)입니다.
- 체크섬은 이력에 그대로 남깁니다 — 원격 사본과 대조할 근거이기 때문입니다.
  다만 체크리스트 설명에는 앞 12자만 싣습니다(읽으라고 있는 문장이므로).

**2. Offsite Replication — 같은 곳에만 있으면 함께 사라진다**

`BACKUP_OFFSITE=on`이면 덤프를 오브젝트 저장소에도 올립니다.

- **복제 실패가 백업을 실패시키지는 않습니다** — 덤프는 이미 받았습니다.
  대신 로그로 남기고 화면에서 드러냅니다.
- 미구성은 실패가 아니라 `주의`이고, 복구 가능성을 막지도 않습니다 — 로컬
  덤프로 복구 자체는 되기 때문입니다.
- 원격 키는 노출하지 않고 **있는지만** 알립니다 — 저장소 구조를 드러낼 이유가
  없습니다.

**3. RPO · RTO — 추정이 아니라 측정**

| | 정의 | 기본 목표 |
| --- | --- | --- |
| RPO | 마지막 성공 백업 이후 경과 | 24시간 |
| RTO | **마지막 복원 검증에 실제로 걸린 시간** | 30분 |

복원 검증이 이미 매일 돌고 소요 시간을 기록하고 있으므로, **별도 계측 없이
근거 있는 값**을 씁니다. 다만 이는 **하한**입니다 — 사람이 장애를 알아차리고
결정하는 시간, 인프라를 준비하는 시간은 포함하지 않습니다. **화면에도 그렇게
적습니다.** 측정치가 없으면 `직접 확인`이고 통과가 아닙니다.

**4. 복원 대상 강제 분리 (CTO 결정 1601-②)**

복원은 대상 스키마를 **지우고 씁니다**. 대상이 운영 DB면 검증이 곧 사고입니다.

- 호스트·포트·DB 이름만 비교합니다 — **자격 증명이 달라도 같은 DB는 같은 DB**
  입니다.
- 같으면 **기동하지 않습니다**. 개발 환경에서도 오류입니다 — 운영 DB를 지우는
  설정은 어디서도 허용할 수 없습니다.
- 기동 후 설정이 바뀔 수 있으므로 **실행 직전에 한 번 더** 봅니다.

**5. `BACKUP_DIR` 운영 필수 (CTO 결정 1601-①)**

미설정이면 **기동하지 않습니다**(Fail Fast). 백업이 컨테이너와 함께 사라지는
구성으로 운영을 시작할 수는 없습니다.

**6. 이미지 저장소 보호 상태 (CTO 결정 1601-④)**

버킷의 Versioning·Replication을 읽어 체크리스트에 표시합니다.
**애플리케이션은 이미지를 직접 백업하지 않습니다.**

- 저장소가 알려 주지 않으면 `직접 확인`으로 남깁니다 — 조회를 지원하지 않는
  저장소를 "정상"이라고 말하면 그 화면은 거짓이 됩니다.
- 꺼져 있으면 `주의`이지 `실패`가 아닙니다. 버전 관리는 **삭제·덮어쓰기로부터
  보호**하는 장치이지, 지금 이미지가 없다는 뜻이 아닙니다.

**7. WAL · PITR · Incremental 도입 검토 (CTO 결정 1601-③)**

구현하지 않고 **판단 근거를 정리**했습니다 —
`docs/operations/backup-strategy.md`. 결론:

| 선택지 | 판단 |
| --- | --- |
| **백업 주기 단축** | **먼저 검토 권고** — RPO 24시간 → 1시간을 **복구 절차 변경 없이** 얻습니다. 덤프가 100KB라 하루 24회도 2.4MB입니다 |
| WAL Archive + PITR | **지금은 아님** — RPO는 분 단위가 되지만 **복구를 더 어렵게** 만듭니다. 지금은 `pg_restore` 한 줄이지만 PITR은 기준 백업 선택 + WAL 재생입니다. **연습하지 않은 PITR은 없는 것보다 위험합니다** |
| Incremental | **지금은 아님** — PostgreSQL 17 필요(현재 16)이고, 100KB 규모에서 **아낄 것이 없습니다**. 증분은 덤프가 커서 자주 못 받을 때 쓰는 수단이지, 하루 1회라서 24시간을 잃는 문제를 푸는 수단이 아닙니다 |

재검토 조건 4가지(덤프 1GB 초과 · 백업 1회 5분 초과 · 시점 복구 요구 발생 ·
리허설 절차 정착)를 두었고, **전부 이미 기록 중인 값**(`backup_runs`)으로
확인할 수 있습니다.

**8. 신선도 기본값 유지 (CTO 결정 1601-⑤)**

백업 2일 · 복원 검증 8일. 환경변수(`BACKUP_MAX_AGE_HOURS` ·
`RESTORE_MAX_AGE_HOURS`)로 조정 가능하되 **기본값을 회귀 테스트로 고정**
했습니다.

**9. 스스로 발견해 고친 결함 1건**

라이브 기동 검증에서 나왔습니다.

| 결함 | 증상 | 조치 |
| --- | --- | --- |
| 환경변수 설명의 마크다운 `**` | 기동 실패 로그에 `... — **컨테이너 밖 볼륨**을 가리켜야 한다`가 별표째 출력 | 3건 제거 + **ENV_SPECS 전체**를 검사하는 회귀 테스트 |

1302(경보 문구)·1601(경보 문구)에 이은 **같은 계열 세 번째 재발**이라, 이번에는

## 5. 아키텍처 변경 및 현황

**이번 주기 변경 — 존재 확인에서 사용 가능성 확인으로**:

```
backup ─▶ pg_dump ─┬─▶ stat (크기)          ─▶ 1KB 미만이면 실패
                   ├─▶ pg_restore --list    ─▶ 목차 0개면 읽힌 게 아니다
                   ├─▶ sha256               ─▶ 원격 사본 대조 근거
                   └─▶ putObject (선택)     ─▶ 실패해도 백업은 성공

GET /ops/readiness
   ├─ judgeIntegrity        ─▶ 확인 못 함 = manual, 읽기 실패 = fail(critical)
   ├─ judgeOffsite          ─▶ 미구성 = warn (복구는 된다)
   ├─ judgeStorageProtection ─▶ unknown = manual (모르는 것을 통과로 세지 않는다)
   ├─ judgeRecoveryObjectives ─▶ RTO = 측정된 복원 소요 시간(하한)
   └─ judgeRestoreTarget    ─▶ 운영 DB와 같으면 fail(critical) + 기동 차단
```

① **"있다"와 "쓸 수 있다"가 분리**됐습니다 — 크기·나이만 보던 판정에 **판독**이
   들어왔습니다.
② **위험한 설정이 런타임 판정이 아니라 기동 차단**이 됐습니다. 복원 대상 검사는
   환경 검증(코어)에 들어가 개발에서도 막습니다.
③ **RTO가 추정이 아니라 관측**입니다 — 이미 재고 있던 값을 판정에 연결했습니다.
④ **앱이 하지 않는 일을 화면이 대신 말해 줍니다** — 이미지 백업은 하지 않되,
   저장소 정책 상태를 표시합니다.

**유지되는 핵심 결정**: Alert 정책 4종(1302-①) · 게이트 운영 기본 ON(1302-③) ·
보관 90일·삭제 금지(1302-④·1501-③) · Live Check 수동(1301-①) · 자동 폴백
없음(1401-①) · 워커는 리더만(1401-②) · 로컬 시각 일 1회(1501-①) · Redis 장애 시
LLM 계속(1501-②) · 신선도 2일/8일(1601-⑤) · `/ops/*` ADMIN 전용

**현황**: 모노레포(web·api·core/shared/agents/ui), **마이그레이션 30건**,
drift 없음

"손상됨"이라는 거짓 경보가 되고, `true`로 채우면 더 나쁩니다.**
