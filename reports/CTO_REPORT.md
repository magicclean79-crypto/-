| ② OCR 운영 표준은 Google Cloud Vision | `PRODUCTION_OCR_PROVIDER === "google-vision"` · 개발용 엔진은 **성공 50건이어도 `done: false`** · 표준 엔진 단가가 가격표에 있음 |

②의 마지막 항목은 이번에 새로 확인한 연결입니다 — **운영 표준 엔진인데
가격표에 없으면** 비용이 미산정으로 빠져 예산 상한이 무력해집니다.

**4. OCR 비용 편입 (결정 2901-④)**

> OCR은 **호출당 과금되는 AI 호출**인데 비용이 어디에도 기록되지 않았습니다.
> 예산 상한은 LLM 지출만 보고 있었고, TASK-2901에서 실 OCR 엔진을 붙인 순간
> **예산 밖에서 돈이 나가는 경로**가 생겼습니다.

- `ocr_results.cost`·`units` 신설. 단가는 `DEFAULT_OCR_PRICING`(코드 선언
  중앙 정의) — `google-vision` 1,000단위당 $1.50.
- **무료 구간을 반영하지 않습니다.** Google Cloud Vision은 월 1,000단위까지
  무료지만 빼지 않고 전액을 셉니다: 빼면 예산이 **낙관적으로** 보이고, 한
  계정을 여러 환경이 공유하면 **남은 무료 구간을 우리가 알 수 없습니다.**
  모르는 것을 유리하게 가정하지 않습니다.
- **표에 없는 엔진은 `null`(미산정)입니다** — 0("과금 없는 엔진")과 다릅니다.
  0으로 채우면 예산 상한이 **조용히 무력**해집니다.
- **실패한 호출에는 비용을 적지 않습니다.** Provider에 따라 과금될 수 있지만
  우리는 알 수 없고, **모르는 것을 숫자로 적으면 예산이 거짓**이 됩니다.
  실패 호출 수는 관측에 그대로 남습니다.

**5. 예산은 "AI 지출 총액"입니다**

`combineAiSpend`가 두 원장(LLM Execution · OCR 실행 이력)을 합쳐 일·월 예산과
비교합니다.

> **원장을 합치지 않고 둘로 유지한 이유**: OCR은 LLM 호출이 아닙니다. 같은
> 표에 넣으면 토큰·모델·Failover·Provider 장애 판정이 뒤섞입니다.
> **지출은 하나로 보고, 원장은 성격대로 나눕니다.**

- 초과 시 **OCR도 호출 전에 429로 막습니다** — LLM과 같은 관문이고, 실행
  기록은 남지 않습니다(하지 않은 일을 기록하지 않습니다).
- **무엇이 막혔는지 문구가 말합니다**: "LLM 예산"이라고만 하면 OCR을 눌렀다
  429를 받은 사람이 엉뚱한 곳을 봅니다.
- 예산 현황에 `bySource`를 더했습니다 — 총액만 보여 주면 "왜 늘었는가"에 답할
  수 없어 예산을 올릴지 호출을 줄일지 판단할 수 없습니다.

**6. 비용 검증·관측 편입**

| 편입한 것 | 방식 |
| --- | --- |
| 비용 대조 | `verifyOcrCosts`가 LLM과 **같은 결과 모양**을 돌려주고, `/llm/cost-verification`이 둘을 합산하되 `bySource`로 원장별을 밝힘 |
| 미산정 경보 | 기존 `unpriced-model` 종류를 그대로 씀 (`unpriced-model:<engine>:text-detection`) |
| 성공률·지연·비용 | `monitorOcr`이 LLM과 **같은 판정 함수**(`monitorProduction`)를 씀 · `/llm/monitoring/ocr` |
| 장애 경보 | **같은 종류**(`provider-failure`) — 운영자에게는 "AI 경로가 죽었다"는 같은 사건 |

health-check는 LLM·OCR을 **한 번에 동기화**합니다 — 같은 종류를 두 번 부르면
뒤 호출이 앞의 경보를 "이번에 감지되지 않았다"며 해소합니다(TASK-2801에서
배운 형태를 그대로 피했습니다).

**7. 자체 발견 결함 — `null`을 0으로 세어 "불일치"로 보고했습니다**

> 비용이 `null`인 실행(비용 편입 이전의 실행)을 `cost ?? 0`으로 읽어
> **"기록 $0 vs 기대 $0.003 — 기록된 비용이 다릅니다"**로 보고했습니다.
> 기록이 없는 것과 0이 기록된 것은 다르고, 저 문구는 **기록된 값이 다르다**는
> 뜻이 되어 사실과 어긋납니다. 라이브 검증에서 문구를 읽다 드러났습니다.

`unrecorded` 종류를 신설해 **LLM·OCR 양쪽에서** 갈랐습니다("산정할 수 있는
호출인데 비용이 기록되지 않았습니다 — 예산 합계에서 빠집니다"). 이 프로젝트가
반복해서 고쳐 온 같은 형태입니다: **모르는 것을 0으로 취급하지 않습니다.**

## 5. 아키텍처 변경 및 현황

```
예산 관문 (호출 전)
   LlmService.complete ──┐
                         ├─▶ LlmBudgetService.assertWithinBudget({ what })
   OcrService.runOcr ────┘        │
                                  ├─ execution.aggregate(cost)   ← LLM 원장
                                  ├─ ocrResult.aggregate(cost)   ← OCR 원장
                                  └─ combineAiSpend → evaluateBudgetWindow
                                        초과면 429 (Failover 대상 아님)

비용 기록
   PrismaOcrRunStore.markSuccess ─▶ estimateOcrCost(provider, units)
        가격표 없음 → null(미산정) · 과금 없는 엔진 → 0 · 실패 → 기록 안 함

검증·관측 (같은 기준, 다른 표)
   /llm/cost-verification ─▶ verifyCosts(LLM) + verifyOcrCosts(OCR)
        unpriced / unrecorded / mismatch / missing-usage
   /llm/monitoring      ─▶ monitorProduction(LLM 표본)
   /llm/monitoring/ocr  ─▶ monitorProduction(OCR 표본)   ← 같은 함수
        health-check가 둘의 provider-failure를 **한 번에** sync
```

① **지출은 하나, 원장은 성격대로.** 상한을 나누면 어느 쪽도 총액을 막지 못하고,
   표를 합치면 통계가 뒤섞입니다.
② **모르는 것을 0으로 세지 않습니다.** `null`(미산정·미기록)을 0으로 읽는
   순간 예산도 문구도 거짓이 됩니다 — 이번 결함이 정확히 그것이었습니다.
③ **유리한 가정을 하지 않습니다.** 무료 구간을 빼지 않는 이유이고, 실패 호출에
   비용을 적지 않는 이유이기도 합니다(둘의 방향이 반대인데 원칙은 같습니다:
   **아는 것만 적는다**).
④ **판정 기준은 엔진마다 다를 이유가 없습니다.** 관측을 같은 함수로 두면
   한쪽 기준이 조용히 낡는 일이 없습니다.
⑤ **같은 종류의 경보는 한 번에 동기화합니다.** 두 번 부르면 뒤가 앞을 지웁니다.

**유지되는 핵심 결정**: Alert 정책 4종(1302-①) · 보관 90일·삭제 금지
(1302-④·1501-③·2501-⑤) · Live Check 기본 꺼짐(1301-①) · 예산 초과는 Failover
대상 아님(1002) · 백업 1시간 간격(1701-①) · 자동 복구 없음(2201-②) · 우회

## 6. 데이터 모델

**이번 주기 마이그레이션 1건** — `20260807000000_ocr_cost`.

| 컬럼 | 뜻 |
| --- | --- |
| `ocr_results.cost` (nullable) | 예상 비용(USD) — **`null`은 "가격표에 없어 산정하지 못했다"**이고 0("과금 없는 엔진")과 다릅니다 |
| `ocr_results.units` (기본 1) | 과금 단위 수 (이미지 1장 · 검사 1종 = 1) |
| `ocr_results` `createdAt` 인덱스 | 일·월 예산 집계가 기간으로 자릅니다 — 없으면 전체 스캔입니다 |

기존 행의 `units`는 1입니다 — 그때도 호출 1건이었다는 것이 아는 전부입니다.
기존 행의 `cost`는 `null`로 남고, 비용 검증이 그것을 **`unrecorded`**(기록되지
않음)로 정확히 보고합니다 — 0으로 백필하지 않았습니다: **나가지 않은 돈을 0으로
적으면 그 실행이 공짜였다는 뜻이 되고, 사실은 모르는 것입니다.**

**Major Migration으로 지정하지 않았습니다.** nullable 컬럼 추가와 인덱스
추가뿐이고, 데이터 이전도 파괴적 변경도 없으며 재해 복구 절차를 바꾸지
않습니다(결정 1901-① 기준).

## 7. API 표면

**새 엔드포인트 1개**:

- `GET /llm/monitoring/ocr?minutes=` — OCR 성공률·지연·비용. **ADMIN 전용**.
  LLM 모니터링과 같은 DTO(`ProductionMonitorDto`)입니다 — 같은 기준으로
  판정하므로 모양도 같습니다.

**기존 계약 확장**:

- `GET /llm/budget` — **`bySource`** 추가 (`{daily, monthly} × {llm, ocr}`).
  `daily.spend`·`monthly.spend`의 의미가 **"AI 지출 총액"**으로 넓어졌습니다
  (그전에는 LLM만).
- `GET /llm/cost-verification` — **`bySource`**(원장별 기록 합계)와
  **`ocrPricing`** 추가. `checked`·`unpricedCalls`·`issues`가 **OCR을 포함**합니다.
- `CostIssueDto.kind`에 **`unrecorded`** 추가.
- `POST /images/:id/ocr`·`GET …/ocr` — **`cost`·`units`** 추가.
  **예산 초과 시 429**가 새로 나올 수 있습니다(그전에는 OCR이 상한 밖이었습니다).
- `POST /ops/checks/run?job=health-check` — `detail`에 OCR 호출 수·상태가
  붙고, **OCR 엔진 장애가 `provider-failure` 경보로 나갑니다.**

**내부 계약**: `LlmBudgetService.assertWithinBudget({ what? })` — 인자는
선택이고, 넘기지 않으면 문구가 "AI 호출"입니다.

## 8. 리스크·기술 부채

1. **3001 해석 미확인** — 단가 갱신 책임·무료 구간·OCR 예산 분리
   (CTO_REQUEST #63)
2. **단가는 코드에 박혀 있습니다** — Google이 단가를 바꾸면 우리 계산이
   조용히 틀립니다. 비용 검증이 `mismatch`로 드러내지만, **표를 갱신하는 책임과
   주기는 정해지지 않았습니다**(#63 ①)
3. **무료 구간을 반영하지 않아 예상 비용이 실제보다 큽니다** — 보수적인 쪽으로
   틀린 것이지만, 월 1,000단위 이하로 쓰는 환경에서는 예산이 실제보다 빨리
   찹니다(#63 ②)
4. **OCR과 LLM이 같은 상한을 씁니다** — OCR 급증이 LLM 호출을 막을 수 있고,
   반대도 가능합니다. 원장은 나눠 두었으니 상한을 나누는 것도 가능하지만,
   **총액을 막는 상한이 하나여야 한다**고 판단했습니다(#63 ③)
5. **실패한 OCR 호출의 과금은 모릅니다** — 비용을 적지 않으므로 **실제 청구가
   우리 집계보다 클 수 있습니다.** Provider별 정책 확인이 필요합니다
6. **실 Google Cloud Vision·실 LLM 호출은 여전히 미검증** — 실 키와 외부
   네트워크가 필요합니다(TASK-2901과 동일)
7. **OCR 예산 초과가 사용자 흐름을 끊습니다** — 이미지를 올린 뒤 OCR이 429가
   되면 사용자는 다음 단계로 갈 수 없습니다. 상한의 목적이 그것이지만, 화면
   안내는 아직 API 메시지 그대로입니다
8. **운영 저장소가 아직 S3가 아닙니다**(결정 2101-④) · **백업 성능 기준은 개발
   규모에서만 검증**(1901-④ 대기) · **GitHub Actions 실제 실행 미확인**
9. **디스크 할당량이 빠듯합니다** — 이번 검증 중 소진되어 e2e가 2건 실패했고,
   정리 후 통과했습니다. 빌드 캐시·검증 산출물 정리가 반복 작업이 되고 있습니다
