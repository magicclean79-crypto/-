## 3. 변경 사항 (이번 보고 주기)

### TASK-2001 — Enterprise Backup Integrity Platform

CTO 결정 1901-①~⑤가 이번 TASK의 범위였습니다.

주제는 **남지 않은 것을 보는 것**입니다. 지금까지의 판정은 전부 **남은
기록**을 읽었습니다 — 백업이 실패하면 이력에 남고, 복원이 실패하면 이력에
남습니다. 그런데 **돌지 않은 백업은 아무 데도 기록되지 않습니다.** 서버가
멈춰 있던 구간에는 실패 기록조차 없어서, 백업 이력만 보면 **개별 백업이 전부
성공**으로 보입니다. 이번 TASK는 그 빈 구간을 판정 대상으로 끌어왔습니다.

**1. 백업 사슬 연속성 (신규)**

관측 창(기본 24시간) 안에 **있어야 할 개수와 실제 개수를 비교**합니다.
공백은 세 곳에서 셉니다 — 창 시작 ~ 첫 백업, 백업 사이, 마지막 백업 ~ 지금.

| 상황 | 판정 |
| --- | --- |
| 최대 공백 ≤ 간격 × 2 | 통과 |
| 최대 공백 > 간격 × 2 | **실패** (심각 경보 `backup-integrity:chain`) |
| 창 안 성공 0회 | **실패** |
| 이력이 전혀 없는 첫 도입 | 직접 확인 |

- **`backup-chain`은 복구 필수 항목입니다.** 공백 구간은 되돌아갈 수
  없습니다 — 백업 파일이 하나도 없는 것과 그 구간에 한해 같습니다.
- **한 번 걸러도 2배 안이면 통과합니다.** 지연에 매번 경보하면 정작 불러야
  할 때 오지 않습니다.
- **처음 켠 서버를 "사슬이 끊겼다"고 하지 않습니다.** 다만 **기동 전에 이미
  백업이 돌던 시스템이라면 꺼져 있던 동안의 공백은 진짜 공백입니다** —
  재기동이 공백을 지우지 않습니다(§4 자체 발견 결함 ①).

**2. 원격 사본 무결성 (결정 1701-④ 후속)**

올렸다는 **기록**과 사본이 실제로 **있다**는 것은 다릅니다.
`POST /ops/backup/verify-remote`가 마지막 원격 사본을 **내려받아** SHA-256을
기록된 체크섬과 대조합니다.

| verdict | 뜻 |
| --- | --- |
| `unchecked` | 확인하지 않음 → **통과가 아니라 `직접 확인`** |
| `missing` | 올렸다고 기록됐지만 실제로는 없음 (수명 주기 정책·삭제) |
| `mismatch` | 업로드 절단·덮어쓰기 — **이 사본으로는 복구를 장담할 수 없음** |
| `ok` | 일치 |

- **기본으로 돌지 않습니다** — 전송 비용이 듭니다(결정 1301-⑤의 연장).
- **복구 필수 항목은 아닙니다** — 로컬 덤프로 복구는 되므로, 지금의 복구
  가능성을 막지는 않습니다. 실패는 심각 경보로만 알립니다.

**3. 운영 저장소 표준 = Amazon S3 (결정 1901-③)**

1801-④에서는 기동 시 **경고**였습니다. 이번에 체크리스트 항목
`storage-standard`로 **승격**했습니다.

| 상황 | 판정 |
| --- | --- |
| 운영 · `*.amazonaws.com` | 통과 |
| 운영 · 그 외 / 미설정 | **실패** |
| 개발 · 아무 호스트 | 통과 (`개발에서는 정상입니다`) |
| 해석 불가 주소 | 직접 확인 |

**개발자에게 S3를 요구하지 않습니다.** 표준은 운영에만 적용합니다 — 개발
환경까지 실제 S3를 쓰게 만들면 비용이 들고, 결국 아무도 지키지 않습니다.

**4. DB 규모 재평가 신호 (결정 1901-④)**

`pg_database_size`로 실측해 10 · 50 · 100GB 도달을 알립니다.
**크기 자체가 문제가 아니라, 백업 성능 기준(2초·10초·30초)을 실측으로 다시
재라는 신호**입니다.

- 기준마다 경보 키가 다릅니다(`backup-integrity:scale:<bytes>`) — 10GB를
  해소하고 50GB에서 **다시** 알려야 하기 때문입니다.
- **기준을 자동으로 바꾸지 않습니다.** 재평가는 사람이 합니다.
- 크기를 읽지 못하면 통과로 세지 않고 `직접 확인`으로 둡니다.

**5. Major Migration만 자동 등록 (결정 1901-①)**

마이그레이션이 전부 대규모 변경은 아닙니다. 컬럼 하나 추가할 때마다 리허설을
요구하면 **부를 일이 아닌데 부르는 것**이고, 그러면 정작 불러야 할 때 오지
않습니다.

`apps/api/prisma/major-migrations.json`에 지정된 것만, 기동 시
`_prisma_migrations`와 대조해 등록합니다. `dr-change`·`pitr-adoption`은 코드가
알 수 없는 사건이므로 **운영자가 직접 등록**합니다.

**6. 중복 등록 금지 (결정 1901-⑤)**

같은 `trigger`가 미해소 상태이면 `409 Conflict`입니다. 리허설 1회로 함께
해소되므로 쌓을 이유가 없고, 쌓이면 목록만 길어져 **정작 무엇이 남았는지**
보이지 않습니다.

**7. 삭제 금지, 취소만 (결정 1901-②)**

`cancelledAt` · `cancelledBy` · `cancelReason`을 추가했습니다.

- `cancelledBy`와 `reason`은 **필수**입니다 — 왜 취소했는지가 남지 않으면
  기록이 아닙니다.
- 이미 리허설로 해소된 요구는 취소할 수 없습니다(`409`).
- 취소된 요구는 목록에서 **사라지지 않고 사유와 함께 남습니다.** 지운 요구는
  왜 지웠는지 남지 않지만, 취소는 남습니다.
- 취소 후에는 같은 `trigger`를 다시 등록할 수 있습니다.

**8. 화면 (`/admin/operations`)**

백업 보호 구역에 **백업 사슬 연속성 · 원격 사본 무결성 · 운영 저장소 표준 ·
데이터베이스 규모** 4개 항목을 추가했습니다. 원격 사본 검증 버튼에는
**"(전송 비용)"**을 명시했고, 리허설 요구마다 **취소** 버튼과 **취소된 요구**
목록을 두었습니다.

## 5. 아키텍처 변경 및 현황

**이번 주기 변경 — 기록의 부재를 판정 대상으로**:

```
backup_runs (기간 조회) ─▶ judgeBackupChain
                            ├─ 있어야 할 개수 vs 실제 개수
                            ├─ 최대 공백 > 간격 × 2 → fail (critical)
                            └─ 이력 없는 첫 도입   → manual
                                  ▲
                                  └── 돌지 않은 백업은 아무 데도 남지 않는다

S3 backup bucket ─▶ getBackupObject ─▶ SHA-256 ─▶ judgeRemoteIntegrity
   (수동 실행 — 전송 비용)                            └─ 미확인은 통과가 아니다

pg_database_size ─▶ judgeDatabaseScale  ─▶ 10·50·100GB → 재평가 신호
S3_ENDPOINT      ─▶ judgeStorageStandard ─▶ 운영은 S3, 개발은 그대로

major-migrations.json ─┬─▶ _prisma_migrations 대조 ─▶ db-major-change 자동 등록
                       └─ 지정된 것만 (부를 일이 아닌데 부르지 않는다)

cancelRequirement ─▶ cancelledAt/By/Reason  (삭제 없음)
```

① **부재를 판정합니다** — 기록된 실패가 아니라 **기록되지 않은 구간**을
   봅니다. 이것이 이번 TASK의 유일한 새 개념입니다.
② **비용이 드는 확인은 기본으로 돌지 않습니다** — 결정 1301-⑤의 원칙을
   원격 사본 대조까지 그대로 이었습니다.
③ **자동 조치를 넣지 않았습니다** — 성능 기준 재평가도, 저장소 전환도,
   `dr-change` 등록도 사람의 몫입니다.
④ **기록은 지우지 않습니다** — 경보(1302-④), Dead Letter(1501-③)에 이어
   리허설 요구까지 같은 규칙을 적용했습니다.

**유지되는 핵심 결정**: Alert 정책 4종(1302-①) · 보관 90일·삭제 금지
(1302-④·1501-③) · 자동 폴백 없음(1401-①) · 로컬 시각 일 1회(1501-①) ·

## 6. 데이터 모델

**마이그레이션 33** (`20260801000000_requirement_cancel`):

| 대상 | 변경 | 이유 |
| --- | --- | --- |
| `drill_requirements` | **`cancelledAt`** · **`cancelledBy`** · **`cancelReason`** 추가 | 삭제는 금지, 취소만 허용 (결정 1901-②) |

세 컬럼을 함께 둔 이유는 **취소가 사건이기 때문**입니다. 언제·누가·왜를
같이 남기지 않으면 나중에 "이 요구는 왜 없어졌지"에 답할 수 없습니다.

사슬·원격·규모·저장소 표준은 **새 컬럼 없이** 기존 `backup_runs`와
`pg_database_size`, 환경변수로 판정합니다.

**신규 매니페스트** `apps/api/prisma/major-migrations.json` — Major Migration
목록입니다. DB가 아니라 **코드에 둔 이유**는, 어떤 변경이 대규모인지는 그
변경을 만든 사람이 판단해야 하고, 그 판단이 리뷰를 거쳐야 하기 때문입니다.

## 8. 리스크·기술 부채

1. **2001 해석 미확인** — 사슬 관측 창·원격 검증 주기·Major Migration 지정
   주체 (CTO_REQUEST #53)
2. **사슬 관측 창이 24시간 고정입니다** — 환경변수로 열지 않았습니다. 백업
   간격이 길어지면(예: 일 1회) 창 안 표본이 1~2개뿐이라 판정이 거칠어집니다(#53 ①)
3. **원격 사본 대조는 수동입니다** — 비용 때문에 기본으로 돌리지 않았으나,
   아무도 누르지 않으면 영영 `직접 확인`으로 남습니다(#53 ②)
4. **Major Migration 지정은 사람이 합니다** — 매니페스트에 넣는 것을 잊으면
   자동 등록도 일어나지 않습니다. 자동화의 시작점이 여전히 수동입니다(#53 ③)
5. **`db-major-change` 자동 등록은 기동 시 1회만 일어납니다** — 마이그레이션만
   적용하고 재기동하지 않으면 등록되지 않습니다
6. **운영 저장소가 아직 S3가 아닙니다** — 이제 체크리스트에서 **실패**로
   드러납니다. 전환 전까지 이 실패가 상시 표시됩니다
7. **백업 성능 기준은 여전히 개발 규모에서만 검증됐습니다** — 실측 10.5MB.
   10GB 신호는 아직 울려 본 적이 없습니다(주입 테스트로만 확인)
8. **복원 검증은 테이블 수만 봅니다** — 행 수·제약까지 보지 않습니다
9. **실 Provider 스모크는 여전히 미검증** — 샌드박스 차단 + 과금
