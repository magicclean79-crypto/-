## 3. 변경 사항 (이번 보고 주기)

### TASK-2701 — Enterprise Governance Automation Platform

TASK-2601이 스캔 **도구**를 만들었습니다. 이번에는 그것을 **예약으로 돌리고,
늘었을 때만 부르고, 큰 프로젝트에서도 정확하게** 만들었습니다.

**1. 이미 나간 위반의 공식 절차 (결정 2601-①)**

`PUBLISHED → ARCHIVED → 수정 → 재발행`으로 확정됐습니다.

> **그런데 그 절차를 코드가 막고 있었습니다.**
>
> `ARCHIVED`는 Sprint 1부터 **종결 상태**(`ARCHIVED: []`)였습니다. 즉 내린
> 콘텐츠를 고쳐 다시 올릴 길이 없었고, 확정된 절차의 "수정 → 재발행"을 밟을
> 수 없었습니다.
>
> **절차를 정해 두고 코드가 막고 있으면 사람은 새 콘텐츠를 만들어
> 우회합니다.** 그러면 **왜 내렸는지가 새 콘텐츠에 남지 않습니다** — 감사
> 이력이 끊기고, 같은 위반이 다시 나가도 아무도 설명할 수 없습니다.

`ARCHIVED → DRAFT` **되살리기**를 열었습니다.

- **`ARCHIVED → PUBLISHED` 직행은 열지 않았습니다.** 되살린 것은 `REVIEW`를
  거쳐야 하고, 그래야 **거버넌스 게이트가 다시 돕니다**(TASK-2501). 내린
  이유를 고치지 않은 채 곧바로 되돌아가는 길을 열면 내린 것이 아무 의미가
  없습니다. 400 문구가 경로를 안내합니다.
- **별도 상태(`SUSPENDED`)는 만들지 않았습니다.** 상태 목록 자체를 테스트로
  고정했습니다 — 주석이 아니라 값을 봅니다.

**2. 예약 스캔 (결정 2601-②)**

`governance-scan` 작업, **매일 03:50 로컬**. 보관 정리(04:00)보다 **앞에**
두었습니다 — 스캔이 남긴 기록을 보관이 곧바로 치우면 방금 만든 것을 못 봅니다.

위반이 있는 것은 시스템 장애가 아니므로 점검 자체는 `ok: true`입니다.
`ok: false`로 두면 **예약 점검 실패로 읽혀 엉뚱한 곳을 보게 됩니다.**

**3. 늘었을 때만 부른다 (결정 2601-③)**

| 상황 | 경보 | 이유 |
| --- | --- | --- |
| 첫 스캔 | 없음 (**기준선**) | 규칙을 처음 켠 직후 위반이 잔뜩 있는 것은 정상입니다 |
| 늘었음 | **발생** | 증가분과 무엇이 늘었는지 말합니다 |
| 같음 | 없음 | 이미 알렸습니다 |
| 줄었음 | 없음 (기존 경보 유지) | 좋은 일로 사람을 깨우지 않습니다 |
| 0이 됨 | **해소** | 있던 것이 없어졌을 때만 해소입니다 |

이미 나간 위반이 섞이면 **심각**입니다. 비교 기준은 **범위별**
(`all` / `project:<id>`) — 뭉치면 어디를 봐야 할지 알 수 없습니다.

**경보를 만들지 않은 실행도 기록합니다.** "돌았지만 조용했다"와 "돌지
않았다"는 다르고, 그 구분이 없으면 예약이 멈춘 것을 알아챌 수 없습니다.

**4. 페이지 (결정 2601-④)**

`?offset`·`?limit`은 **목록만** 자르고 **`summary`는 항상 전체 기준**입니다.

판정은 **전량**을 합니다. 내부에서 **커서**(`createdAt`+`id`)로 200건씩 나눠
읽습니다 — `skip`으로 넘기면 읽는 도중 새 콘텐츠가 생겼을 때 **한 건을 두 번
세거나 건너뜁니다.**

잘못된 `offset`은 **400**입니다. 조용히 0으로 되돌리면 운영자는 **다른 페이지를
보고 있는 줄도 모릅니다.**

**5. 규칙 캐시는 Request Scope만 (결정 2601-⑤)**

`GovernanceRulesService.snapshot()` — 스캔 한 번에 규칙을 **한 번만** 읽습니다.
500건 스캔이면 조회 500회가 1회로 줄고, **한 스캔 안에서 규칙은 바뀌지
않으므로** 판정의 단일 원천을 흐리지 않습니다.

**전역 캐시는 두지 않았습니다.** 규칙을 고친 운영자가 **언제 반영되는지 알 수
없게 되면** 규칙을 신뢰할 수 없습니다 — "고쳤는데 왜 그대로인가"를 TTL로
설명해야 하는 상태를 만들지 않습니다. 없다는 사실을 소스 검사로 고정했습니다.

## 5. 아키텍처 변경 및 현황

**이번 주기 변경 — 예약과 비교**:

```
governance-scan (매일 03:50 로컬)          ← 보관 정리(04:00)보다 앞
   └─ GovernanceScanService.run(scope)
        ├─ GovernancePreflightService.scan   쓰기 없음 · 전량 판정
        │    └─ rules.snapshot()  ← 요청 1회만 읽는다 (전역 캐시 없음)
        ├─ compareScan(previous, current)    ← governance_scan_runs 직전 행
        │    baseline / increased / decreased / unchanged / resolved
        ├─ detectGovernanceScanAlert   ← **increased일 때만** 경보
        └─ shouldSyncScanAlerts        ← increased·resolved일 때만 sync

PUBLISHED ──▶ ARCHIVED ──▶ DRAFT ──▶ REVIEW ──▶ PUBLISHED
              (내림)      (되살림)   (검토)     (게이트 재실행)
                └─ ARCHIVED → PUBLISHED 직행 없음
```

① **경보의 기준은 "있다"가 아니라 "늘었다"입니다.** 매번 도는 점검이 상태를
   그대로 알리면 그 경보는 배경 소음이 됩니다.
② **경보를 만드는 것과 저장소를 동기화하는 것은 다른 판단입니다.** 이번 결함이
   그 구분을 놓쳐서 생겼습니다 — `sync`는 "감지되지 않았으면 해소"로 읽으므로
   부를 때를 따로 정해야 합니다.
③ **절차를 정하면 코드가 그 절차를 밟을 수 있어야 합니다.** 막혀 있으면 사람은
   우회하고, 우회하면 기록이 끊깁니다.
④ **되살리는 길은 게이트를 다시 지나게 합니다.** 내린 이유를 고치지 않은 채
   되돌아가는 길을 열면 내린 것이 무의미합니다.
⑤ **페이지는 목록만 자릅니다.** 집계가 페이지에 따라 달라지면 그 숫자로는
   아무 판단도 할 수 없습니다.
⑥ **캐시는 요청 안에서만** — 규칙 반영 시점을 사람이 예측할 수 있어야 합니다.

## 6. 데이터 모델

**이번 주기 마이그레이션 1건** — `20260805000000_governance_scan_runs`.

`governance_scan_runs` 테이블 신설:

| 컬럼 | 뜻 |
| --- | --- |
| `scope` | `all` 또는 `project:<id>` — **비교 기준을 가르는 키** |
| `scanned`·`blocked`·`publishedViolations`·`warned`·`clean` | 그때의 집계 |
| `byCheck` (JSONB) | 검사별 집계 — 무엇이 늘었는지 되짚을 근거 |
| `verdict` | 지난 결과와 비교한 판정 |
| `previousTotal`·`total` | 비교의 양쪽 (첫 스캔이면 `previousTotal`은 null) |
| `alerted` | 이 실행이 경보를 만들었는가 |
| `trigger` | `schedule` \| `manual` |

**"늘었을 때만"을 판정하려면 지난 결과가 남아 있어야 합니다.** 같은 결과로
반복해서 부르지 않는다는 것은 곧 "지난번이 무엇이었는지 기억한다"는 뜻입니다.

**Major Migration으로 지정하지 않았습니다.** 새 테이블·새 인덱스뿐이고 데이터
이전도 파괴적 변경도 없으며 재해 복구 절차를 바꾸지 않습니다(결정 1901-① 기준).

`ContentStatus` enum은 **바뀌지 않았습니다** — 되살리기는 전이 규칙(코드)만
바꿉니다. 그래서 이 결정에는 마이그레이션이 필요하지 않습니다.

## 7. API 표면

**새 엔드포인트 2개**:

- `GET /governance/scans` — 전체 범위 예약 스캔 이력. **ADMIN 전용**.
  `?scope=`·`?limit=`
- `GET /projects/:projectId/governance/scans` — 프로젝트 범위 이력

**기존 계약 확장**:

- `GET …/governance/preflight` — `?offset=` 추가, 응답에 **`page`** 추가
  (`offset`·`limit`·`total`·`hasMore`). `summary`의 의미는 그대로 **전체 기준**
- `PATCH …/contents/:id/status` — **`ARCHIVED → DRAFT`가 허용됩니다.**
  그 전에는 400이었습니다. `ARCHIVED → PUBLISHED`·`ARCHIVED → REVIEW`는
  여전히 400이고, 응답 `message`가 되살리기 경로를 안내합니다
- `POST /ops/checks/run?job=governance-scan` — 새 작업. `GET /ops/alerts`의
  `schedules`에 항목이 하나 늘어납니다

**shared DTO 추가**: `PreflightPageDto` · `GovernanceScanRunDto`

**새 경보 종류**: `governance-scan` (쿨다운 `ALERT_COOLDOWN_GOVERNANCE_SCAN_MS`)

## 8. 리스크·기술 부채

1. **2701 해석 미확인** — 되살리기 권한·재발행 시각·스캔 범위
   (CTO_REQUEST #60)
2. **되살리기 권한이 발행과 같습니다** — `EDITOR` 이상이면 보관된 콘텐츠를
   되살릴 수 있습니다. 내린 것을 되살리는 일이 더 높은 권한을 요구해야
   하는지는 정하지 않았습니다(#60 ①)
3. **`publishedAt`이 최초 발행 시각을 보존합니다**(TASK-0703 승인 ②) —
   내렸다 다시 올린 콘텐츠는 **"언제부터 나가 있는가"를 이 값으로 알 수
   없습니다.** 감사 이력에는 남지만 목록 화면은 옛 날짜를 보여줍니다(#60 ②)
4. **예약 스캔은 전체 범위만 돕니다** — 프로젝트별 기준선은 사람이 한 번
   호출해야 생깁니다. 프로젝트가 많아지면 전체 숫자 하나로는 어디가
   나빠졌는지 알기 어렵습니다(#60 ③)
5. **전량 판정의 비용은 콘텐츠 수에 비례합니다** — 규칙 조회는 1회로 줄였지만
   판정 자체는 건당 수행됩니다. 현재 실측(32건) 기준으로는 문제가 없고,
   상한을 두지 않은 것은 **요약의 정확성이 결정 ④의 요구**이기 때문입니다
6. **경보 문구는 총량만 말합니다** — 어떤 콘텐츠가 새로 위반이 됐는지는
   말하지 않습니다(`byCheck`는 기록에만 남습니다)
7. **보관된 판정 기록은 목록 UI가 없습니다** — API로만 볼 수 있습니다
8. **운영 저장소가 아직 S3가 아닙니다** — 전환은 운영 담당자 몫(결정 2101-④)
9. **백업 성능 기준은 여전히 개발 규모에서만 검증됐습니다**(결정 1901-④ 대기)
10. **실 Provider 스모크는 여전히 미검증** — 샌드박스 차단 + 과금
11. **GitHub Actions 실제 실행은 확인하지 못했습니다** — 워크플로 순서는
    테스트로 고정했습니다
