## 3. 변경 사항 (이번 보고 주기)

### TASK-4601 — Operations Intelligence

**3-1. 정책 ①②에 대해 먼저 말씀드립니다**

정책 ①은 "준비되는 즉시 수행한다", ②는 "성공 후 완료한다"였습니다.
**둘 다 하지 못했습니다.**

```
POST /ops/validation-run/execute  → HTTP 403
SELECT count(*) FROM validation_runs;  →  0
```

넷 중 하나도 준비되지 않았습니다. TASK-4501에서 만든 실행기는 **준비가
끝나는 순간 이 경로 하나로 검증이 시작되도록** 되어 있고, 지금 막고 있는
것은 코드가 아니라 그 넷입니다.

**3-2. Teams Adaptive Card 전환 계획과 구현안 (정책 4601-③)**

정책은 "계획과 구현안을 **준비한다**"였습니다. 그래서 **둘 다 만들되 기본값은
바꾸지 않았습니다.**

이 저장소는 **실제 Teams 워크스페이스에 붙어 본 적이 없습니다.** 지금까지
Teams로 나간 알림은 전부 우리 수신 스텁이 받았습니다. 확인할 수 없는 형식을
기본값으로 두면 그것이 틀렸다는 사실을 **첫 장애 때** 알게 되고, 알림
체계에서 그건 가장 하면 안 되는 변경입니다 — 알림이 안 가는 것은 조용하기
때문입니다.

특히 위험한 실패 모양 하나를 코드로 막았습니다:

> **봉투 없이 카드만 보내면 Teams는 200을 돌려주고 아무것도 안 띄웁니다.**

우리 기록에는 `ok: true · status: 200`으로 남습니다. **성공으로 기록되는
실패**이고, 우리가 스프린트마다 경계해 온 바로 그 모양입니다. 그래서
`teamsAdaptiveBody()`는 Workflows 봉투(`{type:"message", attachments:[…]}`)
까지 만들고 테스트가 그 봉투를 검사합니다.

그리고 **형식이 둘이면 한쪽만 고치는 날**이 옵니다. 담아야 하는 사실을
`teamsCardFacts()` 목록으로 두고 두 형식 모두에 들어 있는지 검사합니다.

전환은 `TEAMS_CARD_FORMAT=adaptive` **한 줄**이고 되돌리는 것도 같은 한
줄입니다. 절차·확인 항목·되돌리는 법은
`docs/operations/teams-adaptive-card-plan.md`에 적었습니다.

**3-3. 최근 24시간 도달 (정책 4601-④)**

TASK-4501의 Go-Live는 "이 채널로 **한 번이라도** 성공한 기록이 있는가"를
물었습니다. 그건 너무 약한 질문이었습니다 — 3주 전에 한 번 닿은 채널과 지금
닿는 채널이 같은 초록으로 보이고, 웹훅 주소는 조용히 만료되며, 만료된 주소는
**다음 장애 때** 알게 됩니다.

이제 **최근 24시간**을 봅니다. 다만 여기서 한 가지를 조심했습니다:

| 판정 | 뜻 |
| --- | --- |
| `reached` | 창 안에 성공이 있다 |
| `failing` | 창 안에 시도가 있는데 전부 실패 |
| **`silent`** | **창 안에 시도가 없다 — 죽은 것인지 조용한 것인지 모른다** |
| `never` | 성공 기록이 아예 없다 |
| `disabled` | 주소가 없다 (실패가 아니다) |

24시간 동안 아무 시도도 없었다면, 그건 채널이 죽어서가 아니라 **보낼 일이
없어서**일 수 있습니다. 장애가 없는 하루는 좋은 하루입니다. 그 하루를 "채널
실패"로 칠하면 경고가 배경 소음이 되고, 진짜로 주소가 만료된 날에 아무도 안
봅니다. 그렇다고 통과로 세지도 않습니다 — 우리는 **모릅니다.**

모른다고만 적고 끝내지 않았습니다. **확인하는 방법**(`POST
/ops/notifications/test`)을 함께 적습니다 — 방법을 안 적으면 그 칸은 영원히
회색으로 남습니다.

**3-4. 담당자 직접 알림 (정책 4601-④)**

TASK-4401부터 남아 있던 부채입니다(#78 ③ · #79에서도 남음). 검토 알림은
담당자 이름을 본문에 적고 **공용 채널로** 갔습니다 — 채널을 보는 사람과
항목을 맡은 사람은 대개 다릅니다.

`ALERT_OWNER_CONTACTS`로 표를 받고, 세 가지를 지켰습니다:

- **연락처를 못 찾아도 조용히 삼키지 않습니다.** 안 보내면 담당자를 적어 둔
  것이 오히려 알림을 없애는 셈이 됩니다. 공용 채널로 보내되 **"이 사람의
  연락처가 없다"를 본문에 붙입니다.**
- **이름에서 주소를 유추하지 않습니다**(`김운영` → `kim@…`). 틀린 주소로
  보낸 알림은 안 보낸 것과 같은데, 기록에는 "보냈다"로 남습니다.
- **직접 보내도 공용 채널을 끄지 않습니다.** 직접 경로가 생겼다고 공용을
  끄면 담당자가 휴가 중일 때 그 항목은 아무도 모르는 채로 지나갑니다.

**3-5. 재전송 (정책 4601-④)**

재시도와 재전송은 다릅니다:

| | 재시도 (1401) | 재전송 (4601) |
| --- | --- | --- |
| 언제 | 한 번의 전송 안에서, 초 단위 | 전송이 끝난 뒤, 분·시간 단위 |
| 고치는 것 | 순간적인 흔들림 | 잠깐 죽었다 살아난 채널 |
| 한계 | 4회 안에 끝 | 15분 → 1시간 → 4시간, 3회 |

TASK-1401의 재시도는 4회 만에 포기하고 **그것으로 끝이었습니다.** 슬랙이
5분 죽어 있었다면 그 사이의 경보는 영영 전달되지 않고, 사람은 장애가
있었다는 사실 자체를 모릅니다.

| 규칙 | 왜 |
| --- | --- |
| 같은 `alertKey`로 보낸다 | 새 키를 만들면 한 장애가 여러 장애로 보이고 장애 건수가 부풀려진다 |
| 4xx는 재전송하지 않는다 | 재시도에서 정한 판단을 뒤집지 않는다 — 잘못된 URL은 4시간 뒤에도 잘못된 URL이다 |
| 해소된 경보는 보내지 않는다 | 끝난 일로 사람을 깨우는 것은 알림을 끄게 만드는 가장 빠른 길이다 |
| 하루 지나면 보내지 않는다 | 그때는 알림이 아니라 기록이다 — 그 시점에 할 수 있던 일이 이미 달라졌다 |
| **상한에 닿아도 조용히 그만두지 않는다** | 조용히 그만두면 아무도 못 받은 알림이 **없는 일**이 된다 |
| 본문에 몇 번째인지 적는다 | 안 적으면 한 장애를 여러 장애로 착각한다 |

**3-6. 통합 운영 대시보드 (정책 4601-⑤)**

Validation · Attribution · Notification · Recovery를 한 화면에 모읍니다.
**여기서 새로 판정하지 않습니다**(4301-④ · 4401-⑤ · 4501-⑤와 같은 규칙).

준비 화면과 묻는 질문이 다릅니다: 준비 화면은 **"검증을 시작해도
되는가"**(앞), 이 화면은 **"지금 운영이 어떤 상태인가"**(지금).

통합 화면의 유혹은 **"전체 정상"이라는 한 줄**입니다. 넷 중 하나를 못
읽었는데 나머지가 초록이면 그 한 줄은 거짓말이 됩니다. 그래서 요약은
최악값을 따르고, **못 본 사실을 문장 맨 앞에** 적습니다 — 뒤에 붙이면
앞부분만 읽힙니다.

### 4-1. 라이브 결함 — 요약은 "못 읽었다", 칸은 "판정 안 했다"

통합 화면을 실 DB로 처음 열었을 때 요약이 이랬습니다:

```
1개 갈래를 읽지 못했습니다(Attribution) — 이 화면의 요약은 그만큼 덜 본 것입니다.
```

그런데 바로 아래 Attribution 칸은 이렇게 말했습니다:

```
귀속 대상 8건 중 5건 귀속 (62.5%). 표본이 20건에 못 미쳐 목표(95%) 달성
여부를 판정하지 않았습니다 — 달성도 미달도 아닙니다.
```

**우리는 그 갈래를 읽었습니다.** 판정을 유보했을 뿐입니다. 같은 화면 안에서
같은 사실에 두 개의 답이 있었고, 이건 우리가 4101부터 계속 경계해 온 모양
입니다.

원인은 `unknown` 하나에 두 가지를 뭉쳐 넣은 것입니다:

| | 뜻 | 사람이 할 일 |
| --- | --- | --- |
| 못 읽음 | 판정을 부르지 못했다 | **고칠 버그** |
| 판정 유보 | 읽었는데 판단할 근거가 모자라다 | **표본·트래픽이 더 필요한 일** |

둘 다 통과가 아니지만 **할 일이 다릅니다.** 뭉쳐 놓으면 고칠 버그가 "기다리면
되는 일"로 읽힙니다.

`OverviewTile.read`를 더해 갈랐고, 요약도 두 문장으로 나눴습니다. 세는
자리의 이름도 "확인 못 함"에서 **"확실하지 않음"** 으로 바꿨습니다 — 한 칸에
둘이 들어가므로 어느 한쪽 이름으로 부르면 다시 칸과 요약이 어긋납니다.

수정 후 같은 상태에서:

```
1개 갈래는 읽었지만 판정을 유보했습니다(Attribution) — 정상이라는 뜻이
아니라 아직 판단할 근거가 모자라다는 뜻입니다.
운영 상태 실패 — 실패 1 · 확실하지 않음 1 · 정상 2.
```

화면의 칸도 "확인 못 함"이 아니라 **"판정 유보"** 로 뜹니다.

| 시험 발송 후 | `failing` | 창 안 1건 시도, 0건 성공 — "이 채널만 보는 사람은 지금 아무것도 못 받고 있습니다" |

### 4-3. 라이브 검증 — 재전송 (정책 ④)

```
1) 조회 → 이력 건수 20 → 20  (**조회는 아무것도 보내지 않는다**)
2) 실행(슬랙 죽은 상태) → sent 0 · failed 1 · rounds 0→1
3) 슬랙 복구 후 실행       → sent 1 · failed 0
```

3번에서 수신 스텁이 실제로 받은 본문:

```
⚠️ *[주의] 전달되지 못한 경보: test:notification*
[재전송 2/3] 이 알림은 31분 전에 보내려다 실패한 것입니다 — 새로 생긴 문제가 아닙니다.
```

**같은 `alertKey`(`test:notification`)** 로 갔고, 몇 번째인지와 "새로 생긴
문제가 아니다"가 본문에 있습니다.

### 4-4. 라이브 검증 — 담당자 직접 알림 (정책 ④)

`ALERT_OWNER_CONTACTS`에 **일부러 읽을 수 없는 선언 2개**를 섞었습니다
(`이름만`, `박서버=`).

| 확인 | 결과 |
| --- | --- |
| 읽을 수 없는 선언 | ✅ `rejected: ["이름만", "박서버="]` — 버리되 화면에 적음 |

## 8. 리스크·기술 부채

1. **정책 4601-①②의 조건이 충족되지 않았습니다** — 사람이 줘야 하는 넷이
   그대로이며 **열 Sprint 연속**입니다. 이 하나가 두 정책을 함께 막고
   있습니다 (CTO_REQUEST #80 ④)
2. **Adaptive Card는 실제 Teams에서 확인하지 못했습니다** — 코드와 계획은
   준비됐고 기본값은 바꾸지 않았습니다. 확인은 사람이 눈으로 봐야 합니다
   (#80 ③)
3. **`silent` 채널은 여전히 "모름"입니다** — 주기적 시험 발송을 자동으로
   돌리면 확실해지지만, 그건 알림 채널에 정기적으로 소음을 넣는 일입니다.
   지금은 사람이 누를 때만 확인합니다 (#80 ①)
4. **담당자 연락처는 환경변수 표입니다** — 사람이 바뀌면 배포가 필요합니다.
   DB로 옮기면 화면에서 고칠 수 있지만, 그러면 **누가 언제 바꿨는지**가
   또 하나의 감사 대상이 됩니다 (#80 ②)
5. **재전송은 원본 본문을 복원하지 않습니다** — 이력에 본문을 담지 않는다는
   1401의 규칙을 지켰으므로, 재전송 본문은 "무엇이 언제 어느 채널로
   실패했는지"입니다. 원래 경보의 상세는 화면에서 봐야 합니다
6. **순수 IPv6 상대의 매칭은 여전히 라이브로 확인하지 못했습니다** — 이
   컨테이너에 IPv6 스택이 없습니다(#79 ①에서 이어짐)
7. **`peer`는 바로 앞 상대입니다** · **검토 알림의 등급은 올리지 않습니다**
   (4401에서 이어짐)
8. **저장된 옛 기록의 별표는 그대로입니다** — TASK-4001 수정 전 초안 본문
   10건
9. **Live Verification은 CI에서 돌지 않습니다** · **운영 저장소가 아직
   S3가 아닙니다** · 백업 성능 기준은 개발 규모에서만 검증(1901-④ 대기)
10. **최근 창 표본이 작습니다** — 이 환경의 트래픽이 적어 귀속률 판정이
    대부분 "판정 유보"입니다
11. **`.turbo/cache`가 다시 자랍니다** — 캐시 상한을 권합니다
