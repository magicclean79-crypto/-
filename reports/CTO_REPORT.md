## 3. 변경 사항 (이번 보고 주기)

### TASK-2801 — Enterprise Governance Intelligence Platform

TASK-2701이 **"늘었으면 부른다"**를 만들었습니다. 이번에는 그 부름이
**어느 프로젝트에서, 무엇이 새로 위반됐는지**까지 담게 만들었습니다.

**1. 되살리기 권한은 EDITOR 유지 (결정 2701-①)**

코드는 바꾸지 않았습니다. 대신 **바꾸지 않았다는 사실을 고정**했습니다.

- `PATCH …/contents/:id/status`는 `@RequireRole("EDITOR")`이고, 그 파일에
  `ADMIN`이 **없음**을 소스 검사로 고정했습니다.
- **되살리기를 별도 API로 분리하지도 않았습니다.** `revive`·`restore`·
  `unarchive` 같은 경로가 없음을 함께 고정했습니다 — 분리하면 권한과 감사
  이력이 두 갈래가 되고, 어느 쪽이 진짜인지 나중에 알 수 없습니다.

> ADMIN으로 올리면 콘텐츠를 고치는 사람이 내린 것을 되살릴 수 없습니다.
> 그러면 사람들은 **새 콘텐츠를 만들어 우회**하고, 그 순간 "왜 내렸는지"가
> 끊깁니다 — 결정 2601-①에서 절차를 코드가 막고 있던 것과 같은 형태의 문제입니다.

**2. 마지막 발행 시각 (결정 2701-②)**

`publishedAt`은 **최초** 발행 시각으로 그대로 두고 `lastPublishedAt`을
신설했습니다.

| 값 | 뜻 | 언제 바뀌는가 |
| --- | --- | --- |
| `publishedAt` | 최초 발행 시각 (TASK-0703 승인 ②) | **한 번만** 기록되고 이후 바뀌지 않습니다 |
| `lastPublishedAt` | 지금 나가 있는 본문이 나간 시각 | **발행할 때마다** |

- 판정은 core 순수 함수 **`resolvePublishTimestamps` 하나**에서만 합니다.
  두 곳에서 정하면 한쪽이 최초 시각을 덮어쓰는 순간을 아무도 알아채지
  못합니다. 서비스가 직접 `new Date()`를 넣지 않는다는 사실도 고정했습니다.
- **`null`은 "모르는 것"입니다** — 이 값을 두기 전에 발행된 콘텐츠는 그
  사이에 재발행이 있었는지 알 수 없습니다. 그래서 `isRepublished`는
  `false`가 아니라 **`null`**을 돌려주고, 화면은 "재발행 없음"이 아니라
  **"마지막 발행 시각 미기록"**이라고 말합니다.
- **백필을 `publishedAt` 복사로 하지 않았습니다.** 복사하면 **이미 재발행된
  콘텐츠가 "한 번만 발행"으로 보입니다.** 상태 전이 기록(TASK-0704)에
  `PUBLISHED` 전이가 모두 남아 있으므로, 그중 **가장 늦은 것**을 되살립니다.
  전이 기록이 없는 옛 데이터만 `publishedAt`으로 되돌립니다 — 그때는 그것이
  아는 전부입니다. (라이브에서 실제로 재발행된 행을 되살려냈습니다 — §4)

**3. 프로젝트별 예약 스캔 (결정 2701-③)**

예약 실행이 **프로젝트를 하나씩 훑고, 전체 범위는 그 결과를 합해서** 만듭니다.

```
프로젝트 6개 + 전체 범위 스캔 · 위반 총 11건 · 경보 1건 (프로젝트 콘텐츠 테스트 (…))
```

전체를 따로 한 번 더 훑지 않은 이유는 둘입니다 — 콘텐츠를 두 번 읽는
낭비이고, **읽은 시점이 달라 전체와 프로젝트별 숫자가 어긋날 수 있습니다.**
합으로 만들면 **어긋날 수가 없습니다**(라이브에서 2+9=11 일치 확인).

프로젝트가 하나도 없어도 전체 범위 실행은 남깁니다 — 기록이 없으면 **"돌지
않았다"와 구분되지 않습니다.**

**4. 프로젝트별 Alert와 독립 Cooldown (결정 2701-④)**

범위마다 **비교 기준선과 경보 키가 따로**입니다
(`governance-scan:violations:all` / `…:project:<id>`). 뭉치면 두 가지가 깨집니다:

| 뭉치면 | 무슨 일이 생기는가 |
| --- | --- |
| 기준선을 뭉치면 | 한 프로젝트가 나아지고 다른 프로젝트가 나빠질 때 **총량이 그대로라 아무 경보도 오지 않습니다** |
| 경보 키를 뭉치면 | 프로젝트 A의 스캔이 **B의 경보를 해소해 버립니다** — B의 위반은 그대로인데 화면에서 사라집니다 |

- **재알림 간격은 이미 키 단위**였습니다(`AlertState.notifiedAt`이 키마다
  있습니다). 그 독립성을 회귀 테스트로 고정했습니다.
- **해소 범위를 좁혔습니다.** `reconcileAlerts(…, { resolvableKeys })`를 더해
  **이번에 실제로 판정한 범위만** 해소 대상이 됩니다. 넘기지 않으면 기존
  동작(그 종류 전체)이 그대로입니다.
- 경보 제목에 범위를 적습니다 — 프로젝트별 경보가 여러 건 왔을 때 **제목만
  보고 어디인지** 알 수 있어야 합니다. 이름을 모르면 id를 쓰되, **id를 이름처럼
  보여 주지 않습니다.**

**5. 경보에 증가 수와 새로 위반된 콘텐츠 (결정 2701-⑤)**

`diffViolations`로 지난 실행의 위반 목록과 대조해 **최대 10건**을 제목·id와
함께 담습니다.

```
프로젝트 콘텐츠 테스트 (…) 범위에서 위반이 0건에서 12건으로 12건 늘었습니다.
발행이 막힐 것 12건. 새로 위반된 콘텐츠 12건: 대량 위반 1(content-2801-1) · …
나머지 2건은 문구에 담지 않았습니다 — 스캔 이력에서 보세요.
```

- **증가 수와 새로 위반된 수는 다를 수 있습니다.** 2건이 새로 생기고 1건이
  해소되면 총량은 1건만 늘어납니다. 한 숫자로 뭉치면 **문구가 거짓**이 되므로
  둘을 따로 말합니다.
- 10건이 넘으면 **몇 건을 생략했는지 밝힙니다** — 조용히 자르지 않습니다.
  저장도 표본 10건만 하고 **건수는 전체를 남깁니다**(목록은 잘라도 숫자는
  사실이어야 합니다).
- **`newlyCount`의 `null`은 "가릴 수 없었다"**입니다(첫 스캔이거나, 위반
  목록을 남기기 전의 실행과 비교하는 경우). **0("새로 생긴 것이 없다")과
  다릅니다** — 섞으면 목록을 두기 전의 위반이 **전부 "새로 생겼다"로 보고**되고,
  마이그레이션 직후 첫 실행이 있지도 않은 급증을 알립니다.
- **늘지 않은 실행에도 구성 변화를 이력에 남깁니다**(총량이 같아도 한 건이
  해소되고 다른 한 건이 생길 수 있습니다). **경보는 여전히 늘었을 때만**
  나갑니다(결정 2601-③) — 이력에 적는 것은 부르는 것이 아닙니다.

| **③ 총량 그대로, 한 프로젝트만 악화** | 한 프로젝트 2→1(해소), 다른 프로젝트 0→1(악화) → 전체 `unchanged`(**경보 없음**)인데 **악화된 프로젝트만 경보** — TASK-2701 설계로는 **아무 경보도 오지 않았을 상황** |
| **경보 문구** | `위반이 0건에서 1건으로 1건 늘었습니다 … 새로 위반된 콘텐츠 1건: 신규 매트 상세(content-2801a)` · 제목에 범위 |
| **구성 변화 기록** | 전체 범위는 조용했지만 실행 기록에 `newlyCount 1 · resolvedCount 1` |
| **④ 독립 해소** | 그 위반을 고치자 **해당 키만 RESOLVED** · 전체 범위의 기존 CRITICAL은 **ACTIVE 유지**(위반 10건이 남아 있으므로) — 거짓 해소 없음 |
| **⑤ 표본 상한** | 12건 동시 위반 → `newlyCount 12` · 저장 표본 10건 · 문구에 **"나머지 2건은 문구에 담지 않았습니다"** |
| **⑥ 재발행 시각** | 발행 `04:32:36.618` → 보관·되살림·검토 → 재발행: `publishedAt` **04:32:36.618 유지** · `lastPublishedAt` **04:32:38.727 갱신** |
| **⑦ EDITOR 권한** | 실제 `EDITOR` 계정을 만들어 로그인 → **보관→되살림→검토→재발행 전 과정 200** (ADMIN 불필요) |

화면: 예약 스캔 이력 스크린샷 첨부 — **기준선(신규 판별 불가)** ·
**변화 없음(조용)** · **늘었음(신규 위반 1건·12건)** · **해소**가 한 화면에
있습니다.

**이번 주기에는 자체 발견 결함이 없습니다.** 대신 **결함이 생길 수 있었던
지점 셋**을 설계에서 막았습니다(위 스텁 3건과 백필 방식) — 특히
`newlyCount`를 `NOT NULL DEFAULT 0`으로 두었다면 **마이그레이션 직후 첫
실행이 기존 위반 전부를 "새로 생겼다"로 알렸을 것**입니다.

## 5. 아키텍처 변경 및 현황

**이번 주기 변경 — 범위와 대조**:

```
governance-scan (매일 03:50 로컬)
   └─ GovernanceScanService.runScheduled(trigger)
        ├─ project.findMany()                    ← 프로젝트 목록
        ├─ for each project:
        │    preflight.items(projectId)  →  judgeScope("project:<id>")
        ├─ judgeScope("all", 위 결과를 **합한 것**)   ← 다시 훑지 않는다
        └─ { detected, resolvableKeys }
             │
             └─ alerts.sync(["governance-scan"], detected, { resolvableKeys })
                     ↑ 이번에 판정한 범위만 해소 대상

judgeScope(scope, items):
   summarizePreflight(items)          → 총계 (blocked + publishedViolations)
   compareScan(previous, current)     → baseline / increased / decreased / unchanged / resolved
   diffViolations(previousIds, now)   → newly / resolvedCount / comparable
   detectGovernanceScanAlert(…)       → **increased일 때만** 경보 (증가 수 + 신규 목록)
   shouldSyncScanAlerts(…)            → increased·resolved일 때만 저장소를 건드린다

PUBLISHED ──▶ ARCHIVED ──▶ DRAFT ──▶ REVIEW ──▶ PUBLISHED
              (내림)      (되살림)   (검토)      publishedAt 유지 · lastPublishedAt 갱신
                            └─ 권한은 EDITOR 이상 (별도 경로 없음)
```

① **총량은 나빠진 곳을 숨깁니다.** 한 프로젝트가 나아지고 다른 프로젝트가
   나빠지면 합은 그대로입니다 — 범위를 나누는 것은 편의가 아니라 **감지
   능력의 문제**입니다.
② **전체는 합으로 만듭니다.** 같은 사실을 두 번 재면 두 답이 생기고, 그러면
   어느 쪽도 신뢰할 수 없습니다(결정 2301-①과 같은 결).
③ **한 종류 안에도 독립적인 경보가 있습니다.** 해소 판정을 kind 단위로만
   좁히면 프로젝트 A의 스캔이 B의 경보를 지웁니다 — 축이 하나 더 필요합니다.
④ **모르는 것은 0이 아닙니다.** `newlyCount`의 `null`이 그 구분이고, 이것을
   섞으면 없던 급증이 보고됩니다.
⑤ **숫자는 사실이어야 하고 목록은 잘라도 됩니다.** 표본 10건을 남기되 건수는
   전체를 남기는 이유입니다.
⑥ **최초는 덮어쓰지 않고, 모르면 모른다고 합니다.** 두 시각의 역할이 겹치지
   않으므로 한 값이 다른 값을 대신하지 않습니다.

## 6. 데이터 모델

**이번 주기 마이그레이션 1건** — `20260806000000_governance_intelligence`.

**`contents`**:

| 컬럼 | 뜻 |
| --- | --- |
| `lastPublishedAt` (nullable) | 마지막 발행 시각 — **발행할 때마다** 갱신. `publishedAt`이 있는데 이 값이 없으면 **모르는 것**입니다 |

백필은 **감사 이력(`content_status_history`)에서 마지막 `PUBLISHED` 전이**를
읽습니다. `publishedAt` 복사로 채우면 **이미 재발행된 콘텐츠가 "한 번만
발행"으로 보입니다** — 라이브 DB에 실제로 그런 행이 있었고, 이력 기반 백필이
그 시각을 되살려냈습니다.

**`governance_scan_runs`** (4컬럼 추가, 전부 nullable):

| 컬럼 | 뜻 |
| --- | --- |
| `violatingIds` (JSONB) | 그때 위반이던 콘텐츠 id — **다음 실행이 "새로 위반된 것"을 가리는 근거** |
| `newly` (JSONB) | 새로 위반된 콘텐츠 **표본**(최대 10건, 제목 포함) |
| `newlyCount` | 새로 위반된 **전체 수** |
| `resolvedCount` | 지난 실행에는 있었으나 사라진 위반 수 |

**전부 nullable인 것이 설계입니다.** `NULL`은 **"그 실행은 목록을 남기지
않았다"**(TASK-2701 이전)이고, `0`·빈 배열("위반이 없었다")과 **다릅니다.**
`NOT NULL DEFAULT 0`으로 두면 마이그레이션 직후 첫 실행이 기존 위반 전부를
**"새로 생겼다"로 알립니다.**

**Major Migration으로 지정하지 않았습니다.** nullable 컬럼 추가와 새 컬럼
백필뿐이고, 기존 컬럼의 의미·형식을 바꾸지 않으며 재해 복구 절차도 바꾸지
않습니다(결정 1901-① 기준).

## 7. API 표면

**새 엔드포인트 없음.** 이번 변경은 **기존 응답에 사실을 더한 것**입니다.

**기존 계약 확장**:

- `ContentDto`에 **`lastPublishedAt`** 추가 (`publishedAt`의 의미는 그대로
  **최초 발행**)
- `GovernanceScanRunDto`에 **`newlyCount`**(`number | null`) ·
  **`newly`**(최대 10건) · **`resolvedCount`**(`number | null`) 추가
- `POST /ops/checks/run?job=governance-scan` — 이제 **프로젝트마다 + 전체
  범위**로 실행하고, `detail`이 범위 수와 경보가 난 범위를 말합니다
- 경보 `key` 규칙은 그대로(`governance-scan:violations:<scope>`)이고,
  **예약 실행이 프로젝트 범위 키를 만들기 시작**합니다 — 외부 모니터링이
  이 종류를 키 단위로 세고 있다면 건수가 늘어날 수 있습니다

**내부 계약(호출부 영향)**:

- `AlertService.sync(kinds, detected, { resolvableKeys? })` — 세 번째 인자는
  선택이고, 넘기지 않으면 **기존 동작 그대로**입니다
- core `reconcileAlerts(…, { resolvableKeys? })` — 같음

## 8. 리스크·기술 부채

1. **2801 해석 미확인** — 전체 범위의 의미·스캔 비용·표본 상한
   (CTO_REQUEST #61)
2. **경보 건수가 프로젝트 수에 비례합니다** — 결정 2701-④의 의도된 결과지만,
   여러 프로젝트가 동시에 나빠지면 **전체 + 프로젝트별로 여러 건**이 나갑니다.
   전체 범위 경보를 남겨 둔 것은 "어디인지"와 "얼마나 큰가"가 다른 질문이기
   때문입니다(#61 ①)
3. **전량 판정 비용이 프로젝트 수만큼의 질의로 늘었습니다** — 콘텐츠는 한 번씩
   읽지만 프로젝트마다 별도 질의입니다. 실측(6 프로젝트·32건)은 156ms이고,
   프로젝트가 수백 개가 되면 재볼 필요가 있습니다(#61 ②)
4. **표본 10건은 고정값입니다** — 환경변수로 열지 않았습니다(열면 "일단
   늘려 두는" 우회가 생기고 경보가 목록이 됩니다). 건수는 항상 전체를
   말하므로 잘린 사실은 감춰지지 않습니다(#61 ③)
5. **`lastPublishedAt`이 `null`인 옛 데이터가 남을 수 있습니다** — 전이 기록이
   없는 콘텐츠는 백필할 근거가 없습니다. 화면이 "미기록"이라고 말하므로
   거짓을 보여 주지는 않습니다
6. **재발행 **횟수**는 세지 않습니다** — 감사 이력에서 셀 수 있으므로 값을
   따로 두지 않았습니다
7. **보관된 판정 기록은 목록 UI가 없습니다** — API로만 볼 수 있습니다
8. **운영 저장소가 아직 S3가 아닙니다** — 전환은 운영 담당자 몫(결정 2101-④)
9. **백업 성능 기준은 여전히 개발 규모에서만 검증됐습니다**(결정 1901-④ 대기)
10. **실 Provider 스모크는 여전히 미검증** — 샌드박스 차단 + 과금
11. **GitHub Actions 실제 실행은 확인하지 못했습니다** — 워크플로 순서는
    테스트로 고정했습니다
