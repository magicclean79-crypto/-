## 3. 변경 사항 (이번 보고 주기)

### TASK-3101 — Enterprise AI Cost Intelligence Platform

> 단가는 **돈의 기준**입니다. 지금까지는 코드 상수였고, 그래서 ⓐ 누가 왜 바꿨는지
> 남지 않고 ⓑ 예산·리포트의 숫자가 **어느 시점부터** 달라졌는지 아무도 설명할 수
> 없었습니다. 이번 TASK는 그 기준에 **절차와 시점**을 붙였습니다.

**1. 가격표는 검토 → 승인 → 적용 절차를 거칩니다 (정책 3101-①)**

단계 전이 판정은 core 순수 함수(`judgePricingTransition`)가 하고, 어댑터는
**누가 언제 했는지**만 기록합니다.

| 규칙 | 왜 그렇게 했는가 |
| --- | --- |
| 검토 없이 승인·승인 없이 적용 **불가** | 한 사람의 오타가 예산 전체를 흔든다 |
| **적용·반려는 끝** (되돌릴 수 없음) | 끝난 것을 되살리면 "무엇이 언제 적용됐는가"의 이력이 흐려진다 — 되돌리려면 **새 제안**을 낸다 |
| 사유 **필수** (제안·반려 모두) | 사유가 없으면 이력이 있어도 판단을 복원할 수 없고, 제안자는 무엇을 고칠지 모른다 |
| **0은 허용, 음수는 거부** | 무료 모델·엔진은 실제로 있다. 음수 단가는 지출을 줄여 **예산 상한을 무력화**한다 |
| **적용만** 계산을 바꾼다 | 승인은 "적용해도 된다"는 뜻이다. 적용 시각이 있어야 "언제부터 이 단가로 계산됐나"에 답할 수 있다 |
| 제안자 = 승인자면 **경고만** | 절차가 막히면 사람은 코드를 고쳐 우회하고 이력이 아예 없어진다 (결정 2601-① 교훈) — 대신 **사실을 남긴다** |

적용된 단가는 **LLM Execution 기록과 OCR 비용 기록 양쪽**에 쓰입니다.
`ExecutionTracker`가 가격표를 **함수로** 받게 바꿨고(`LlmPricingSource`),
`PrismaOcrRunStore`도 같은 출처를 씁니다 — 경로마다 가격표를 따로 읽으면 어느
한쪽이 조용히 낡고, 그때부터 같은 호출의 비용이 화면마다 다르게 보입니다.

**조회가 실패하면 기준 가격표로 계산합니다.** 비용을 `null`로 남기면 그 호출은
예산 계산에서 빠지고 상한이 무력해집니다 — 조회 실패보다 그것이 위험합니다.

**2. 비용 기록은 수정하지 않습니다 (정책 3101-②, Append Only)**

단가가 바뀌어도 이미 기록된 `Execution.cost`·`OcrResult.cost`는 **그대로**입니다.
대신 비용 검증이 **그 시점에 유효했던 단가**로 대조합니다(`resolvePricingAt`).

> 새 단가로 과거를 대조하면 단가를 한 번 바꿀 때마다 **과거 전체가 "불일치"로
> 보고**되고, 그런 경보는 곧 무시됩니다. **무시되는 경보는 없는 경보보다
> 나쁩니다** — 있다고 착각하기 때문입니다.

경계를 **테스트로 못질**했습니다(`pricing/append-only.spec.ts`): 비용 컬럼을
갱신하는 코드가 생기면 테스트가 깨집니다. 적용 이력은 표본마다 조회하지 않고
**한 번만 읽어** 시점별 해석 함수를 만듭니다(1,000건 검증이 1,000번 질의가 되지
않도록).

**3. Forecast는 참고자료입니다 (정책 3101-③)**

- 방식은 **하루 평균 × 이번 달 일수**(UTC — 예산 창과 같은 경계). 정교한 모델을
  쓰지 않은 이유는 표본이 며칠뿐인 구간에서 정교한 모델이 **더 그럴듯하게
  틀리기** 때문입니다.
- 관측 **3일 미만이면 숫자를 만들지 않습니다.** 최소 일수는 **고정값**입니다 —
  환경변수로 열면 "일단 1일로 낮추는" 우회가 생기고, 하루 관측으로 만든 숫자가
  화면에서 예측처럼 보입니다.
- **차단하지 않습니다.** 예산 관문이 예측 모듈을 **모른다**는 사실을 소스 검사로
  고정했습니다. 예측으로 막으면 **아직 쓰지 않은 돈 때문에 서비스가 멈추고**,
  "왜 막혔나"에 답할 수도 없습니다.
- 비용이 빠진 호출이 있으면 **추정도 실제보다 작을 수 있다**고 함께 말합니다 —
  미산정을 숨기면 "예산 안에 들어온다"는 낙관이 사실처럼 읽힙니다.

**4. Billing Report는 운영 지표입니다 (정책 3101-④)**

응답과 화면에 **항상** 면책 문구가 붙고, 실제 청구와 다를 수 있는 이유를
**함께** 적습니다.

| 이유 | 우리 총액의 방향 |
| --- | --- |
| 미산정 (가격표에 없는 모델·엔진) | **작다** |
| 실패한 호출 (과금될 수 있는데 적지 않는다) | **작다** |
| 무료 구간 (반영하지 않는다 — TASK-3001) | **크다** |
| 환율·세금·단가 변동 | 청구서에는 있고 우리에게는 없다 |

> 이유를 적지 않으면 "우리 숫자가 틀렸다"로 읽히고, 그러면 리포트를 신뢰하지
> 않습니다. 반대로 숫자만 있으면 누군가 그것을 **청구서로 다루고**, 회계와
> 어긋나는 순간 리포트 전체가 신뢰를 잃습니다.

정렬은 **비용 큰 것부터**입니다(리포트를 여는 이유는 대개 "무엇이 돈을
쓰는가"입니다). 총액이 0이면 비중을 `null`로 둡니다 — 0%로 적으면 "안 썼다"로
읽힙니다.

**5. 자체 발견 결함 — 실효 가격표에서 LLM 단가의 출처가 비어 있었습니다**

> 라이브 스크린샷을 보니 OCR 줄에는 "승인된 제안으로 적용됨 (시각)"이 있는데
> **LLM 줄은 `—`**였습니다. 승인된 단가와 코드 기본값이 구분되지 않으면
> **"이 금액은 누가 정했나"에 답할 수 없습니다** — 이 TASK가 존재하는 이유가
> 바로 그 질문입니다.

OCR은 단가 자체가 출처를 들고 있었고(`note`) LLM은 없었습니다. 적용 이력에서
출처를 만들어 **양쪽을 같은 모양**으로 맞췄습니다("승인된 제안으로 적용됨 (시각)"
/ "코드 기본값 — 승인 이력이 없습니다").

## 5. 아키텍처 변경 및 현황

```
가격표 (절차)
   POST /ops/pricing                 → DRAFT   (현재 단가 스냅샷 · 사유 필수)
   POST /ops/pricing/:id/review      → REVIEWED
   POST /ops/pricing/:id/approve     → APPROVED (자기 승인이면 경고 기록)
   POST /ops/pricing/:id/apply       → APPLIED  ← 여기서부터 계산이 바뀐다
   POST /ops/pricing/:id/reject      → REJECTED (사유 필수)
        판정: judgePricingTransition (core 순수) · 끝난 것은 전이 없음

단가의 단일 출처
   PricingService.effective()  ─┬─▶ ExecutionTracker (LLM 비용)
   (적용 이력 + 기준 가격표)     └─▶ PrismaOcrRunStore (OCR 비용)
        조회 실패 → 기준 가격표 (비용을 null로 남기지 않는다)

검증 (Append Only)
   /llm/cost-verification ─▶ PricingService.resolvers()
        표본의 createdAt → resolvePricingAt(그 시점 단가) → 대조
        과거 기록은 다시 계산하지 않는다

판단 재료 (아무것도 막지 않는다)
   /ops/cost-forecast ─▶ forecastMonthlySpend   (3일 미만이면 숫자 없음)
   /ops/billing       ─▶ buildBillingReport     (면책 문구 항상)
        ↕ 완전히 분리
   차단: LlmBudgetService.assertWithinBudget ─▶ 실제 원장 두 개만
```

① **단가에는 절차가, 기록에는 시점이 있습니다.** 절차 없는 단가는 "누가 정했나"에
   답할 수 없고, 시점 없는 기록은 "그때 맞았나"에 답할 수 없습니다.
② **적용과 승인을 나눴습니다.** 합치면 "언제부터 이 단가로 계산됐나"를 잃습니다.
③ **막는 것과 보여 주는 것을 코드 수준에서 갈랐습니다.** 예산 관문은 예측
   모듈을 아예 모릅니다 — 의도가 아니라 **구조**로 지켰습니다.
④ **모르는 것을 유리하게 쓰지 않습니다.** 표본이 적으면 예측하지 않고, 미산정이
   있으면 총액이 작다고 말합니다.
⑤ **절차는 막지 않고 기록합니다.** 자기 승인을 차단하면 사람은 코드를 고쳐
   우회하고, 그러면 이력이 아예 없어집니다(결정 2601-①에서 배운 형태).

**유지되는 핵심 결정**: Alert 정책 4종(1302-①) · 보관 90일·삭제 금지
(1302-④·1501-③·2501-⑤) · Live Check 기본 꺼짐(1301-①) · 예산 초과는 Failover
대상 아님(1002) · 백업 1시간 간격(1701-①) · 자동 복구 없음(2201-②) · 우회

## 7. API 표면

**새 엔드포인트 6개** (모두 **ADMIN 전용**):

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| `GET` | `/ops/pricing` | 제안 목록(진행 중/끝난 것) + **실효 가격표**(줄마다 출처) |
| `POST` | `/ops/pricing` | 단가 변경 제안 (사유 필수 · 201) |
| `POST` | `/ops/pricing/:id/review` | 검토 완료 |
| `POST` | `/ops/pricing/:id/approve` | 승인 (자기 승인이면 `selfApproval` 경고) |
| `POST` | `/ops/pricing/:id/apply` | **적용** — 이후 호출에 이 단가가 쓰인다 |
| `POST` | `/ops/pricing/:id/reject` | 반려 (사유 필수) |

경로 이름(`approve`)과 저장 값(`APPROVED`)을 따로 둔 이유: URL은 **행동**이고
저장되는 것은 **상태**입니다. 같게 두면 상태 이름을 바꿀 때 외부 호출이 함께
깨집니다.

**새 조회 2개** (ADMIN 전용):

- `GET /ops/cost-forecast` — 월말 예측. **참고자료**이며 `projectedExceeds`는
  표시용입니다. 표본이 3일 미만이면 숫자가 전부 `null`입니다.
- `GET /ops/billing?from=&to=` — 운영 비용 리포트. 기본 이번 달(UTC), 최대
  366일. **`disclaimer`가 항상 담깁니다.**

**기존 계약 확장**:

- `GET /llm/cost-verification` — `pricing`·`ocrPricing`이 **지금 실제로 쓰는
  단가**(적용 반영)를 돌려줍니다. 대조는 **표본 시점의 단가**로 합니다 — 단가를
  바꾼 뒤에도 과거가 불일치로 뜨지 않습니다.
- `POST /images/:id/ocr` · `POST /llm/complete` — 응답 형태는 그대로이고,
  기록되는 `cost`가 **적용된 가격표**를 따릅니다.

**내부 계약**: `ExecutionTracker`의 `pricing` 옵션이 표 또는 **함수**를 받습니다
(`LlmPricingSource`) · `verifyCosts`/`verifyOcrCosts`가 표 또는 **시점 해석
함수**를 받습니다 · `LlmBudgetService.limits()` 신설(예측이 월 예산을 읽습니다 —
**차단에는 쓰이지 않습니다**).

## 8. 리스크·기술 부채

1. **3101 해석 미확인** — 단가 갱신 책임·교차 확인 강도·적용 시점·예측 경보
   (CTO_REQUEST #64)
2. **단가 갱신을 촉발하는 장치가 없습니다** — 절차는 만들었지만 **누가 언제
   공지를 확인해 제안을 내는지**는 정해지지 않았습니다. Provider가 단가를 바꾸면
   비용 검증이 `mismatch`로 드러내지만, 그것을 **읽는 사람**이 절차에 없습니다
   (#64 ①)
3. **실효 가격표에 30초 캐시가 있습니다** — 다중 인스턴스에서 적용 직후 최대
   30초는 인스턴스마다 다른 단가로 계산할 수 있습니다. 적용한 인스턴스는 즉시
   반영합니다. 영구 캐시를 두지 않은 이유는 §3-1에 있습니다
4. **적용 시점을 미래로 지정할 수 없습니다** — Provider 공지가 "8월 1일부터"인
   경우 그날 사람이 눌러야 합니다(#64 ③)
5. **통화는 USD 하나입니다** — 환율·세금은 리포트에 없고, 면책 문구가 그 사실을
   밝힙니다
6. **예측은 하루 평균 × 일수뿐입니다** — 추세·요일 효과를 보지 않습니다.
   참고자료로 단순함을 택했지만, 월초 급증/급감 구간에서는 크게 틀립니다
7. **실패한 OCR·LLM 호출의 과금은 여전히 모릅니다** — 실제 청구가 우리 집계보다
   클 수 있습니다(TASK-3001에서 이어지는 부채)
8. **무료 구간 미반영으로 예상 비용이 실제보다 큽니다** — 보수적인 쪽으로
   틀린 것이지만 소규모 환경에서는 예산이 빨리 찹니다(#63 ②에서 이어짐)
9. **실 Google Cloud Vision·실 LLM 호출은 미검증** — 실 키와 외부 네트워크가
   필요합니다
10. **운영 저장소가 아직 S3가 아닙니다**(결정 2101-④) · **백업 성능 기준은 개발
    규모에서만 검증**(1901-④ 대기) · **GitHub Actions 실제 실행 미확인**
11. **디스크 할당량이 빠듯합니다** — 검증 중 여유가 1GB 수준이어서 빌드 캐시
    정리가 반복 작업이 되고 있습니다
