## 1. 프로젝트의 최종 목표

### 무엇을 만들고 있는가

**AI Product Content OS** — 쇼핑몰 운영자가 **상품 사진 몇 장만 올리면
판매용 상세페이지가 만들어지는 시스템**입니다.

지금 쇼핑몰 사장님이 상품 하나를 올리려면 이런 일을 해야 합니다.

- 제품 사진을 여러 각도로 찍는다
- 포장지의 재질·규격·주의사항을 옮겨 적는다
- 사진 보정과 배경 합성을 맡기거나 직접 한다
- 카피를 쓴다
- 상세페이지로 조립한다

**며칠이 걸리고, 외주를 주면 수십만 원이 나갑니다.** 그리고 상품이 100개면
그 일을 100번 합니다.

이 시스템은 그 과정을 **사진 업로드 → 확인 → 발행**으로 줄이는 것을
목표로 합니다.

### 완성되면 무엇을 할 수 있는가

```
상품 사진 여러 장 업로드
      ↓
글자를 읽어 실제 제품 정보를 뽑아낸다        (OCR)
      ↓
사진을 보고 제품을 이해한다                  (Vision + GPT)
      ↓
사람이 확인하고 고친다                       ★ 사람의 자리
      ↓
마케팅용 사진을 만든다                       (Gemini)
      ↓
사람이 마음에 드는 사진을 고른다             ★ 사람의 자리
      ↓
상세페이지를 만든다                          (Claude, Sprint 2)
      ↓
사람이 최종 승인하고 발행한다                ★ 사람의 자리
```

**AI가 전부 하는 것이 아닙니다.** 사람이 판단해야 하는 자리가 세 군데
명확히 있고, 그 자리를 없애지 않는 것이 이 시스템의 설계입니다.

## 2. 개발 철학

이 프로젝트에서 무엇이 더 중요한지 다툼이 생기면, 아래 순서로 판단합니다.

### 철학 1 — 제품 동일성이 이미지 품질보다 항상 우선한다

AI가 만든 사진이 아무리 멋져도 **그게 우리 제품이 아니면 쓸 수 없습니다.**
쇼핑몰에서 사진과 다른 물건이 오면 그건 반품이고 분쟁입니다.

Gemini의 역할은 **새 제품을 디자인하는 것이 아니라, 실제 제품을 다양한
상황에서 보기 좋게 표현하는 것**입니다.

> 연출과 동일성이 부딪히면 **연출을 포기합니다.**

### 철학 2 — 추측하지 않는다. 확인한 사실만 사용한다

모르는 것은 **"모른다"고 적습니다.** 빈칸을 그럴듯한 값으로 채우지
않습니다.

이번 세션에서 실제로 있었던 일입니다. OCR을 돌리지 않은 상태에서 GPT가
사진만 보고 제품명을 지어냈습니다.

| | 포장지에 적힌 사실 | AI가 추측한 값 |
| --- | --- | --- |
| 제품명 | 베란다용 스텐 호스 세트 3M | "물 분사용 스프레이 건 세트" |
| 브랜드 | 삼정크린마스터(주) | 없음 |
| 재질 | ABS, PVC, 스테인리스 | "플라스틱, 금속" |

**그럴듯해 보이지만 전부 틀렸습니다.** 그리고 그 틀린 정보가 Gemini에게
넘어가 다른 제품이 그려졌습니다. 추측은 이렇게 전파됩니다.

### 철학 3 — 사람이 최종 판단한다. AI는 보조다

**생성 결과의 품질은 AI가 판단하지 않습니다.**

Claude는 "확인했습니다" · "정상입니다" · "품질이 좋습니다" 라고 말하지
않습니다. 브라우저에서 사람이 직접 볼 수 있는 상태까지만 준비하고 멈춥니다.

이유는 단순합니다. **AI가 만든 것을 AI가 검사하면 그건 검증이 아닙니다.**

### 철학 4 — 사실과 평가를 구분해서 보고한다

Claude가 보고해도 되는 것과 안 되는 것이 다릅니다.

| 보고해도 되는 것 (사실) | 보고하면 안 되는 것 (평가) |
| --- | --- |
| 생성 13장, 실패 0장 | "품질이 좋습니다" |
| 프롬프트에 이 문장이 들어갔다 | "의도대로 적용됐습니다" |
| OCR이 987자를 읽었다 | "정확하게 읽었습니다" |
| 이 필드는 비어 있다 | "문제없습니다" |

### 철학 5 — 하지 않기로 한 것은 흔적을 남긴다

없앤 기능, 넣지 않기로 한 우회 경로는 **"없다"는 사실 자체를 테스트로
고정**합니다. 코드에서 사라진 것은 흔적이 없어서, 나중에 누군가 "안전을
위해" 되살려도 아무도 모르기 때문입니다.

## 3. AI 역할 분담

세 AI가 각각 **가장 잘하는 일**만 맡습니다.

### GPT — 제품을 이해한다

- 사진과 OCR 텍스트를 함께 읽고 제품 정보를 구조화합니다
- 결과물: **Product Profile** (제품명·브랜드·재질·규격·구성품·특징)

**왜 GPT인가**: 글과 이미지를 함께 놓고 **모순을 가려내는 일**에 강합니다.
OCR이 잘못 읽은 글자와 사진에 보이는 실물이 어긋날 때 판단해야 합니다.

### Gemini — 제품을 표현한다

- 실제 제품 사진을 받아 마케팅용 이미지를 만듭니다
- 결과물: 대표 썸네일 · 사용 장면 · 디테일 · 특징 강조 이미지

**왜 Gemini인가**: 이미지를 입력으로 받아 **편집·합성·재구성**하는 데
강합니다. 중요한 건 **처음부터 그리는 것이 아니라 주어진 제품을 유지한 채
바꾼다**는 점입니다.

### Claude — 시스템을 만들고 글을 쓴다

- 프로그램 개발, 문서 작성
- Sprint 2부터: 상세페이지 카피와 구조 생성

**왜 Claude인가**: 코드와 긴 글의 일관성 유지에 강합니다. 다만 **자기가 만든
결과를 스스로 승인하지 않습니다**(철학 3).

### 왜 이렇게 나누었는가

한 AI에게 다 시키면 **어디서 틀렸는지 알 수 없습니다.** 나눠 놓으면
"제품 정보가 틀린 것"과 "이미지가 이상한 것"을 구분해 고칠 수 있습니다.

이번 세션이 그 사례입니다. 이미지가 다른 제품으로 나온 원인이 **Gemini가
아니라 그 앞 단계(OCR 미실행 → Product Package 부실)** 였습니다. 단계가
나뉘어 있어서 찾을 수 있었습니다.

## 4. 현재 개발 방식

### 왜 Sprint 단위인가

한 번에 다 만들면 **무엇 때문에 좋아졌는지 나빠졌는지 알 수 없습니다.**

```
Sprint 1   제품 인식 엔진 (Product Recognition Engine)
Sprint 2   Claude → 상세페이지 생성 → 품질 개선
```

**Sprint 1은 GPT→Gemini 연결이 아닙니다** (2026-08-09 재정의). **제품 인식
엔진을 완성하는 것**입니다.

```
① 사진 분석   ② OCR   ③ Vision   ④ 이미지 자동 분류   ⑤ 바코드 인식
⑥ 모델명 추출   ⑦ 필요 시 공식 웹 조사   ⑧ 교차 검증
⑨ Product Profile 생성   ⑩ Product Package 생성
```

> **이번 Sprint는 Gemini 품질을 높이는 Sprint가 아니라,
> Gemini가 추측하지 않아도 되는 수준의 Product Package를 만드는
> Sprint입니다.**

**완료 조건**: Gemini가 실제 제품과 동일한 제품을 생성할 수 있을 정도로
제품 인식 엔진이 완성되는 것.

### 정보 출처 우선순위 (절대 순서)

```
실제 제품 사진  >  OCR  >  Vision  >  바코드  >  모델명
                >  공식 제조사 홈페이지  >  공식 카탈로그  >  기타 검색
```

- **쇼핑몰 정보는 공식 정보로 취급하지 않습니다.** (다나와·G마켓·11번가·
  이마트·GS SHOP 등 — 판매처 표기는 제조사 표기가 아니며, 규격이 다른
  제품 정보가 섞여 있는 경우가 실제로 있었습니다)
- **검색 결과보다 실제 제품 사진을 우선합니다.**
- 웹 조사는 **항상 하지 않습니다.** OCR·Vision·바코드·모델명만으로 충분하면
  **생략합니다.**
- 웹 조사를 하더라도 **공식 정보만** 씁니다.

**Sprint 1이 끝나기 전에는 Claude 기능(Sprint 2)을 추가하지 않습니다.**
앞 단계가 부실한 채로 다음을 쌓으면, 나중에 어느 층이 문제인지 못 찾습니다.

### 왜 Benchmark를 쓰는가

**같은 제품으로 반복 측정해야 변화를 비교할 수 있습니다.**

제품을 바꾸면 결과가 좋아졌을 때 **개선 덕분인지 제품이 쉬워서인지 구분할
수 없습니다.** 그건 측정이 아닙니다.

### 왜 사람이 마지막에 검증하는가

AI 생성물의 품질은 **기계가 판정할 수 없는 영역**입니다.

- "이게 우리 제품이 맞나?" — 실물을 아는 사람만 압니다
- "이 사진을 쇼핑몰에 올려도 되나?" — 파는 사람이 책임집니다
- "글자가 이상하게 박혔나?" — 눈으로 봐야 압니다

테스트가 통과했다는 것은 **배선이 맞다**는 뜻이지 **결과가 좋다**는 뜻이
아닙니다.

## 5. 현재 세션에서 확립된 운영 원칙

아래는 전부 **실제로 사고가 나서 만들어진 규칙**입니다.

### 원칙 1 — 환경을 먼저 확인한다. 추측하지 않는다

**있었던 일**: 3000·4000번 포트를 로컬 서버로 착각하고 작업하다가, 실제로는
**SSH 터널로 AWS EC2에 연결된 것**임을 뒤늦게 확인했습니다. 그 사이 "원격을
건드리지 않았다"는 보고가 부정확했습니다.

**규칙**: 작업 전 `docs/DEVELOPMENT_ENVIRONMENT.md`를 읽습니다. 환경이
바뀌면 **문서를 먼저 고치고 코드를 나중에 고칩니다.**

### 원칙 2 — 실행 전에 승인을 받는다. 요금을 밝힌다

돈이 나가는 호출(GPT·Gemini·Vision)은 **실행 전에 알리고 승인**을 받습니다.

모든 작업에 **"이건 요금이 없습니다" / "이건 요금이 발생합니다"** 를
명시합니다.

### 원칙 3 — 예/아니오 질문은 결과를 풀어서 설명한다

"진행할까요?" 만 묻지 않습니다. **"예를 선택하면 무엇이 일어나고, 아니오면
무엇이 남는지"** 를 한글로 적습니다.

### 원칙 4 — 사람의 환경을 임의로 끄지 않는다

로컬 서버를 재시작해야 하면 **먼저 묻습니다.** 끄기 전에 복구 방법을
기록하고, 끝나면 **원래 상태로 되돌립니다.**

**SSH 터널은 어떤 경우에도 종료하지 않습니다.**

### 원칙 5 — 원본을 건드릴 때는 백업하고 즉시 복구한다

`benchmark/constants.ts` 같은 기준 파일은 **사람 승인 없이 바꾸지
않습니다.** 확인을 위해 잠시 바꿔야 하면 백업 → 확인 → 즉시 복구합니다.

### 원칙 6 — 브라우저에서 사람이 직접 확인한다

이미지 생성이 끝나면:

1. 브라우저에서 볼 수 있는 상태까지 준비한다
2. 주소와 확인 방법을 안내한다
3. **"여기까지 준비되었습니다. 브라우저에서 직접 확인해 주세요."** 라고
   보고하고 **멈춘다**

### 원칙 7 — 실패를 감추지 않는다

테스트가 실패하면 **실패했다고 첫 문단에 씁니다.** 원래부터 실패하던
것인지 내가 깨뜨린 것인지 **직접 확인해서 근거와 함께** 보고합니다.

### 원칙 8 — 한글로, 코드를 들이밀지 않고 설명한다

사용자에게는 **한글**로, 코드·명령어를 그대로 붙여넣지 않고 **무엇을 왜
하는지**를 설명합니다.

## 6. Benchmark 철학

### 공식 Benchmark — 베란다 호스

**정식 명칭**: 베란다용 스텐 호스 세트 3M (삼정크린마스터(주))

### 왜 이 제품인가

이 제품 하나에 **테스트에 필요한 요소가 다 들어 있습니다.**

| 요소 | 베란다 호스에서 |
| --- | --- |
| 복잡한 형태 | 분사기 손잡이·나팔·트리거·나사선 |
| 여러 재질 | 플라스틱(검정) · 스테인리스(은색) · 고무(파랑) · 황동 |
| 구성품 여러 개 | 분사기 + 호스 3M + 고무패킹 2개 |
| **글자가 많은 포장지** | 제품명·재질·규격·사용법·주의사항·바코드·연락처 |
| 사용 장면이 명확 | 베란다·정원에서 물을 뿌린다 |

특히 **포장지의 글자**가 중요합니다. OCR이 제 역할을 하는지, 그리고 그
글자가 **생성 이미지에 잘못 박히지 않는지**를 동시에 시험할 수 있습니다.

### 왜 항상 같은 제품으로 테스트하는가

**변화를 비교하기 위해서입니다.**

```
프롬프트 바꾸기 전  → 베란다 호스 → 결과 A
프롬프트 바꾼 후    → 베란다 호스 → 결과 B
                              ↓
                    A와 B의 차이 = 프롬프트 변경의 효과
```

제품이 바뀌면 이 뺄셈이 성립하지 않습니다.

### 왜 새 제품으로 테스트하지 않는가

새 제품에서 잘 나오면 **개선된 것인지 그 제품이 쉬운 것인지 모릅니다.**
그건 측정이 아니라 기분입니다.

### Benchmark 규칙

- 모든 테스트는 Benchmark로 한다
- 새 Benchmark는 **사람 승인 없이 추가하지 않는다**
- Benchmark는 **삭제하거나 초기화하지 않는다**
- 구체적인 ID는 `docs/DEVELOPMENT_ENVIRONMENT.md` §5에 있다

## 7. 품질 철학

### 좋은 이미지란 무엇인가

**순서가 있습니다. 위가 아래보다 항상 중요합니다.**

```
1순위  원본과 같은 제품인가          ← 이게 아니면 나머지는 의미 없다
2순위  글자가 잘못 박히지 않았나
3순위  사람이 나오면 한국인인가
4순위  사진으로서 보기 좋은가        ← 마지막이다
```

1순위가 깨지면 **나머지가 아무리 좋아도 버립니다.**

### 제품 동일성이란 무엇인가

원본 사진 기준으로 **유지되어야 하는 것**과 **바꿔도 되는 것**입니다.

**바꿔도 되는 것** (2026-08-09 확정)

```
배경 · 조명 · 촬영 구도 · 분위기 · 사람 모델 · 연출
```

**바꾸면 안 되는 것**

```
제품 형태 변경 · 구성품 추가 · 구성품 삭제 · 제품 색상 변경
제품 구조 변경 · 제품 재질 변경 · 제품 크기 비율 변경 · 제품 특징 변경
사진에 없는 제품 생성 · 사진에 없는 구성품 생성 · 허구의 제품 정보 생성
```

> **사진에 없는 것은 만들지 않습니다.
> 확인되지 않은 것은 추측하지 않습니다.**
>
> 실제 제품과 다른 결과가 나오면 **이미지 품질과 관계없이 실패**입니다.

### 정보 수집에 대한 전제

실제 운영에서 사용자는 **제품을 충분히 촬영해 제공합니다** — 정면·후면·
측면·상단·하단·디테일·구성품·연결부·포장지·라벨·사양표·설명서.

따라서 AI는 **제공된 사진 안에서 제품을 최대한 정확하게 이해**해야 합니다.
부족한 정보를 상상하거나 추측해서 채우는 것이 목적이 아닙니다.

**웹 조사는 사진만으로 식별이 어려울 때만 보조로 씁니다. 웹 조사 결과도
실제 사진보다 우선하지 않습니다.**

### OCR이 왜 중요한가

**포장지에는 사진으로 알 수 없는 사실이 적혀 있습니다.**

호스 사진을 아무리 들여다봐도 길이가 3M인지, 재질이 PVC인지, 어느 회사가
만들었는지 알 수 없습니다. **그건 글자로만 알 수 있습니다.**

이번 세션에서 OCR을 돌리자 **987자**가 나왔고, 그 결과 Product Package가
추측에서 사실로 바뀌었습니다.

### Product Package가 왜 중요한가

> **Product Package의 품질이 곧 이미지 품질입니다.**

Gemini는 Product Package를 믿고 그립니다. **거기에 없는 정보는 Gemini가
상상으로 채웁니다.** 그리고 상상으로 채운 부분이 바로 "다른 제품"이
됩니다.

즉 이미지가 이상하면 **Gemini를 의심하기 전에 Package를 먼저 봅니다.**

```
Package가 부실하다  →  Gemini가 상상한다  →  다른 제품이 나온다
Package가 정확하다  →  Gemini가 근거를 갖는다  →  같은 제품이 유지된다
```

## 8. 세션이 바뀌어도 유지해야 하는 것

**아래는 절대 바뀌면 안 됩니다.**

### 개발 방식

- Sprint 단위로 진행한다. 앞 Sprint가 끝나기 전에 다음 것을 추가하지 않는다
- Local → Benchmark → 검증 → 승인 → 원격 순서를 지킨다
- 환경 문서를 먼저 고치고 코드를 나중에 고친다

### 검증 방식

- 모든 테스트는 Benchmark(베란다 호스)로 한다
- **브라우저에서 사람이 직접 본다**
- Build · Test · Lint · Typecheck를 통과시킨다
- 실패는 감추지 않고 원인을 확인해 보고한다

### 사고방식

- **추측하지 않는다.** 확인한 사실만 쓴다
- 모르는 것은 "미확인"이라고 적는다
- **사실과 평가를 구분한다**
- 사람의 판단 자리를 없애지 않는다

### 절대 원칙 (요약)

1. **제품 동일성 > 이미지 품질**
2. **사람이 최종 판단한다.** Claude는 "확인했다"고 말하지 않는다
3. **추측 금지.** 확인한 사실만
4. **돈이 나가는 호출은 사전 승인**
5. **SSH 터널·원격 환경은 건드리지 않는다**
6. **Benchmark를 바꾸지 않는다**

## 9. 새로운 Claude가 처음 해야 하는 일

### 1단계 — 문서를 순서대로 읽는다

```
① docs/MASTER_GUIDE.md              ← 이 문서. 왜 이렇게 하는가
② AGENTS.md                          ← 규칙과 개발 순서
③ docs/DEVELOPMENT_ENVIRONMENT.md    ← 환경 사실 (SSOT)
```

**순서를 지킵니다.** 왜(①)를 모르고 무엇을(②③) 먼저 읽으면 규칙을 형식으로만
따르게 됩니다.

### 2단계 — 지금 상태를 확인한다

추측하지 말고 직접 봅니다.

- 어떤 포트에 무엇이 떠 있는가 (SSH 터널인가, 로컬인가)
- 로컬 데이터베이스에 Benchmark가 있는가
- 현재 브랜치와 커밋
- 커밋되지 않은 변경이 있는가

**환경 문서와 실제가 다르면, 문서를 먼저 고칩니다.**

### 3단계 — 현재 Sprint 목표를 확인한다

지금 어느 Sprint이고 무엇이 남았는지 확인합니다. **Sprint를 건너뛰지
않습니다.**

### 4단계 — 작업 순서를 지킨다

```
1. AGENTS.md 읽기
2. docs/DEVELOPMENT_ENVIRONMENT.md 읽기
3. 현재 Sprint 목표 확인
4. 코드 작업
5. Build
6. Test
7. 브라우저에서 사람이 직접 확인할 수 있도록 화면 준비
8. 사람 승인
9. 완료 보고
```

**7·8번을 건너뛰지 않습니다.**

### 5단계 — 보고할 때

- 한글로 쓴다
- 코드·명령어를 그대로 들이밀지 않는다
- 요금 발생 여부를 밝힌다
- **사실만 보고하고 평가하지 않는다**
- 예/아니오 질문은 각 선택의 결과를 설명한다

## 10. 프로젝트가 커져도 잃으면 안 되는 가치

### 하나 — 사람의 자리

기능이 늘고 자동화가 늘어도 **사람이 판단하는 세 자리를 없애지
않습니다.**

```
① Product Object 확정   — 뽑아낸 제품 정보가 맞는지
② 생성 이미지 선택      — 이게 우리 제품이 맞는지
③ 발행 승인             — 세상에 내보내도 되는지
```

이 자리를 없애면 **빨라지지만, 틀린 것이 그대로 나갑니다.**

### 둘 — 모른다고 말할 수 있는 능력

시스템이 "모른다"를 "괜찮다"로 바꾸는 순간 **모든 초록색이 의미를
잃습니다.**

- 확인하지 못한 것은 **미확인**
- 표본이 적으면 **판정 유보**
- 돌려보지 않았으면 **모름**

**"문제를 못 봤다"와 "문제가 없다"는 다른 말입니다.**

### 셋 — 실제 제품에 대한 정직함

이 시스템의 결과물은 **실제로 팔리는 상품 페이지**가 됩니다. 사진과 다른
물건이 배송되면 그건 소비자 피해입니다.

**제품 동일성은 기술 취향이 아니라 파는 사람의 책임입니다.**

### 넷 — 왜 그렇게 했는지에 대한 기록

규칙만 남고 이유가 사라지면, 다음 사람이 **"이거 왜 이렇게 복잡하지"**
하며 되돌립니다.

이 문서의 규칙들은 대부분 **사고가 나서 생긴 것**입니다. 새 규칙을 만들 때는
**그것을 만든 사건을 함께 적습니다.**

### 다섯 — 속도보다 신뢰

빨리 만드는 것보다 **틀리지 않는 것**이 중요합니다.

한 번 잘못된 상세페이지가 나가면 되돌리는 비용이 만드는 비용보다 큽니다.

> **"이미지 품질보다 제품 동일성이 항상 우선한다."**
>
> 이 한 문장이 이 프로젝트 전체의 요약입니다.
