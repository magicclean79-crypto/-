# PROJECT MEMORY — 프로젝트가 겪어서 알게 된 것

> **이 문서는 "왜 그렇게 해야 하는지"를 기억합니다.**
>
> 규칙만 남고 이유가 사라지면, 다음 사람이 "이거 왜 이렇게 복잡하지" 하며
> 되돌립니다. 그래서 **각 항목에 그것을 알게 된 사건**을 함께 적습니다.
>
> 새 경험을 얻으면 여기에 **추가**합니다. 지우지 않습니다.
>
> 확인한 사실만 적습니다. "그럴 것 같다"는 적지 않습니다.

**마지막 업데이트: 2026-08-09**

## AI · 이미지 생성

### M-1. Product Package의 품질이 곧 이미지 품질이다

**Gemini는 Product Package를 믿고 그립니다. 거기 없는 정보는 상상으로
채웁니다.** 그리고 상상으로 채운 부분이 정확히 "다른 제품"이 됩니다.

**겪은 일 (2026-08-08)**: Product Package가 부실한 상태로 이미지를 생성했더니
특징 강조·구성품·디테일·사용 장면·썸네일이 **원본과 다른 제품**으로
나왔습니다.

**그래서**: 이미지가 이상하면 **Gemini를 의심하기 전에 Package를 먼저 봅니다.**

```
Package 부실  →  Gemini가 상상  →  다른 제품
Package 정확  →  Gemini가 근거 확보  →  같은 제품 유지
```

### M-2. OCR을 돌리지 않으면 제품 정보가 전부 추측이 된다

**겪은 일 (2026-08-08)**: Product Profile의 OCR 결과가 0자였습니다. 처음엔
"OCR 성능이 나쁘다"고 판단했는데, **확인해 보니 OCR을 한 번도 실행하지
않았습니다.**

`POST /images/:id/ocr` 는 **별도 단계**이고, Product Profile은 DB에 저장된
OCR 결과를 읽어 쓸 뿐입니다. 실행하지 않으면 그냥 빈칸입니다.

**결과 비교**

| 항목 | OCR 없이 (GPT 추측) | OCR 실행 후 (사실) |
| --- | --- | --- |
| 제품명 | 물 분사용 스프레이 건 세트 | **베란다용 스텐 호스 세트 3M** |
| 브랜드 | 없음 | **삼정크린마스터(주)** |
| 재질 | 플라스틱, 금속 | **ABS, PVC, 스테인리스** |
| 규격 | 없음 | **호스 길이 3M · 원산지 한국** |
| OCR 원문 | 0자 | **1,015자** |

**그래서**: **Product Profile 전에 반드시 OCR을 먼저 실행합니다.**

**교훈 하나 더**: "성능이 나쁘다"고 결론 내리기 전에 **"실행되긴 했나"를
먼저 확인합니다.**

### M-2-1. 포장지의 "품명"은 상품명이 아니다 (2026-08-09)

포장지에는 이름이 **두 군데** 적혀 있고, 뜻이 다르다.

| 위치 | 표기 | 정체 |
| --- | --- | --- |
| **라벨 앞면 큰 글씨** | 베란다용 스텐 호스 세트 3M | **실제 상품명** |
| 품질표시 "품명" 칸 | 연질염화비닐호스 | **법정 재질 분류** |

**겪은 일**: "품명"을 `공식 품명`이라는 이름으로 프롬프트에 함께 넘겼더니
**상품명이 두 개인 것처럼 읽혔다.** CTO가 "상품명 추출이 잘못됐다"고
지적했고, 확인해 보니 상품명 자체는 맞았지만 **옆에 붙은 다른 이름이
혼란을 만들고 있었다.**

**그래서**: 품명은 상품명 자리에 두지 않고 `법정 재질 분류(상품명 아님)`
으로만 넘긴다. 재질 정보(연질염화비닐)는 제품 동일성에 쓸모가 있으므로
버리지는 않는다.

**교훈**: 값이 맞아도 **이름표가 틀리면 틀린 정보가 된다.** 받는 쪽(Gemini)
은 이름표를 보고 뜻을 정한다.

### M-3. 원본 사진을 함께 보내야 제품이 유지된다

배경 제거본만 보내면 Gemini가 **색상·질감·디테일의 근거를 잃습니다.** 그
빈자리를 상상으로 채우면 다른 제품이 됩니다.

**그래서**: 두 장을 함께 보냅니다.

| 사진 | 역할 |
| --- | --- |
| 배경 제거본 | 제품 **윤곽** 기준 |
| 원본 사진 | **색상·재질·질감·형태·구성품·디테일** 기준 |

프롬프트에도 두 장이 각각 무엇인지, **둘이 같은 제품**임을 명시합니다.

---

### M-4. 제품 동일성 규칙은 프롬프트 맨 앞에 둔다

프롬프트는 **뒤에 오는 지시일수록 약하게 반영되는 경향**이 있습니다.

**그래서**: 가장 중요한 제약(제품 동일성)을 **맨 앞**에 놓습니다.

현재 순서:

```
① [최우선 규칙 — 제품 동일성]
② [제품 정보 — 참고용]
③ [제품 정보 사용 규칙]   ← 글자 렌더링 금지
④ [사람이 등장하는 경우]  ← 한국인 모델
⑤ 실제 지시문
```

---

### M-5. 글자 금지 규칙은 제품 정보가 없어도 붙인다

**이유**: 원본 사진 자체에 라벨·포장 문구가 찍혀 있고, Gemini는 그것을
**그대로 베껴 그리려 합니다.** 글자를 넣지 말라는 지시가 필요한 이유는
우리가 정보를 넘겼기 때문이 아니라 **사진에 이미 글자가 있기 때문**입니다.

### M-6. 사람 모델은 한국인이 기본이다

**겪은 일 (2026-08-08)**: 사용 장면 이미지에 **서양인 모델**이 생성됐습니다.

이 제품의 실제 사용자는 한국 소비자이고, 상세페이지에 서양인이 나오면
제품과 사용 맥락이 어긋납니다.

**그래서**: 20~30대의 자연스럽고 세련된 한국인을 기본으로 명시합니다.
**사람이 필요 없는 장면이면 사람을 넣지 않습니다.**

### M-7. 이미지 생성 경로가 갈라지면 품질이 갈라진다

**겪은 일 (2026-08-08)**: 후보 생성 경로만 Product Package를 쓰고, 대표
사진·사용 장면 경로는 쓰지 않았습니다. **같은 앱인데 어떤 버튼을 누르냐에
따라 결과가 달라지는** 상태였습니다.

**그래서**: 모든 경로가 **문장 조립 함수 하나**만 씁니다. 경로마다 프롬프트를
따로 만들면, 나중에 "왜 이 사진만 이상하지"를 추적할 수 없습니다.

### M-20. 웹 자동 조사를 첫 단계에 둔다 (방침, 2026-08-09)

**CTO 지시**: 어떤 사진이 들어와도 **철저한 조사를 기본**으로 하고, 모든
정보를 분석해 Gemini에 전달한다. **웹 자동 조사는 첫 단계에서 다 끝내고**
그다음에 Gemini로 넘어간다.

```
사진 → OCR·Vision → [웹 자동 조사] → 교차 검증 → Product Package → Gemini
                          ↑ 첫 단계에 포함
```

**수동 조사로 확인된 효과 (2026-08-09, 베란다 호스)**:
포장지만으로는 알 수 없던 것들이 나왔다 — 고무패킹 2개의 **용도**(연결부
누수 방지), 표면 **이온 연마 처리**, 내부 PVC 호스 구조, 부품 명칭
(분사망 본체·나팔·축너트·손잡이). 이런 구조 정보는 **제품 동일성에 직접
도움**이 된다.

### M-20-1. 정보 출처에는 절대 순서가 있다 (2026-08-09)

```
실제 제품 사진 > OCR > Vision > 바코드 > 모델명
              > 공식 제조사 홈페이지 > 공식 카탈로그 > 기타 검색
```

**쇼핑몰 정보는 공식 정보가 아니다.** 다나와·G마켓·11번가·이마트·GS SHOP
같은 판매처 표기는 제조사 표기가 아니다.

**겪은 일 (2026-08-09)**: 수동 웹 조사에서 얻은 "새 사실"의 대부분이 쇼핑몰
출처였다 — 고무패킹 용도, 이온 연마 처리, 내부 PVC 구조, 분사 6가지. 그중
**분사 6가지는 실제로 5m 제품 정보**였고 실물 3M 포장지는 4가지였다.

새 기준을 적용하자 그 조사 결과의 **대부분이 폐기 대상**이 됐고, 포장지
OCR에서 나온 것만 남았다.

**웹 조사는 항상 하지 않는다.** OCR·Vision·바코드·모델명으로 충분하면
생략한다. 조사 자체가 목적이 아니라, **Gemini가 추측하지 않게 하는 것**이
목적이다.

### M-22. "우선순위로 덮어쓰기"와 "교차 검증"은 다르다 (2026-08-09)

T1-21까지는 브랜드·모델을 `identification.brand ?? profile.brand ?? null`
식으로 채웠다 — OCR이 있으면 OCR, 없으면 GPT 분석. **이건 우선순위이지
검증이 아니다.** 두 출처가 서로 다른 값을 말해도 조용히 OCR 값으로
덮어썼고, 충돌이 있었다는 사실 자체가 어디에도 남지 않았다.

**그래서(T1-23)**: 값을 가진 출처가 하나뿐일 때만 그 값을 쓴다. 둘
이상인데 값이 다르면 **채우지 않는다** — `resolvedValue`가 null로
남고, 어떤 출처가 무엇을 말했는지는 그대로 기록해 브라우저에서 사람이
본다. `packages/core/src/product-profile/cross-verification.ts`.

**아직 못 한 것**: 실제 충돌 사례로 화면을 확인하지 않았다. 벤치마크
(베란다 호스)에서는 OCR과 GPT 분석의 브랜드가 같은 값이라 지금까지
`agreed`만 나왔다 — `conflict` 화면은 유닛 테스트로만 확인했다.

### M-21. 자동 조사는 "비슷한 제품"을 가져올 위험이 크다

**겪은 일 (2026-08-09)**: 같은 브랜드 **5m 제품**의 스펙이 검색 결과 상위에
나왔고, 분사 방식이 **6가지**로 적혀 있었다. 그런데 실물 3M 포장지에는
**4가지**(일반·45°·90°·직수)였다.

사람이라서 "이건 다른 규격 제품"이라고 걸러냈지만, **자동화하면 그대로
가져온다.** 호스·청소용품은 이름이 비슷한 제품이 아주 많다.

**그래서 자동 조사에는 반드시 안전장치를 둔다:**

| | 규칙 |
| --- | --- |
| 1 | **바코드가 일치할 때만 신뢰한다** — 제품을 하나로 특정하는 유일한 식별자 |
| 2 | 바코드가 없으면 **제조사 + 제품명 + 규격이 모두 일치**할 때만 쓴다 |
| 3 | **포장지(실물) 정보가 웹 정보보다 항상 우선한다** |
| 4 | 충돌하면 **채우지 않고 "충돌 있음"으로 표시**한다 — 사람이 판단 |
| 5 | **출처 URL을 반드시 함께 기록**한다 |

**GPT에게 "아는 것"을 묻는 방식은 쓰지 않는다.** 모르는 제품을 그럴듯하게
지어내면 "추측 금지" 원칙이 무너진다. 공식 바코드 조회(코리안넷)처럼
**출처가 특정되는 수단**을 1순위로 쓴다.

### M-8. AI가 만든 것을 AI가 검사하면 검증이 아니다

**겪은 일 (2026-08-08)**: Claude가 생성 이미지를 보고 *"품질 양호"·"글자 박힘
없음"·"제품 형태 정확히 재현"* 이라고 보고했습니다. **그 판단은 사람의
몫이었습니다.**

**그래서**: Claude는 브라우저에서 확인 가능한 상태까지만 준비하고,
**"여기까지 준비되었습니다. 브라우저에서 직접 확인해 주세요."** 라고 보고하고
멈춥니다.

**사실과 평가를 구분합니다.**

| 보고해도 되는 것 (사실) | 보고하면 안 되는 것 (평가) |
| --- | --- |
| 생성 13장, 실패 0장 | "품질이 좋습니다" |
| 프롬프트에 이 문장이 들어갔다 | "의도대로 적용됐습니다" |
| OCR이 987자를 읽었다 | "정확하게 읽었습니다" |

### M-9. 테스트 통과는 "배선이 맞다"이지 "결과가 좋다"가 아니다

단위 테스트는 **문자열이 프롬프트에 들어갔는지**만 확인합니다. 그 프롬프트가
**실제로 좋은 이미지를 만드는지는 증명하지 않습니다.**

**그래서**: 검사 102개가 전부 통과해도 **사람의 브라우저 확인을 건너뛰지
않습니다.**

### M-11. 포트가 로컬인지 터널인지 반드시 확인한다

**겪은 일 (2026-08-08)**: 3000·4000번을 로컬 서버로 착각하고 작업했습니다.
실제로는 **SSH 터널로 AWS EC2에 연결**돼 있었습니다. 그 결과 "원격을 건드리지
않았다"는 보고가 부정확했습니다.

**확인 방법**: 포트를 점유한 **프로세스 이름과 명령줄**을 봅니다. `ssh.exe`면
터널입니다.

**그래서**: 환경을 **추측하지 않습니다.** `docs/DEVELOPMENT_ENVIRONMENT.md`를
먼저 읽고, 다르면 **문서를 먼저 고칩니다.**

확인**합니다. 이번 경우 코드는 이미 완성돼 있어 새로 작성하지 않고

원인 규명은 여전히 `bridge/`를 고치는 일이라 이번에도 하지 않았습니다
(`docs/PROJECT_STATE.md` §3-5).

### M-24. 오래 걸리는 작업을 HTTP 응답으로 기다리면 끊긴다

**겪은 일 (2026-08-09)**: ChatGPT에서 T1-22를 실행했더니 **Cloudflare
524(timeout)** 가 났습니다. `POST /run` 이 Claude Code 호출이 끝날 때까지

**중요한 사실**: 524가 났어도 **작업은 죽지 않았습니다.** 서버는 끝까지

그대로 사실로 읽었다면 멀쩡한 결과를 버리고 다시 돌렸을 것입니다.

**그래서**: 요청과 실행을 분리했습니다. `/run` 은 실행을 시작하고 **즉시
202**로 돌아오고(실측 83ms), 진행은 `GET /tasks/:id` 와 현황판
(`localhost:4201`)으로 봅니다.

**딸려 온 문제**: 비동기가 되면 **실행이 죽었는지 아직 도는지** 구분해야
합니다. 30초마다 심장박동을 기록하고, 신호가 끊긴 IN_PROGRESS는 대기열로
되돌립니다. 되돌리는 길도 **상태 게이트가 허용하는 전이만** 밟습니다 —
복구를 만든다고 게이트에 구멍을 내지 않습니다.

### M-28. 공통 시스템에 프로젝트 이야기를 넣지 않는다

**겪은 일 (2026-08-09)**: Bridge는 이 저장소 하나를 위해 만들어졌습니다.
읽을 문서 목록도, 건드리면 안 되는 파일도, 검증 명령도 **코드 안에 문자열로
박혀 있었습니다.** 다음 프로젝트를 시작하려면 코드를 고쳐야 하는 상태였고,
작업 파일도 같은 통에 섞였습니다.

**그래서**: 나누는 기준을 하나로 정했습니다.

| | |
| --- | --- |
| **공통 시스템** (`bridge/*.mjs`) | 어느 프로젝트에서든 그대로 |
| **프로젝트 데이터** (`projects/<ID>/`) | 저장소 경로·문서·금지 항목·검증 명령·작업·결과 |

판단 기준은 간단합니다 — **프로젝트가 바뀌면 달라지는 값은 전부 등록
정보로** 뺍니다. 새 프로젝트를 시작할 때 고칠 코드가 있다면, 그것은 아직
분리가 덜 된 것입니다.

**동작하는 것은 옮기지 않았습니다.** 기존 프로젝트(`acos`)의 작업은
`bridge/tasks`·`bridge/results` 그대로 둡니다. 재사용을 만든다고 멀쩡한
것을 이사시키면 없던 사고가 생깁니다.

### M-29. "막힘"을 쉬운 선택지로 만들면 무인 실행이 무너진다

BLOCKED 상태를 만들 때 가장 조심한 것은 **그것이 도피처가 되는 것**입니다.
조금만 애매해도 사람에게 미루면, 사장님은 지시 한 번에 질문 열 개를 받게
됩니다 — 무인 실행의 목적이 사라집니다.

**그래서 BLOCKED에는 조건을 걸었습니다.** `question`(무엇을 정해야 하는지)과
`why`(왜 스스로 정할 수 없는지)가 없으면 **BLOCKED로 들어오지 못합니다.**
이유 없이 멈춘 작업은 아무도 풀 수 없기 때문입니다.

| 상황 | 어떻게 |
| --- | --- |
| 문서에 답이 있음 | 스스로 정한다 |
| 어느 쪽이든 되는 사소한 선택 | **가장 보수적인 쪽**을 고르고 이유를 적는다 |
| 사장님 지시 범위를 넘는 결정 | BLOCKED |

**스스로 정할 수 있는 것을 사람에게 미루는 것도 실패입니다.**

### M-30. 무인이었는지는 모델의 자기 보고로 확인하지 않는다

`--dangerously-skip-permissions` 를 줬다고 해서 승인 요청이 정말 없었는지는
알 수 없습니다. 모델에게 "물어봤니?"라고 되묻는 것도 검증이 아닙니다.

**실측(2026-08-09, T1-29)**: 플래그를 **빼면** 승인이 필요한 호출이 멈추는
대신 **자동 거부**되고, 그 사실이 결과 이벤트의 `permission_denials` 배열에
남습니다. 즉 **그 배열이 비어 있지 않다는 것 자체가 "이번 실행은 완전한
무인이 아니었다"는 증거**입니다.

**그래서**: 매 실행마다 그 배열을 기록하고, 비어 있지 않으면 무엇을 허용할지
사람이 정하도록 BLOCKED로 만듭니다. **주장 대신 흔적으로 확인합니다.**

### M-27. 통과 여부를 문장에서 짐작하면 게이트가 엉뚱한 것을 막는다

**겪은 일 (2026-08-09)**: 게이트는 `testResults` 의 문장에 "실패"·"오류"
같은 낱말이 있는지로 통과 여부를 판정했습니다. 그래서 아래가 전부 **실패로
잡혔습니다.**

| 실제로 적힌 말 | 뜻 | 게이트 판정 |
| --- | --- | --- |
| `12장 생성 · 실패 0` | 성공 | 실패 |
| `13건 통과, 0건 실패` | 성공 | 실패 |
| `eslint 0건 (새 오류 없음)` | 성공 | 실패 |
| `1025/1033 통과(8건은 preExisting)` | 이번 변경분 성공 | 실패 |

낱말을 지우는 정규식을 계속 덧붙였지만, **정직하게 쓸수록 막히는** 구조는
그대로였습니다. 보고를 잘할수록 벌을 받는 규칙은 오래 못 갑니다.

**그래서**: 판정을 명시값으로 받습니다.

```json
"lint": { "ok": true, "detail": "npx eslint . — 0건" }
```

`ok` 가 있으면 문장은 사람이 읽는 설명일 뿐입니다. 옛 기록(문자열)도 계속
읽되, 새로 쓰는 것은 전부 명시합니다.

**교훈**: 기계가 판정해야 하는 값을 **사람 말로 받으면 안 됩니다.**
막아야 할 것을 막는 것만큼, **막지 말아야 할 것을 통과시키는 것**도
게이트의 일입니다.

### M-26. 무인 실행에서 가장 위험한 것은 "조용히 멈추는 것"이다

**겪은 일 (2026-08-09)**: Bridge가 부르는 Claude Code는 `stdin`이 열린 채로

| | |
| --- | --- |
| `stdin` | 아예 닫는다(`ignore`) |

| 무응답 15분 | 끊고 이유를 남긴다 |

**살아 있는 것과 일하고 있는 것은 다릅니다.** 프로세스가 살아 있다는 신호
하나만으로는 구분할 수 없어서, 출력이 있었는지를 따로 봅니다.

   32GB 중 **10.9GB가 그대로 남아 있었다.** 즉 진짜 원인은 메모리가
   아니라 **디스크가 없어 워커의 캐시 쓰기(또는 페이지파일 확장)가
   실패한 것**으로 보인다 — 에러 메시지를 곧이곧대로 믿으면 엉뚱한
   곳(RAM 증설)을 고치게 된다. **"메모리 부족" 에러가 나면 디스크
   여유부터 확인한다.**
2. **디스크가 바닥난 동안 쓰인 파일이 0바이트로 잘렸다** —
   `bridge/tasks/T1-30.json`이 그 예다. Bridge의 `listTasks`가 이 파일을
   읽다가 `JSON.parse`에서 죽었는데, 이 함수는 **서버가 뜰 때마다**
   (`recoverAbandonedRuns`) 불린다 — 즉 **깨진 파일 하나가 Bridge
   서버 전체를 못 뜨게 만들 수 있었다**(실측: 별도 포트에서 새
   서버를 띄우자 그 자리에서 죽었다). 지우지 않고 **건너뛰도록**
   `bridge-io.mjs`의 `listTasks`를 고쳤다(`readJsonSkipBroken`) —
   무엇을 요청했는지 모르는 파일을 지어내거나 없애지 않는다.

**그래서**: 디스크가 타이트한 환경에서는 ① 워커 크래시의 "메모리
부족"이라는 말을 문자 그대로 믿지 않는다(RAM을 실제로 확인한다),
② **목록을 훑는 코드는 파일 하나가 깨져도 죽지 않아야 한다** —
특히 서버 시작 경로처럼 매번 불리는 곳은 더욱 그렇다(M-26 "조용히
멈추는 것이 가장 위험하다"의 또 다른 형태). ③ **떠 있는 Bridge
서버는 코드를 고쳐도 재시작 전까지 옛 코드로 돈다** — 이번엔 이
세션이 그 서버의 자식 프로세스라 재시작하면 스스로 죽을 위험이 있어
재시작하지 않고, 별도 포트(4210)에 임시 인스턴스를 띄워 검증만
했다.

### M-31. `bridge/`가 통째로 git 미추적이다 — PC·디스크가 바뀌면 Bridge 이력이 사라진다 (2026-08-09, T1-30)

**겪은 일**: 하드웨어 변경(PC 교체·추가 SSD) 대응을 표준화하다가
`git ls-files bridge/`가 **빈 결과**를, `git status --porcelain bridge/`가
`?? bridge/`(전체 미추적)를 돌려주는 것을 확인했다. `.gitignore`에는
`bridge/.secrets/`·`bridge/tunnel-url.txt` 두 줄만 있어 **의도적으로
전부 제외한 것이 아니라, 애초에 한 번도 `git add`된 적이 없다.**

즉 Bridge 코드(`.mjs` 전부)·작업 지시(`tasks/`)·작업 결과(`results/`)·
프로젝트 등록 정보(`projects/`)·`STATUS.md`·`README.md`가 **이 워크트리
디스크 하나에만 존재한다.** `docs/PROJECT_STATE.md` §3-4의 "`T1-30.json`이
0바이트로 잘려 있었다"(디스크 포화 중 쓰다 만 것으로 추정, M-30과 같은
사건)도 같은 종류의 취약점이다 — git이라는 안전망이 없는 영역에서
일어났다.

**하지 않은 것**: `bridge/`를 git에 추가하는 것은 "건드리면 안 되는
것"(bridge/ 전부, 사람 승인 없이 수정 금지) 목록에 해당하고, 여러
프로젝트(acos 외 demo-widget 등)의 등록 정보·작업 이력이 한 커밋에
같이 들어가는 문제라 **사람이 정할 일**이라고 판단해 커밋하지 않았다.
`docs/RECOVERY_GUIDE.md` §9-6에 근거를 남기고, 이 작업(T1-30) 결과의
`decisionNeeded`에 올렸다.

**그래서**: git에 포함하기로 결정되기 전까지는, `bridge/tasks`·
`bridge/results`·`bridge/projects`를 주기적으로 다른 드라이브에
복사해 두는 것만으로도 PC 교체 시 이력 유실을 줄일 수 있다 — 이 복사는
`bridge/` 안의 파일을 고치는 게 아니라 밖으로 내보내는 것이라 가드레일에
걸리지 않지만, 이번 세션은 "정말 필요한 결정(git 포함 여부)"이 먼저라고
보고 실행하지 않았다.
