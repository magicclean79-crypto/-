## AI · 이미지 생성

### M-1. Product Package의 품질이 곧 이미지 품질이다

**Gemini는 Product Package를 믿고 그립니다. 거기 없는 정보는 상상으로
채웁니다.** 그리고 상상으로 채운 부분이 정확히 "다른 제품"이 됩니다.

**겪은 일 (2026-08-08)**: Product Package가 부실한 상태로 이미지를 생성했더니
특징 강조·구성품·디테일·사용 장면·썸네일이 **원본과 다른 제품**으로
나왔습니다.

**그래서**: 이미지가 이상하면 **Gemini를 의심하기 전에 Package를 먼저 봅니다.**

```
Package 부실  →  Gemini가 상상  →  다른 제품
Package 정확  →  Gemini가 근거 확보  →  같은 제품 유지
```

### M-2. OCR을 돌리지 않으면 제품 정보가 전부 추측이 된다

**겪은 일 (2026-08-08)**: Product Profile의 OCR 결과가 0자였습니다. 처음엔
"OCR 성능이 나쁘다"고 판단했는데, **확인해 보니 OCR을 한 번도 실행하지
않았습니다.**

`POST /images/:id/ocr` 는 **별도 단계**이고, Product Profile은 DB에 저장된
OCR 결과를 읽어 쓸 뿐입니다. 실행하지 않으면 그냥 빈칸입니다.

**결과 비교**

| 항목 | OCR 없이 (GPT 추측) | OCR 실행 후 (사실) |
| --- | --- | --- |
| 제품명 | 물 분사용 스프레이 건 세트 | **베란다용 스텐 호스 세트 3M** |
| 브랜드 | 없음 | **삼정크린마스터(주)** |
| 재질 | 플라스틱, 금속 | **ABS, PVC, 스테인리스** |
| 규격 | 없음 | **호스 길이 3M · 원산지 한국** |
| OCR 원문 | 0자 | **1,015자** |

**그래서**: **Product Profile 전에 반드시 OCR을 먼저 실행합니다.**

**교훈 하나 더**: "성능이 나쁘다"고 결론 내리기 전에 **"실행되긴 했나"를
먼저 확인합니다.**

### M-2-1. 포장지의 "품명"은 상품명이 아니다 (2026-08-09)

포장지에는 이름이 **두 군데** 적혀 있고, 뜻이 다르다.

| 위치 | 표기 | 정체 |
| --- | --- | --- |
| **라벨 앞면 큰 글씨** | 베란다용 스텐 호스 세트 3M | **실제 상품명** |
| 품질표시 "품명" 칸 | 연질염화비닐호스 | **법정 재질 분류** |

**겪은 일**: "품명"을 `공식 품명`이라는 이름으로 프롬프트에 함께 넘겼더니
**상품명이 두 개인 것처럼 읽혔다.** CTO가 "상품명 추출이 잘못됐다"고
지적했고, 확인해 보니 상품명 자체는 맞았지만 **옆에 붙은 다른 이름이
혼란을 만들고 있었다.**

**그래서**: 품명은 상품명 자리에 두지 않고 `법정 재질 분류(상품명 아님)`
으로만 넘긴다. 재질 정보(연질염화비닐)는 제품 동일성에 쓸모가 있으므로
버리지는 않는다.

**교훈**: 값이 맞아도 **이름표가 틀리면 틀린 정보가 된다.** 받는 쪽(Gemini)
은 이름표를 보고 뜻을 정한다.

### M-3. 원본 사진을 함께 보내야 제품이 유지된다

배경 제거본만 보내면 Gemini가 **색상·질감·디테일의 근거를 잃습니다.** 그
빈자리를 상상으로 채우면 다른 제품이 됩니다.

**그래서**: 두 장을 함께 보냅니다.

| 사진 | 역할 |
| --- | --- |
| 배경 제거본 | 제품 **윤곽** 기준 |
| 원본 사진 | **색상·재질·질감·형태·구성품·디테일** 기준 |

프롬프트에도 두 장이 각각 무엇인지, **둘이 같은 제품**임을 명시합니다.

---

### M-4. 제품 동일성 규칙은 프롬프트 맨 앞에 둔다

프롬프트는 **뒤에 오는 지시일수록 약하게 반영되는 경향**이 있습니다.

**그래서**: 가장 중요한 제약(제품 동일성)을 **맨 앞**에 놓습니다.

현재 순서:

```
① [최우선 규칙 — 제품 동일성]
② [제품 정보 — 참고용]
③ [제품 정보 사용 규칙]   ← 글자 렌더링 금지
④ [사람이 등장하는 경우]  ← 한국인 모델
⑤ 실제 지시문
```

### M-5. 글자 금지 규칙은 제품 정보가 없어도 붙인다

**이유**: 원본 사진 자체에 라벨·포장 문구가 찍혀 있고, Gemini는 그것을
**그대로 베껴 그리려 합니다.** 글자를 넣지 말라는 지시가 필요한 이유는
우리가 정보를 넘겼기 때문이 아니라 **사진에 이미 글자가 있기 때문**입니다.

### M-20. 웹 자동 조사를 첫 단계에 둔다 (방침, 2026-08-09)

**CTO 지시**: 어떤 사진이 들어와도 **철저한 조사를 기본**으로 하고, 모든
정보를 분석해 Gemini에 전달한다. **웹 자동 조사는 첫 단계에서 다 끝내고**
그다음에 Gemini로 넘어간다.

```
사진 → OCR·Vision → [웹 자동 조사] → 교차 검증 → Product Package → Gemini
                          ↑ 첫 단계에 포함
```

**수동 조사로 확인된 효과 (2026-08-09, 베란다 호스)**:
포장지만으로는 알 수 없던 것들이 나왔다 — 고무패킹 2개의 **용도**(연결부
누수 방지), 표면 **이온 연마 처리**, 내부 PVC 호스 구조, 부품 명칭
(분사망 본체·나팔·축너트·손잡이). 이런 구조 정보는 **제품 동일성에 직접
도움**이 된다.

### M-20-1. 정보 출처에는 절대 순서가 있다 (2026-08-09)

```
실제 제품 사진 > OCR > Vision > 바코드 > 모델명
              > 공식 제조사 홈페이지 > 공식 카탈로그 > 기타 검색
```

**쇼핑몰 정보는 공식 정보가 아니다.** 다나와·G마켓·11번가·이마트·GS SHOP
같은 판매처 표기는 제조사 표기가 아니다.

**겪은 일 (2026-08-09)**: 수동 웹 조사에서 얻은 "새 사실"의 대부분이 쇼핑몰
출처였다 — 고무패킹 용도, 이온 연마 처리, 내부 PVC 구조, 분사 6가지. 그중
**분사 6가지는 실제로 5m 제품 정보**였고 실물 3M 포장지는 4가지였다.

새 기준을 적용하자 그 조사 결과의 **대부분이 폐기 대상**이 됐고, 포장지
OCR에서 나온 것만 남았다.

**웹 조사는 항상 하지 않는다.** OCR·Vision·바코드·모델명으로 충분하면
생략한다. 조사 자체가 목적이 아니라, **Gemini가 추측하지 않게 하는 것**이
목적이다.

### M-22. "우선순위로 덮어쓰기"와 "교차 검증"은 다르다 (2026-08-09)

T1-21까지는 브랜드·모델을 `identification.brand ?? profile.brand ?? null`
식으로 채웠다 — OCR이 있으면 OCR, 없으면 GPT 분석. **이건 우선순위이지
검증이 아니다.** 두 출처가 서로 다른 값을 말해도 조용히 OCR 값으로
덮어썼고, 충돌이 있었다는 사실 자체가 어디에도 남지 않았다.

**그래서(T1-23)**: 값을 가진 출처가 하나뿐일 때만 그 값을 쓴다. 둘
이상인데 값이 다르면 **채우지 않는다** — `resolvedValue`가 null로
남고, 어떤 출처가 무엇을 말했는지는 그대로 기록해 브라우저에서 사람이
본다. `packages/core/src/product-profile/cross-verification.ts`.

**아직 못 한 것**: 실제 충돌 사례로 화면을 확인하지 않았다. 벤치마크
(베란다 호스)에서는 OCR과 GPT 분석의 브랜드가 같은 값이라 지금까지
`agreed`만 나왔다 — `conflict` 화면은 유닛 테스트로만 확인했다.

### M-21. 자동 조사는 "비슷한 제품"을 가져올 위험이 크다

**겪은 일 (2026-08-09)**: 같은 브랜드 **5m 제품**의 스펙이 검색 결과 상위에
나왔고, 분사 방식이 **6가지**로 적혀 있었다. 그런데 실물 3M 포장지에는
**4가지**(일반·45°·90°·직수)였다.

사람이라서 "이건 다른 규격 제품"이라고 걸러냈지만, **자동화하면 그대로
가져온다.** 호스·청소용품은 이름이 비슷한 제품이 아주 많다.

**그래서 자동 조사에는 반드시 안전장치를 둔다:**

| | 규칙 |
| --- | --- |
| 1 | **바코드가 일치할 때만 신뢰한다** — 제품을 하나로 특정하는 유일한 식별자 |
| 2 | 바코드가 없으면 **제조사 + 제품명 + 규격이 모두 일치**할 때만 쓴다 |
| 3 | **포장지(실물) 정보가 웹 정보보다 항상 우선한다** |
| 4 | 충돌하면 **채우지 않고 "충돌 있음"으로 표시**한다 — 사람이 판단 |
| 5 | **출처 URL을 반드시 함께 기록**한다 |

**GPT에게 "아는 것"을 묻는 방식은 쓰지 않는다.** 모르는 제품을 그럴듯하게
지어내면 "추측 금지" 원칙이 무너진다. 공식 바코드 조회(코리안넷)처럼
**출처가 특정되는 수단**을 1순위로 쓴다.

### M-23. Bridge의 `state`는 실제 코드 상태와 어긋날 수 있다 (2026-08-09)

**겪은 일**: `node bridge/bridge-cli.mjs status`가 T1-22를 `IN_PROGRESS`로
보여줬습니다. 그런데 실제로 `packages/core/src/product-profile/
product-research.ts`·`apps/api/src/product-research/`는 완전히 구현돼
있었고, `bridge/results/T1-22.json`의 `testResults`에도 build·typecheck
·lint·tests가 전부 통과로 기록돼 있었습니다 — **코드와 검증 기록은
`READY_FOR_REVIEW` 수준인데 `state`만 `IN_PROGRESS`에 멈춰 있었습니다.**

원인은 확인하지 않았습니다(추정: 상태를 `TESTING`→`READY_FOR_REVIEW`로
올리는 도중 프로세스가 끊겼거나, 30초 심장박동 기록이 마지막 상태 갱신과

일이라 이 작업(T1-22) 범위가 아닙니다.**

**그래서**: Bridge의 `state` 필드 하나만 보고 "아직 안 됐다"고 판단하지
않습니다. `state`가 앞 단계에 멈춰 있어도 `bridge/results/<ID>.json`의
`testResults`·`workDone`·`blockedOn`을 직접 읽어 **실제로 무엇이 끝났는지
확인**합니다. 이번 경우 코드는 이미 완성돼 있어 새로 작성하지 않고
재검증만 했습니다(`docs/PROJECT_STATE.md` §3-3).

**같은 일이 T1-25에서 다시 있었습니다 (2026-08-09)**: `bridge-cli.mjs
status`가 T1-25를 `IN_PROGRESS`로 보여줬지만, `bridge/results/T1-25.json`
에는 완료 보고(`RESULT_JSON`, workDone 5건·testResults 전부 통과)가 이미
있었고 코드(`product-package.ts`의 `research` 필드·테스트·화면 블록)도
실제로 완성돼 있었습니다. 한 번이 아니라 **반복되는 패턴**이라는 뜻입니다
— `state` 갱신이 실행 종료 시점에 유실되는 경로가 있는 것으로 보이지만,
원인 규명은 여전히 `bridge/`를 고치는 일이라 이번에도 하지 않았습니다
(`docs/PROJECT_STATE.md` §3-5).

### M-24. 오래 걸리는 작업을 HTTP 응답으로 기다리면 끊긴다

**겪은 일 (2026-08-09)**: ChatGPT에서 T1-22를 실행했더니 **Cloudflare
524(timeout)** 가 났습니다. `POST /run` 이 Claude Code 호출이 끝날 때까지
응답을 붙잡고 있었고, 터널은 **100초**에서 끊었습니다.

**중요한 사실**: 524가 났어도 **작업은 죽지 않았습니다.** 서버는 끝까지
일했고 결과도 기록됐습니다. 끊긴 것은 응답뿐입니다. 즉 겉으로는 "실패"로
보였지만 실제로는 **"결과를 볼 방법이 없던 것"** 이었습니다. 오류 메시지를
그대로 사실로 읽었다면 멀쩡한 결과를 버리고 다시 돌렸을 것입니다.

**그래서**: 요청과 실행을 분리했습니다. `/run` 은 실행을 시작하고 **즉시
202**로 돌아오고(실측 83ms), 진행은 `GET /tasks/:id` 와 현황판
(`localhost:4201`)으로 봅니다.

**딸려 온 문제**: 비동기가 되면 **실행이 죽었는지 아직 도는지** 구분해야
합니다. 30초마다 심장박동을 기록하고, 신호가 끊긴 IN_PROGRESS는 대기열로
되돌립니다. 되돌리는 길도 **상태 게이트가 허용하는 전이만** 밟습니다 —
복구를 만든다고 게이트에 구멍을 내지 않습니다.

### M-28. 공통 시스템에 프로젝트 이야기를 넣지 않는다

**겪은 일 (2026-08-09)**: Bridge는 이 저장소 하나를 위해 만들어졌습니다.
읽을 문서 목록도, 건드리면 안 되는 파일도, 검증 명령도 **코드 안에 문자열로
박혀 있었습니다.** 다음 프로젝트를 시작하려면 코드를 고쳐야 하는 상태였고,
작업 파일도 같은 통에 섞였습니다.

**그래서**: 나누는 기준을 하나로 정했습니다.

| | |
| --- | --- |
| **공통 시스템** (`bridge/*.mjs`) | 어느 프로젝트에서든 그대로 |
| **프로젝트 데이터** (`projects/<ID>/`) | 저장소 경로·문서·금지 항목·검증 명령·작업·결과 |

판단 기준은 간단합니다 — **프로젝트가 바뀌면 달라지는 값은 전부 등록
정보로** 뺍니다. 새 프로젝트를 시작할 때 고칠 코드가 있다면, 그것은 아직
분리가 덜 된 것입니다.

**동작하는 것은 옮기지 않았습니다.** 기존 프로젝트(`acos`)의 작업은
`bridge/tasks`·`bridge/results` 그대로 둡니다. 재사용을 만든다고 멀쩡한
것을 이사시키면 없던 사고가 생깁니다.

### M-29. "막힘"을 쉬운 선택지로 만들면 무인 실행이 무너진다

BLOCKED 상태를 만들 때 가장 조심한 것은 **그것이 도피처가 되는 것**입니다.
조금만 애매해도 사람에게 미루면, 사장님은 지시 한 번에 질문 열 개를 받게
됩니다 — 무인 실행의 목적이 사라집니다.

**그래서 BLOCKED에는 조건을 걸었습니다.** `question`(무엇을 정해야 하는지)과
`why`(왜 스스로 정할 수 없는지)가 없으면 **BLOCKED로 들어오지 못합니다.**
이유 없이 멈춘 작업은 아무도 풀 수 없기 때문입니다.

| 상황 | 어떻게 |
| --- | --- |
| 문서에 답이 있음 | 스스로 정한다 |
| 어느 쪽이든 되는 사소한 선택 | **가장 보수적인 쪽**을 고르고 이유를 적는다 |
| 사장님 지시 범위를 넘는 결정 | BLOCKED |

**스스로 정할 수 있는 것을 사람에게 미루는 것도 실패입니다.**

### M-30. 무인이었는지는 모델의 자기 보고로 확인하지 않는다

`--dangerously-skip-permissions` 를 줬다고 해서 승인 요청이 정말 없었는지는
알 수 없습니다. 모델에게 "물어봤니?"라고 되묻는 것도 검증이 아닙니다.

**실측(2026-08-09, T1-29)**: 플래그를 **빼면** 승인이 필요한 호출이 멈추는
대신 **자동 거부**되고, 그 사실이 결과 이벤트의 `permission_denials` 배열에
남습니다. 즉 **그 배열이 비어 있지 않다는 것 자체가 "이번 실행은 완전한
무인이 아니었다"는 증거**입니다.

**그래서**: 매 실행마다 그 배열을 기록하고, 비어 있지 않으면 무엇을 허용할지
사람이 정하도록 BLOCKED로 만듭니다. **주장 대신 흔적으로 확인합니다.**

### M-27. 통과 여부를 문장에서 짐작하면 게이트가 엉뚱한 것을 막는다

**겪은 일 (2026-08-09)**: 게이트는 `testResults` 의 문장에 "실패"·"오류"
같은 낱말이 있는지로 통과 여부를 판정했습니다. 그래서 아래가 전부 **실패로
잡혔습니다.**

| 실제로 적힌 말 | 뜻 | 게이트 판정 |
| --- | --- | --- |
| `12장 생성 · 실패 0` | 성공 | 실패 |
| `13건 통과, 0건 실패` | 성공 | 실패 |
| `eslint 0건 (새 오류 없음)` | 성공 | 실패 |
| `1025/1033 통과(8건은 preExisting)` | 이번 변경분 성공 | 실패 |

낱말을 지우는 정규식을 계속 덧붙였지만, **정직하게 쓸수록 막히는** 구조는
그대로였습니다. 보고를 잘할수록 벌을 받는 규칙은 오래 못 갑니다.

**그래서**: 판정을 명시값으로 받습니다.

```json
"lint": { "ok": true, "detail": "npx eslint . — 0건" }
```

`ok` 가 있으면 문장은 사람이 읽는 설명일 뿐입니다. 옛 기록(문자열)도 계속
읽되, 새로 쓰는 것은 전부 명시합니다.

**교훈**: 기계가 판정해야 하는 값을 **사람 말로 받으면 안 됩니다.**
막아야 할 것을 막는 것만큼, **막지 말아야 할 것을 통과시키는 것**도
게이트의 일입니다.

### M-26. 무인 실행에서 가장 위험한 것은 "조용히 멈추는 것"이다

**겪은 일 (2026-08-09)**: Bridge가 부르는 Claude Code는 `stdin`이 열린 채로
실행되고 있었습니다. 아무것도 써 주지 않으므로, 자식이 입력을 한 번이라도

**그래서**:

| | |
| --- | --- |
| `stdin` | 아예 닫는다(`ignore`) |

| 무응답 15분 | 끊고 이유를 남긴다 |

**살아 있는 것과 일하고 있는 것은 다릅니다.** 프로세스가 살아 있다는 신호
하나만으로는 구분할 수 없어서, 출력이 있었는지를 따로 봅니다.

### M-30. 디스크 포화가 "메모리 부족"으로 잘못 보이고, Bridge 파일을 조용히 깨뜨린다 (2026-08-09, T1-28)

1. **`pnpm turbo run test`에서 Jest 워커가 "메모리 부족(ran out of
   memory)"으로 죽었다.** 처음엔 진짜 메모리 문제로 의심했지만

   아니라 **디스크가 없어 워커의 캐시 쓰기(또는 페이지파일 확장)가
   실패한 것**으로 보인다 — 에러 메시지를 곧이곧대로 믿으면 엉뚱한
   곳(RAM 증설)을 고치게 된다. **"메모리 부족" 에러가 나면 디스크
   여유부터 확인한다.**
2. **디스크가 바닥난 동안 쓰인 파일이 0바이트로 잘렸다** —

   서버를 띄우자 그 자리에서 죽었다). 지우지 않고 **건너뛰도록**

   무엇을 요청했는지 모르는 파일을 지어내거나 없애지 않는다.

**그래서**: 디스크가 타이트한 환경에서는 ① 워커 크래시의 "메모리
부족"이라는 말을 문자 그대로 믿지 않는다(RAM을 실제로 확인한다),
② **목록을 훑는 코드는 파일 하나가 깨져도 죽지 않아야 한다** —
특히 서버 시작 경로처럼 매번 불리는 곳은 더욱 그렇다(M-26 "조용히
멈추는 것이 가장 위험하다"의 또 다른 형태). ③ **떠 있는 Bridge
서버는 코드를 고쳐도 재시작 전까지 옛 코드로 돈다** — 이번엔 이
세션이 그 서버의 자식 프로세스라 재시작하면 스스로 죽을 위험이 있어
재시작하지 않고, 별도 포트(4210)에 임시 인스턴스를 띄워 검증만
했다.

### M-32. TESTING에 멈춘 작업은 reset + taskId 지정 /run으로 정확히 그 작업만 되살릴 수 있다 (2026-08-09, T1-39)

**겪은 일**: T1-24가 `TESTING`에서 `READY_FOR_REVIEW`로 못 올라간 채
멈춰 있었다. 원인은 `blockedOn`에 이미 적혀 있었다 — 게이트가 요구하는
"사용자가 확인할 항목"(`userChecks`) 기록이 빠져 있었다(M-25와 같은
종류). `REQUESTED` 작업이 없으니 `/run`이 아무것도 집지 못했다.

**확인한 것**: `node bridge/bridge-cli.mjs reset <ID> "<사유>"`는
`resetToRequested`의 `BACK_TO_QUEUE` 표(`bridge-io.mjs`)를 따라
`TESTING → IN_PROGRESS → REQUESTED`처럼 상태 계층이 허용하는 전이만
밟고, 그 작업 하나만 건드린다 — 같은 상태의 다른 작업에는 아무 영향이
없다(`bridge-cli.mjs status`로 직접 확인). 그 뒤 `POST /run`에
`taskId`를 **명시**하면 `startNextTask`(`bridge-executor.mjs`)가 그
작업이 정확히 `REQUESTED`인지 확인한 뒤에만 실행하고, 아니면
`TASK_NOT_FOUND`·`PROJECT_MISMATCH`·`NOT_RUNNABLE`로 **명시적으로
거부**한다 — "못 찾으면 대기열의 다른 것"으로 조용히 대체하는 경로가
코드에 아예 없다. 실행 중 `GET /runs`와 응답에 실린 `runId`를 끝까지
반복 확인해, 시작할 때 받은 `runId`가 종료까지 바뀌지 않았음을 실측
확인했다 — 다른 작업으로 바뀌어 실행되는 일은 없었다.

**그래서**: 특정 작업 하나만 정확히 재실행하고 싶을 때(다른 작업이
실수로 대신 돌면 안 될 때)는 ① 공식 `reset` 경로로 그 작업만
`REQUESTED`로 되돌리고 ② `POST /run`에 `taskId`를 명시해 호출하는
것이 안전하다 — Bridge가 스스로 대상을 검증하고, 대체 실행 경로가
설계상 없다.

### M-33. "직접 taskId 실행"이 안 되는 원인은 실행기가 아니라 CLI에 진입점이 없던 것이었다 (2026-08-09, T1-40)

**겪은 일**: "Bridge가 지정 taskId를 직접 실행하지 못한다"는 지시를 받고
`bridge-executor.mjs`(`startNextTask`)부터 의심했는데, 실제로 읽어 보니
taskId 지정·대체 금지·명시적 오류(`TASK_NOT_FOUND`·`PROJECT_MISMATCH`·
`NOT_RUNNABLE`) 로직은 **이미 정확했다** — `bridge-async.spec.mjs` 108건이
그것을 이미 검사하고 있었다(T1-39가 그 경로를 HTTP로 직접 호출해 확인한
것도 같은 코드였다, M-32). 진짜 빠진 것은 `bridge-cli.mjs`에 `run` 명령
자체가 없었다는 것이다 — `runNextTask` 함수 주석에는 "명령줄과 검사에서만
쓴다"고 적혀 있었는데, 그 명령줄 쪽 배선이 없었다.

**그래서**: 증상("안 된다")을 실행 로직의 결함으로 단정하지 않고, 먼저
**그 경로로 가는 진입점이 실제로 존재하는지**부터 확인한다. 이번 경우
아래 층(상태·실행기)은 이미 옳았고, 위 층(CLI)의 배선 누락이 원인이었다
— 근본 원인이 항상 가장 깊은 층에 있는 것은 아니다.

**딸려 나온 결함 하나**: 처음 CLI `run`을 구현할 때 `startNextTask`의
사전 거부 응답에만 있는 `accepted` 필드로 "실행됐는가"를 판정했다.
그런데 `runNextTask`가 실행을 끝까지 기다린 뒤 돌려주는 최종 객체
(`executeTask`의 반환값)에는 `accepted` 필드가 아예 없다 — 그래서
정상적으로 끝까지 실행됐지만 검증 게이트를 못 넘어 TESTING에 남은
경우까지 "실행되지 않음"으로 잘못 보고했다. 새로 만든
`bridge-cli.spec.mjs`를 처음 돌렸을 때 바로 드러났다. **"시작됐는가"는
`ran` 필드로만 판정해야 한다** — `accepted`는 시작 *전* 단계에만 있는
필드다.

**같이 확인한 것**: 문서(`bridge/openapi.yaml`)에는 `/run`이 200/400만
낼 수 있다고 적혀 있었는데, 서버 코드(`bridge-server.mjs`)는 이미
taskId 불일치 시 404·409를 실제로 내고 있었다 — 런타임은 맞고 문서만
낡아 있었다. ChatGPT Actions처럼 명세를 신뢰하는 호출자는 이 어긋남을
겪을 수 있었다.

### M-34. "전체 목록"과 "새로 생긴 것"은 다른 자료구조가 필요하다 (2026-08-09, T1-41)

**겪은 일**: `listTasks`·`getStatus`는 항상 **지금 이 순간의 전체
스냅샷**을 돌려준다. 총괄(CTO)이 완료·결정 필요 상태를 놓치지 않으려면
매번 전체를 훑어야 했는데, 그러면 두 가지 실패가 동시에 가능했다 —
목록이 길어지면 방금 새로 생긴 것을 **놓칠 수 있고**(완료 보고 누락),
반대로 매번 전부를 보고하면 이미 말한 것을 **또 말하게 된다**(중복
보고). 스냅샷 하나로는 이 둘을 동시에 막을 수 없었다 — "지금 무엇이
있는가"와 "지난번 이후 무엇이 새로 생겼는가"는 답이 다른 질문이기
때문이다.

**그래서**: 상태 전이를 **append-only 이벤트**로 따로 쌓고
(`bridge-events.mjs`), "어디까지 전달했는지"를 **별도 커서**로 저장했다
(이메일의 읽음/안읽음과 같은 구조). 스냅샷 조회(`listTasks`)는 그대로
두고, "새 것만" 필요한 자리에는 새 자료구조(`listUnconsumed` + `ack`)를
따로 만들었다 — 기존 것을 고쳐서 두 역할을 다 시키려 하지 않았다.

**딸려 나온 것 — idempotency는 "같은 상태로 다시 쓰기"보다 넓게 잡아야
한다**: 처음에는 "같은 runId로 같은 상태에 두 번 쓰면 이벤트가
중복되는가"를 `writeResult`를 두 번 불러 검사하려 했는데, `writeResult`
자체가 `from === to`면 아무것도 안 하는 지름길이 있어(기존 로직) 이
경로로는 이벤트 큐의 중복 방지 코드(`eventId` 해시)가 전혀 실행되지
않았다 — 방어선이 두 개 있으면 바깥쪽만 시험하고 "안쪽도 됐다"고
착각하기 쉽다. `bridge-events.recordEvent`를 직접 두 번 불러(다른
Bridge 프로세스가 같은 전이를 동시에 쓰는 레이스를 흉내냄) 안쪽 방어선
자체를 따로 검사해야 했다.

### M-35. 라이브 서버를 재시작하지 않고도 시작 스크립트를 검증할 수 있다 — 대체 포트 실측 (2026-08-09, T1-54)

스케줄러를 새로 등록해야 했는데, `start-bridge.ps1`이 실제로 동작하는지

동작하는가"에 대한 근거로 충분했다 — health check 200·현황판 200·

아님). 실측으로 확인한 뒤에도 원래 실행 중이던 worker는 방해받지

**교훈**: "라이브 서비스를 재시작해야 검증할 수 있다"는 항상 참이
아니다. 포트를 환경변수로 분리해 둔 서비스라면 **대체 포트에서 같은

검증할 때 이미 썼던 방법과 같은 원리다.

### M-36. "E: 드라이브 28.9GB 여유"는 대안이 아니었다 — 인증서 전용 탈착식 USB였다 (2026-08-09/10, T1-55)

**교훈**: 디스크 공간을 "다른 드라이브로 옮기면 된다"고 판단하기
전에 **그 드라이브가 내장인지·탈착식인지·파일시스템이 무엇인지·이미
무엇이 들어 있는지**를 반드시 확인한다. 여유 GB 숫자만으로는 그
드라이브가 안전한 목적지인지 알 수 없다.

### M-37. "커밋했다"만으로는 안전하지 않다 — 브랜치 자체가 GitHub에 없을 수 있다 (2026-08-10, T1-56)

**겪은 일**: 재부팅 전 안전 점검(T1-56)에서 `git log`로 최근 커밋이
잘 쌓여 있는 것을 보고 안심할 뻔했다. 그런데 `git rev-parse
--abbrev-ref --symbolic-full-name @{u}`가 "no upstream configured"를
반환했고, `git branch -r --contains HEAD`가 **빈 결과**였다 — 현재
브랜치(`agents/claude-chatbot-integration`) 자체가 **한 번도 GitHub에
푸시된 적이 없었다.** 최근 커밋 2개(`35b1ea5`·`0df5dae`, T1-30·T1-37의
산출물 — bridge/를 처음 git에 넣은 그 커밋들)가 이 디스크 하나에만
있었다.

**교훈**: "커밋됐다"와 "GitHub에 있다"는 다른 질문이다. 로컬
`git log`만 보면 항상 안전해 보인다 — 진짜 확인해야 하는 것은
①`@{u}`로 업스트림이 설정돼 있는가, ②`git branch -r --contains HEAD`로
그 커밋을 포함하는 원격 브랜치가 실제로 있는가, ③`git rev-list
--left-right --count origin/<브랜치>...HEAD`로 얼마나 앞서 있는가다.
디스크가 하나뿐인 환경(`PROJECT_MEMORY` M-36 — 이 PC는 물리 디스크가
1개뿐)에서는 이 확인이 특히 중요하다 — **디스크가 손상되면 git
저장소 전체가 사라지고, 로컬 전용 커밋은 그 순간 영구히 사라진다.**

**그래서**: 재부팅·PC 교체 등 디스크 위험이 있는 작업 전에는 `git
log`가 아니라 위 세 명령으로 **원격과의 실제 관계**를 확인한다.
커밋·푸시 자체는 이 프로젝트의 표준 절차(사람이 명시적으로 요청할 때만
실행)를 따르되, "지금 로컬에만 있는 것이 무엇인지"는 항상 사실로
보고한다 — 사람이 그 사실을 보고 커밋·푸시 여부를 판단할 수 있어야
한다.

### M-38. 이 세션 환경에서는 `git push`가 애초에 안 된다 — 인증 프롬프트가 막혀 있다 (2026-08-10, T1-59)

**겪은 일**: M-37이 남긴 로컬 전용 커밋 2개(`35b1ea5`·`0df5dae`)를
"안전하면 GitHub에 올리라"는 지시를 받고 확인해보니, `credential.helper
= manager`(Windows Git Credential Manager)가 설정돼 있지만 **캐시된
자격 증명이 없었다.** `git push --dry-run`·`git credential fill` 둘 다
`fatal: Cannot prompt because user interactivity has been disabled` /
`terminal prompts disabled`로 실패했다 — 이 세션(비대화형 자동화
환경)은 GCM의 로그인 팝업을 띄울 수 없다. `git ls-remote`(읽기)는
공개 저장소라 인증 없이 성공했지만, push(쓰기)는 구조적으로 불가능했다.

**교훈**: "안전하면 push, 아니면 로컬 백업"이라는 판단은 **보안
판단이기 전에 기술적 가능 여부 확인이 먼저다.** 비대화형 세션에서는
credential.helper가 있어도 캐시가 비어 있으면 push 자체가 실행될 수
없다 — 이걸 확인하지 않고 "위험해 보여서 안 했다"고 적으면 부정확한
보고가 된다. `git push --dry-run`(또는 `git credential fill`)로 먼저
가능 여부를 실측하고, 그 결과를 그대로 보고한다.

**그래서**: 로컬 전용 커밋을 안전하게 보존해야 하는데 push가 막혀
있으면 **`git bundle create`**(브랜치 전체 이력을 파일 하나로,
`git bundle verify`·다른 경로에 clone+checkout까지 해서 복원 가능함을
실측 검증)와 **로컬 안전 태그**(`git tag backup/...`, 기존 커밋을
가리키기만 하고 새 내용을 커밋하지 않음 — 브랜치 삭제·reset 실수에도
태그가 별도로 그 커밋을 붙잡아 둔다)를 저장소 **바깥** 경로에 만드는
것으로 대체했다(`T1-59`, 상세: `PROJECT_STATE.md` §해당 절).
미커밋·미추적 변경(106~108건)은 **`git stash`를 쓰지 않았다** —
stash는 작업트리에서 변경분을 실제로 제거하므로(되돌릴 수는 있지만)
"원본 작업트리를 최대한 건드리지 않는다"는 요구와 어긋난다. 대신
`git diff`/`git diff --cached`로 patch 파일을 뜨고, 미추적 파일은
원본을 그대로 복사(파일시스템 copy, git 명령 아님)해 별도 폴더에
모았다 — 원본 파일은 단 1바이트도 바뀌지 않는다. 복사 직후 해시
비교로 100% 일치를 확인했고, 시간이 지나 재확인했을 때 살아있는
백그라운드 프로세스(CTO Worker)가 계속 갱신하는 상태 파일 3~4개만
해시가 달라졌다 — **이건 백업 실패가 아니라 그 파일들이 원래
실시간으로 바뀌는 운영 상태값이라는 뜻**이다(하트비트 등). 정적인
작업 산출물(코드·문서·결과 JSON 대부분)은 전부 일치했다.

### M-39. 로컬 API(4100)를 기본값(`WEB_URL`)으로 띄우면 로컬 Web(3100)에서 CORS로 막힌다 — 게다가 `NEXT_PUBLIC_API_URL`을 안 넣고 띄운 Web은 조용히 원격(4000)을 부른다 (2026-08-09, T1-62)

**겪은 일**: 사용자가 `http://localhost:3100/image-studio`를 열었는데

이미지가 200으로 정상 반환돼(`Content-Type: image/jpeg`, 565KB) 데이터

원인은 **둘이 겹쳐 있었다**(둘 중 하나만 고치면 여전히 안 됨):

1. **`NEXT_PUBLIC_API_URL` 미설정 → 조용히 원격(4000)으로 나간다.**

   `NEXT_PUBLIC_API_URL=http://localhost:4100` **없이** 띄우면 컴파일된

   "http://localhost:4000"`이 그대로 박혀 **로컬 이미지 ID를 원격

2. **`apps/api/.env`의 `WEB_URL="http://localhost:3000"`이 고정값이라
   3100에서 오는 요청이 CORS로 막힌다.** `apps/api/src/main.ts`가
   `app.enableCors({ origin: process.env.WEB_URL ?? "http://localhost:3000",
   credentials: true })`로 **단일 origin만** 허용한다. 로컬 API(4100)를
   `WEB_URL` 없이(즉 기본값 3000으로) 띄우면, 실제 데이터가 있고
   404가 아니어도 **브라우저가 응답의 `Access-Control-Allow-Origin:
   http://localhost:3000`이 요청 출처(3100)와 다르다고 판단해 fetch
   결과를 JS에 넘기지 않는다.** `curl`은 CORS를 검사하지 않으므로 이
   문제를 **절대 재현하지 못한다** — `curl -H "Origin: ..."`으로 응답
   헤더값을 직접 눈으로 비교해야만 잡힌다.

**확인 방법(재현 가능한 방법)**: `curl -D - <API_URL>/... -H "Origin:
http://localhost:3100"` 으로 받은 `Access-Control-Allow-Origin` 헤더가
요청에 보낸 `Origin`과 같은 문자열인지 직접 비교한다. 다르면(예:
3000이 찍히는데 실제 브라우저는 3100) 데이터가 있어도 브라우저에서는
막힌다. 클라이언트 번들의 실제 값은 `.next/static/chunks`를 통으로
grep하면 **여러 세대의 캐시된 청크가 섞여 있어 헷갈린다** — 반드시
그 순간 서버가 실제로 내려준 HTML(`curl .../image-studio`)에 적힌
`/_next/static/chunks/...` 경로만 골라 그 청크를 **다시 살아있는
서버에서 curl로** 받아 확인한다(디스크에 남은 오래된 파일이 아니라).

**그래서**: 로컬 Web(3100)/로컬 API(4100) 쌍을 띄울 때는 **반드시
둘 다** 맞춰야 한다.

```
로컬 API   PORT=4100 WEB_URL=http://localhost:3100 node apps/api/dist/main.js
로컬 Web   NEXT_PUBLIC_API_URL=http://localhost:4100 npx next dev --port 3100
```

`docs/DEVELOPMENT_ENVIRONMENT.md` §4-2·§9는 `PORT=4100`/포트 3100만
언급하고 `WEB_URL`·`NEXT_PUBLIC_API_URL`을 명시하지 않아 이전 세션들이
브라우저로 실제 열어보지 않고 `curl` 응답이나 코드 리뷰만으로
"정상"이라 적어 왔다(`docs/PROJECT_STATE.md`에 "브라우저에서 실제로
확인하지 않았다"가 반복 등장하는 이유이기도 하다). 이번에 §4-2를
갱신해 두 값을 명시했다.

### M-40. `next dev`로 사람 검증 서버를 띄우면, 동시 진행 중인 다른 Bridge 세션의 편집이 그 자리에서 화면에 반영된다 (2026-08-10, T1-63)

**겪은 일**: "Image Studio가 열 때마다 다른 상태로 보인다"는 요청을
조사하다가, 이 워크트리는 여러 Bridge 세션이 동시에 파일을 계속
고치는 곳이라는 사실(M-28)과 `next dev`의 성질이 겹치는 것을
확인했다. `next dev`는 요청이 들어올 때 그 시점 소스 파일을
다시 컴파일한다 — 즉 사람이 검증하는 도중 **다른 세션이 관련
없는 파일을 고쳐도** 새로고침하면 다른 화면이 나올 수 있다. 실제로
이 작업 도중에도 T1-62 세션이 같은 3100/4100을 실시간으로 재기동하고
`scripts/start-verify-studio.ps1`(이 작업이 막 만든 파일)까지 직접
고쳐 넣는 것을 겪었다 — 같은 워크트리·같은 포트를 다루는 동시
세션은 파일뿐 아니라 **떠 있는 프로세스 자체**도 서로 대체할 수
있다.

**그래서**: 사람이 반복 검증하는 동안 켜 두는 서버는 `next dev`가
아니라 **`next build` + `next start`(프로덕션 빌드)** 로 띄운다.
빌드 시점의 코드가 정적 산출물로 굳어지므로, 그 이후 다른 세션이
소스를 고쳐도 이미 뜬 서버의 응답은 바뀌지 않는다 — 최신 코드를
보려면 다시 빌드해서 띄워야 한다(의도한 동작). `scripts/
start-verify-studio.ps1`(T1-63)이 이 방식을 쓴다.

**딸려 나온 것 — Windows PowerShell 5.1은 BOM 없는 UTF-8 `.ps1`의
한글 주석을 잘못 읽어 실제 구문 오류를 만든다**: 새 `.ps1` 파일을
한글 주석과 함께 작성했더니 `Unexpected token '}' in expression or
statement` 오류가 났다 — 오류가 가리키는 줄 번호의 실제 내용(Read
도구로 본 것)과 PowerShell이 읽은 내용(`Get-Content`로 재확인)이
달랐다. 원인은 인코딩이었다 — BOM이 없으면 Windows PowerShell 5.1은
시스템 기본 코드페이지(이 PC에서는 CP949)로 스크립트를 읽어, UTF-8
한글 주석이 깨지면서 **주석과 다음 줄의 코드가 한 줄로 합쳐졌다.**
`[System.IO.File]::WriteAllText(path, content, (New-Object
System.Text.UTF8Encoding($true)))`로 BOM을 명시적으로 붙이자 정상
파싱됐다. **그래서**: 한글 주석이 들어간 `.ps1`을 새로 쓸 때는 반드시
UTF-8 BOM을 붙인다 — 저장 후 파일의 첫 3바이트가 `EF BB BF`인지
확인한다.

### M-42. pnpm 콘텐츠 주소 저장소는 하드링크로 여러 프로젝트에 걸쳐 있다 — "저장소를 다른 드라이브로 옮긴다"는 착각하기 쉽다 (2026-08-10, T1-74)

**겪은 일**: C: 공간을 확보하려고 pnpm 전역 저장소(`store-dir`,

다른 링크가 남아 있으면 실제 데이터가 사라지지 않는다 — 즉 저장소
디렉터리를 C:에서 지운다고 그만큼 C: 여유공간이 정확히 늘어나는

하드링크가 퍼져 있어, 그 데이터를 실제로 D:로 옮기려면 그
`node_modules`들을 전부 다시 설치해야 한다 — 이번 작업이 확인하지
않은(못한) 소비자까지 건드리는 범위가 된다.

**그래서**: 기존 저장소(0.79GB)는 C:에 그대로 두고, `pnpm config
set store-dir D:\... --global`로 **앞으로 새로 받는 패키지만** D:에
쌓이도록 설정만 바꿨다. "지금 있는 것을 옮긴다"와 "앞으로 생기는
것의 위치를 바꾼다"는 하드링크로 연결된 데이터에서는 다른 작업이다
— 후자만 안전하게 지금 할 수 있었다. 기존 저장소를 실제로 정리하고
싶으면, 이 PC의 다른 프로젝트들이 pnpm install 중이 아닌 시점에
사람이 `pnpm store prune` 이후 직접 지운다(`docs/RECOVERY_GUIDE.md`
§9-4에 이미 있던 안내와 같은 절차 — 이번에도 "다른 Bridge 세션이
없는 시점에"라는 조건은 그대로 유효하다).

### M-43. Prisma의 `{ not: "X" }`는 nullable 필드에서 null 행을 걸러내 버린다 (2026-08-10, T1-75)

**겪은 일**: 상세페이지가 Image Studio에서 선택한 이미지를 쓰게 하면서,
INFO(라벨·포장지 등)로 분류된 사진은 제외하려고 `photoType: { not:
"INFO" }`를 썼다. 로컬 Benchmark(베란다 호스)로 실제 호출해 보니 이미
선택돼 있던 HERO 이미지 3장이 **0장으로 보였다** — 원인은 Gemini가 생성한
이미지는 애초에 `photoType` 분류(STEP 3은 원본 업로드 사진만 분류한다)를
거치지 않아 거의 항상 `null`인데, SQL의 `column != 'INFO'`는 `NULL`에
대해 참/거짓이 아니라 **알 수 없음**이 되어 그 행 자체가 결과에서
빠져버린 것이었다.

**그래서**: "null도 안전하게 허용하고 특정 값만 제외"하고 싶으면
`{ not: X }` 한 줄로 줄이지 않고 `OR: [{ field: null }, { field: "허용값" }]`
처럼 **허용하는 값을 명시적으로 나열**한다. `Image.photoType`처럼 "null =
안전한 기본값으로 취급한다"는 스키마 주석이 있는 필드일수록 이 함정에
걸리기 쉽다 — null이 사실상 가장 흔한 값이기 때문이다.

**교훈**: nullable 필드에 `not` 필터를 쓸 때는 **실제 데이터로(유닛
테스트의 가짜 값이 아니라, 로컬 Benchmark처럼 이미 사람이 만들어 둔
null 값이 섞인 실 데이터로) 한 번 직접 호출해 확인한다.** 이번에도
유닛 테스트(mock)만으로는 이 결함이 드러나지 않았고, 로컬 API를 실제로
띄워 실측했을 때에만 발견됐다.

### M-44. 엔진이 "자동으로 고른 값"은 실제로 저장되는지 별도로 확인해야 한다 (2026-08-10, T1-77)

**겪은 일**: `product-profile-engine.ts`의 STEP 5b는 호출자가 `templateKey`를
안 주면 내부적으로 기본값을 써서 렌더링은 정상으로 보였다. 그런데
`prisma-product-profile-run.store.ts`의 `markSuccess`(실행 성공 시 DB에
쓰는 지점)는 그 "실제로 쓴 값"을 저장하지 않고, `start()` 시점에 받은
**요청 값**(대부분 `null`)만 그대로 두고 있었다 — 즉 DB에는 "무엇을
요청했는지"만 남고 "실제로 무엇이 쓰였는지"는 남지 않았다. 템플릿이
고정 기본값 하나("basic")일 때는 이 차이가 겉으로 드러나지 않았지만,
기본값이 제품마다 달라지는 자동 선택 로직으로 바뀌자(T1-77) 이 결함이
실질적인 버그가 됐다 — 나중에(`getFinalPage`) 같은 실행을 다시 조립할
때 "처음 렌더링에 실제로 쓴 템플릿"을 알 방법이 없어 다른 템플릿으로
갈라질 수 있었다.

**그래서**: 엔진/서비스가 "입력값이 없으면 내부에서 알아서 기본값을
쓴다"는 구조를 만들 때는, **그 결정된 값을 결과 객체(반환 타입)에도
명시적으로 담아야** 저장 계층이 "무엇을 실제로 했는지"를 잃지 않는다.
"기본값을 쓴다"와 "그 기본값이 무엇인지 기록에 남긴다"는 다른 일이다
— 후자를 빠뜨리면 재현성이 조용히 깨진다.

**같이 확인한 것 — 동시 진행 Bridge 세션과의 충돌 회피(M-28의 재확인)**:
이 작업 도중 T1-75가 `product-profile-engine.ts`·
`product-profile.service.ts`·`packages/shared/src/index.ts`를 실시간으로
같이 고치고 있었다. `bridge-cli.mjs status`가 `IN_PROGRESS`인 동안은
그 파일들을 건드리지 않고 **겹치지 않는 새 파일(모듈)만 만들어 두었다가**,
T1-75가 `READY_FOR_REVIEW`로 바뀐 뒤에야 딱 필요한 지점만 최소로
연결했다 — mtime을 주기적으로 재확인해 "아직 그 세션이 살아 있는지"를
추측이 아니라 실측으로 판단했다. M-28이 처음 관찰했던 위험이 이번에도
똑같이 재현됐고, 같은 회피 전략이 다시 통했다.

### M-45. "다시 해 볼 가치가 있는 실패"의 상한은 실패 종류와 무관하게 항상 같은 곳에서 세야 한다 (2026-08-10, T1-79)

**겪은 일**: `recordFailure`(`bridge-executor.mjs`)는 Claude Code 호출
자체가 명시적으로 오류를 던졌을 때만 시도 횟수(`attempts`)를 세고
`nextAfterFailure`로 상한(`MAX_RUN_ATTEMPTS`, 기본 2회)을 적용해 사람에게
넘겼다. 그런데 `recoverAbandonedRuns`(서버 재시작·프로세스 종료로
심장박동이 끊긴 "버려진 실행"을 대기열로 되돌리는 경로)는 **같은 종류의
"다시 해 볼 가치가 있는 실패"인데도 시도 횟수를 전혀 세지 않았다** —
근본 원인(예: 그 작업이 실행될 때마다 항상 죽는 환경 문제)이 반복되면,
매번 사람 몰래 대기열로 되돌려지기만 하고 아무도 원인을 못 본다. 두
실패 경로가 **같은 목적(무한 반복 방지)을 가진 같은 판정 함수
(`nextAfterFailure`)를 하나는 쓰고 하나는 안 쓰는** 어긋남이었다.

**그래서(T1-79)**: 진단 계층(`bridge-diagnostics.mjs`)이 버려진 실행·
TESTING 검증 실패 두 경우 모두에 **같은 `nextAfterFailure`·
`MAX_RUN_ATTEMPTS`**를 적용하도록 만들었다 — 새 상한을 발명하지 않고,
이미 검증된 것을 재사용했다. "무한 반복하지 않는다"는 원칙은 실패가
어디서 왔는지(명시적 오류 vs 조용한 소실)와 무관하게 **하나의 판정
기준**으로 지켜야 한다는 교훈이다 — 같은 성격의 문제를 서로 다른
코드 경로가 각자 판단하게 두면, 나중에 한쪽만 고치고 다른 쪽을
잊는다.

**딸려 나온 것 — `resetToRequested`는 `attempts`를 보존하지도, 늘리지도
않는다**: `resetToRequested`가 대기열로 되돌릴 때 지우는 필드
목록(`cleared`)에 `attempts`가 없어 기존 값은 보존되지만, 그 값을 새로
계산해 넣는 것은 **호출하는 쪽의 책임**이다(`recordFailure`가 이미
그렇게 하고 있었다 — `updateResult`로 `attempts`를 먼저 갱신한 뒤
대기열로 되돌린다). 진단 계층도 같은 순서(먼저 `updateResult`로
`attempts` 기록 → `resetToRequested`)를 따라야 했다 — 순서를
바꾸면(예: `resetToRequested`만 부르고 attempts는 나중에) 이번 시도의
횟수가 기록되지 않고 사라진다. 검사(`bridge-diagnostics.spec.mjs`)가
이 순서를 지키지 않았을 때 실제로 실패해서 잡아냈다.

### M-46. Bridge가 부른 세션은 자신을 낳은 bridge-server를 재시작할 수 없다 — 추정이 아니라 자기 PID로 증명됨 (2026-08-11, T1-46)

M-26·M-30·T1-44 §8-7·T1-51·T1-54가 반복해서 "이 세션이 그 서버의
자식 프로세스일 위험이 있어 재시작하지 않았다"고 적어 왔다. 전부
**추정**이었다 — 실제로 자기 프로세스 계보를 추적해 증명한 적은
없었다.

**겪은 일(T1-46)**: `Get-CimInstance Win32_Process`로 이 세션(T1-46
실행) 자신의 부모 체인을 끝까지 추적했다.

```
nohup.exe → node bridge/bridge-server.mjs(포트 4200)
  → claude.exe(이 세션)
```

**이 세션 자신이 라이브 bridge-server의 직계 자식임을 실측으로
확인했다.** `bridge-executor.mjs`를 다시 읽어 보니 `callClaude`가

재시작하면 이 작업이 나중에 결과를 내놓아도 그것을 받아 적을

**그래서**: 라이브 4200/4201의 실제 재시작은 Bridge가 부르지 않은
사람의 터미널에서만 안전하다 — "안전한 시점을 잘 골라야 한다"가
아니라 **Bridge 세션 내부에는 안전한 시점이 구조적으로 존재하지
않는다.** 앞으로 이 재시작을 요청받는 어떤 Bridge 작업도 같은 결론에
도달할 것이므로, 매번 새로 재보지 않고 이 사실을 그대로 인용해도
된다. 대신 대체 포트(4210/4211, 4212/4213 등)에 임시 인스턴스를
띄워 새 코드를 검증하는 것으로 충분한 대체 확인이 된다(T1-54·T1-46이
이미 두 번 실증).

### M-49. "등록만 되고 트리거된 적 없다"와 "실제로 트리거됐고 실패했다"는 완전히 다른 위험이다 (2026-08-11, T1-56 재실행)

**겪은 일**: T1-46·T1-54·T1-56이 반복해서 "`ACOS-Bridge` 작업
스케줄러는 등록만 됐고 실제 트리거로 검증된 적이 없다"고 기록해
왔다. 이번 재확인에서 `Get-ScheduledTaskInfo ACOS-Bridge`가
`LastRunTime 2026-08-11 10:09:09 · LastTaskResult 1(실패)`을
돌려줬다 — **처음으로 실제 트리거·실제 실패 증거**가 나왔다.
`(Get-CimInstance Win32_OperatingSystem).LastBootUpTime`이 그보다
훨씬 이른 2026-08-10 14:05로 나와, 재부팅이 원인은 아니었다(로그온
트리거 또는 수동 호출로 추정, 원인 자체는 Task Scheduler 이벤트
로그에 기록이 없어 미확인).

**중요한 이유**: "검증된 적 없음"은 위험이 있는지 **모른다**는
뜻이고, "트리거됐고 실패함"은 위험이 **있다는 것을 안다**는
뜻이다 — 둘은 완전히 다른 확신 수준이다. 지금까지의 낙관적 판정
("등록은 됐다, PASS(부분)")은 실제 트리거 시 성공한다는 것을
증명하지 못했다.

**그래서**: 재부팅 자동 복구 스케줄러를 "등록 확인 = 안전"으로
취급하지 않는다. 등록 여부와 무관하게 **재부팅 후에는 반드시 사람이
`http://localhost:4201` 응답을 직접 확인**하고, 안 뜨면
`bridge\start-bridge.ps1`을 사람이 직접(대화형 터미널에서) 다시
실행해야 한다는 지침을 `docs/RECOVERY_GUIDE.md`에 명시했다. **실행
로그 자체가 남지 않아 원인 규명이 불가능한 것도 발견**했다 —
`start-bridge.ps1`이 실패 원인(서버 미기동인지 터널 타임아웃인지)을
파일로 남기지 않아, 다음에 같은 실패가 나면 이번에도 원인을 알 수
없다. 이건 `bridge/` 내부 스크립트를 고치는 일이라 이번 세션은
손대지 않고 사실만 남긴다. [[M-46]]

N개씩 중복돼 보인다"는 증상이 됐다 — 상태(선택 개수)가 늘어난 만큼
화면 반복이 그대로 늘어나는 구조였다.

**고친 방식**: 백엔드 API·`CategoryPanel`/`DetailPagePanel` 컴포넌트
자체는 그대로 두고(T1-88의 선택→상세페이지 연결 로직 보존), 상위
컨테이너만 바꿨다 — 선택된 사진이 여러 장이면 "작업 중인 사진 1장"을
고르는 탭을 추가하고, 카테고리 후보·상세페이지 패널은 **활성 사진
1장 분만** 렌더링한다(`key`에 `activeId`를 포함해 탭 전환 시 완전히
새로 불러오게 함 — 이전 사진의 로컬 UI 상태가 남아 보이는 것을
막는다). 즉 "선택 상태"와 "그 상태를 보여주는 화면 블록 수"를
분리했다 — 선택은 여러 장, 화면은 한 번에 하나.

**앞으로 참고할 점**: `.map()`으로 선택된 항목 배열을 순회하며 그
안에 무거운 하위 워크플로우 전체(생성·확인·조립)를 반복 렌더링하는
패턴을 새로 추가할 때는, 선택 개수가 늘어나면 화면도 그만큼
반복되는지 미리 따져 본다. 반복이 뜻이 있는 목록(예: 썸네일 그리드)
이라면 괜찮지만, 반복되는 것이 "여러 단계로 이어지는 하나의
작업 흐름"이라면 탭/전환 방식으로 바꿔 한 번에 하나만 보이게 하는
편이 사람이 이해하기 쉽다. [[M-49]]

### M-52. "로그인 화면이 뜬다"는 증상이 항상 웹 라우트 가드는 아니다 — Image Studio는 화면은 열리는데 쓰기 버튼마다 401이 나는 구조였다 (2026-08-12, T1-90)

**겪은 일**: "`/image-studio`에 로그인 문제가 있다"는 요청을 받아
먼저 `apps/web`에 `middleware.ts`나 페이지 단위 로그인 리다이렉트가
있는지부터 찾았는데 **없었다** — `image-studio` 화면 자체는 처음부터
로그인 여부를 검사하지 않았고, `curl`로도 `GET /image-studio`는
항상 200이었다. 진짜 막힌 지점은 화면이 아니라 **API 쪽 전역
쓰기 가드**(`write-protection.guard.ts`, TASK-0802)였다 — 이 화면이
호출하는 `/image-gen/*` 쓰기 엔드포인트(사진 재생성·선택)에
`@Public()`이 없어서, 화면은 뜨지만 **버튼을 누르는 순간마다** 401을
받는 구조였다.

**앞으로 참고할 점**: "로그인 문제"라는 보고를 받으면 웹 쪽
라우트/리다이렉트만 보고 "로그인 검사가 없으니 문제 없다"로
결론짓지 않는다 — 화면이 열려도 그 화면이 호출하는 **쓰기 API가
전역 인증 가드에 걸리는지**를 반드시 같이 확인한다. 이 프로젝트는
전역 `WriteProtectionGuard`(APP_GUARD)가 모든 POST/PATCH/PUT/DELETE에
기본 EDITOR 이상을 강제하고, 예외는 컨트롤러/핸들러 단위
`@Public()`로만 뚫려 있다(`docs/architecture/auth.md`) — 원인을
추측하지 말고 실제 API 응답 코드(401 vs 다른 오류)로 확인한다.

### M-53. "사진이 안 보인다"가 반복 재발한 진짜 이유 — WEB_URL이 "설정 안 됨"이 아니라 "3000으로 고정 설정됨"이었다 (2026-08-12, T1-95)

**겪은 일**: T1-62·T1-81·T1-91이 이미 세 번 같은 증상("Image Studio
사진 미표시")을 조사했고, 매번 "코드는 정상, 로컬 API를 WEB_URL=
http://localhost:3100으로 띄우면 해결된다"는 같은 결론에 도달했다.
그런데도 며칠 뒤 사람이 다시 같은 증상을 보고했다(T1-95). 이번에
`apps/api/.env`를 직접 열어보니 `WEB_URL="http://localhost:3000"`이
**명시적으로 박혀 있었다** — "환경변수를 안 정했다"가 아니라
"운영/SSH-터널용 3000으로 고정해 뒀다"였다. `main.ts`의 CORS
설정(`origin: process.env.WEB_URL ?? "http://localhost:3000"`)은
값이 하나만 있으면 그 값 하나만 허용하므로, 누군가 로컬 API(4100)를
`scripts/start-verify-studio.ps1` 없이(예: `pnpm --filter api dev`)
그냥 띄우면 항상 3100이 막혔다 — 매번 "이번엔 스크립트로 고쳤다"고
끝났지만, 다음에 스크립트를 거치지 않고 띄우면 원인 자체가 그대로
남아 있어 재발했다.

**한 일**: 근본 원인을 코드로 없앴다 — `apps/api/src/main.ts`가
`WEB_URL`을 쉼표로 구분된 **여러 출처**로 파싱하도록 바꾸고,
`WEB_URL`이 아예 없을 때의 기본값도 `["http://localhost:3000",
"http://localhost:3100"]` 둘 다로 넓혔다. 이 PC의 실제
`apps/api/.env`와 `.env.example` 둘 다 `WEB_URL="http://localhost:3000,
http://localhost:3100"`으로 갱신했다. 이제 WEB_URL을 한 번도 안
건드리고 로컬 API를 띄워도(스크립트를 거치든 안 거치든) 3000(SSH
터널)·3100(로컬 검증) 둘 다 CORS를 통과한다 — 임의 출처(`evil.
example.com`)는 여전히 막힘을 curl로 확인했다.

**앞으로 참고할 점**: "환경변수를 빠뜨렸다"류의 버그를 조사할 때는
`.env`가 **비어 있는지**뿐 아니라 **다른 값으로 고정돼 있는지**도
확인한다. 같은 증상이 서로 다른 세션에서 "코드는 정상, 이번에
환경을 맞춰 고쳤다"로 세 번 이상 반복되면, 그 "환경을 맞추는 절차"
자체를 코드가 매번 자동으로 만족하도록 바꾸는 것이 맞다 — 사람이
매번 같은 스크립트를 기억해 실행하는 것에 의존하면 언젠가 다시
빠진다.

§14, T1-63/T1-92/T1-97 등 여러 세션이 "`admin@acos.local`/`admin1234`로
`POST /auth/login`이 401난다"고 반복 기록해 왔다(비밀번호가 문서와
다르다고 추정, 원인 미확인, 범위 밖이라 손대지 않음이라고 판단해 옴).
이번 세션(2026-08-13)이 같은 계정·같은 비밀번호로 실제로 로그인을
시도하니 **200과 유효한 토큰이 돌아왔다.** 언제·어떻게 정상화됐는지는
확인하지 못했다(비밀번호를 되돌린 세션이 있었을 수도, 애초에 일시적
문제였을 수도 있다) — 다음 세션은 이 계정이 여전히 401이라고 가정하고
바로 우회 경로(NestJS 서비스 계층 직접 호출 등)로 넘어가지 말고, 먼저
직접 로그인을 시도해 실측해야 한다.

**PATCH 검증 시 겪은 인코딩 함정 (재사용할 점검법)**: `curl -d '{...한글...}'`
처럼 셸 인용부호 안에 한글을 직접 넣어 PATCH 요청을 보내면, 이 워크트리의
Git Bash 환경에서 서버가 받는 바이트가 깨질 수 있었다(응답 JSON의 한글이
mojibake로 보임). 파일로 payload를 만들어 `curl --data-binary @file.json`
으로 보내니 정상 왕복했다 — **한글이 포함된 요청 바디를 curl로 실측할
때는 인라인 `-d`보다 파일 기반 payload를 우선한다.** 서버·DB 자체의
인코딩 문제가 아니라 이 셸의 인자 전달 문제였다(실제 앱은 브라우저
`fetch()`로 JSON을 보내 이 문제와 무관하다).

### M-55. `setx`로 설정한 환경변수는 "새 프로세스"라고 다 받는 게 아니다 —
그 프로세스를 낳은 조상이 언제 떠 있었는지가 기준이다 (2026-08-13, T1-100)

**겪은 일**: §17(T1-84, 2026-08-12)이 `TURBO_CACHE_DIR`·
`PLAYWRIGHT_BROWSERS_PATH`·`TEMP`·`TMP`를 전부 `setx`로 D:에
영구 설정하고 실측까지 검증했는데, 하루 뒤(2026-08-13) C: 여유공간이
**0.03GB**(사실상 0)까지 다시 떨어졌다. 원인을 추적하니 Turborepo
캐시가 `D:\dev-data\turbo-cache`가 아니라 다시
`Documents\GitHub\-\.turbo\cache`(C:, 3.22GB)에 쌓여 있었다.

**직접 실측으로 확인한 원인**: 이번 세션이 새로 띄운 PowerShell
프로세스(`setx` 이후 시각에 시작됨)조차 `$env:TURBO_CACHE_DIR`이
빈 값이었다. **"프로세스가 새로 시작됐다"는 것과 "그 프로세스가
`setx` 이후의 환경을 본다"는 것은 다른 얘기다** — Windows에서 자식
프로세스는 부모가 물려준 환경 블록을 그대로 복사(`CreateProcess`)할
뿐, `HKCU\Environment`를 다시 읽지 않는다. `setx`는 레지스트리만
갱신하고 `WM_SETTINGCHANGE`를 브로드캐스트하지만, 이를 실제로
재조회해 반영하는 것은 탐색기 등 일부 프로그램뿐이다. **`setx` 시점
이전부터 계속 떠 있던 조상 프로세스(이 경우 이 세션을 최종적으로
실행시키는 호스트, 그리고 `bridge/bridge-cto-worker.mjs`처럼 상시
실행되는 Bridge 프로세스)의 자손들은, 그 자손이 언제 새로 스폰됐든
전부 옛 환경을 그대로 물려받는다.**

**그래서**:
1. `setx`로 개발 캐시 경로를 바꾼 뒤 "검증 실행 하나"로 잘 되는 것을
   확인해도, **그 검증 프로세스 자신이 이미 옛 환경을 물려받은 트리
   안에 있었다면 통과가 오히려 착시일 수 있다** — 확인할 때는
   `$env:VARNAME`을 직접 찍어 실제로 새 값이 보이는지 먼저 확인한다.
2. 자동화(Bridge·예약 작업)가 실행하는 빌드에 `setx` 캐시 경로를
   확실히 반영하려면, **그 자동화를 띄우는 최상위 프로세스 자체가
   재시작되어야 한다** — PC 재부팅이 가장 확실하고, 그게 아니면
   해당 자동화 프로세스(여기서는 `ACOS-Bridge`·`ACOS-CTO-Worker`
   스케줄러가 띄우는 프로세스)를 사람이 직접 내렸다 다시 띄워야
   한다. **무인 세션 자신이 자신을 낳은 프로세스를 재시작할 수는
   없다** — `bridge-cto-worker`나 `bridge-server`를 이 세션이
   재시작하면 M-30·T1-46(§3-3-1)이 이미 실측한 것과 같은 이유로
   이 세션 자신의 결과 보고가 유실될 위험이 있다.
3. 재부팅을 기다릴 수 없는 검증(이번 세션의 build/typecheck/lint/test
   재현이 그 예)은 **PowerShell 명령 안에서 `$env:VARNAME = '...'`을
   직접 설정해 그 호출 범위에서만 우회**한다 — 저장소 설정
   (`turbo.json` 등)에는 손대지 않는다.

**딸려 나온 교훈**: "메모리 부족"이 실은 디스크 문제였던 M-30과 같은
종류다 — **증상(캐시가 D:에 안 쌓인다)의 원인이 "설정이 틀렸다"가
아니라 "설정은 맞는데 적용 시점이 아직 안 왔다"일 수 있다.** 설정
자체(레지스트리 값)와 그 설정이 실제로 살아있는 프로세스에 전파됐는지는
**따로 확인해야 하는 별개의 사실**이다.

### M-56. PowerShell `[ordered]@{}`를 정수를 키로 인덱싱하면 값을 잃는다 (2026-08-13, T1-103)

**겪은 일**: `scripts/check-acos-environment.ps1`(신규 진단 스크립트)
에서 포트 번호를 키로 하는 `[ordered]@{ 3000 = "설명" }`을 만들고
`foreach ($p in $ports.Keys) { $ports[$p] }`로 값을 꺼냈더니 **항상
빈 문자열**이 나왔다. `$ports.Item(3000)`으로 직접 불러도
`"Index was out of range. Must be non-negative and less than the
size of the collection."` 오류가 났다 — 마치 존재하지 않는 인덱스에
접근한 것처럼 실패했다.

**원인**: `[ordered]@{}`가 만드는 타입은
`System.Collections.Specialized.OrderedDictionary`이고, 이 타입은
인덱서를 **두 개** 갖고 있다 — `this[object key]`(키로 값 찾기)와
`this[int index]`(몇 번째 항목인지, 위치로 값 찾기). 키를 정수로
쓰면(`3000 = "..."`), 나중에 `$ports[3000]`처럼 정수 인자로 인덱싱할
때 PowerShell의 메서드 오버로드 해석이 **위치 접근 쪽을 선택**한다
— 항목이 2개뿐인 딕셔너리에서 인덱스 3000을 찾으니 범위를 벗어난다.
`$ports.GetEnumerator()`로 직접 순회하면 키·값이 멀쩡하게 나와서
더 헷갈렸다(딕셔너리 자체는 정상, 인덱서 문법만 문제).

**그래서**: 정수처럼 보이는 값(포트 번호 등)을 `[ordered]@{}`·
`@{}`의 키로 쓸 때는 **반드시 문자열로 감싼다**(`"3000" = "..."`).
값을 꺼낼 때 포트를 다시 정수로 써야 하면(`Get-NetTCPConnection
-LocalPort`) `[int]$key`로 그 자리에서만 변환한다.

**교훈**: PowerShell 해시테이블/정렬된 딕셔너리는 "키가 문자열이든
숫자든 상관없이 동작한다"고 가정하기 쉽지만, **정수 키 + 정수 인자
인덱싱의 조합만 예외적으로 다른 동작(위치 접근)을 한다.** 새 스크립트를
쓸 때 값이 조용히 비거나 "범위 초과" 오류가 나면, 인덱서가 예상한
오버로드로 해석되고 있는지 `GetEnumerator()`로 원본을 먼저 눈으로
확인한다.

## M-56 — T1-105: `ACOS-Bridge` 재부팅 실패의 진짜 원인은 환경변수가
아니라 `Start-Process` 리다이렉션 버그였다 (2026-08-13)

**사건**: `ACOS-Bridge` 예약 작업이 재부팅마다 `LastTaskResult=1`로
실패하는 문제가 §16(T1-56)부터 §19(T1-102)까지 여러 세션에 걸쳐
"등록은 정상이지만 실제 성공은 확인된 적 없음"으로만 남아 있었고,
유력 가설은 "S4U/Limited 예약 작업 컨텍스트에서 `$env:LOCALAPPDATA`·
`$env:USERPROFILE` 같은 사용자 환경변수가 깨진다"였다.

이 세션(T1-105) 시작 직전에 **실제 재부팅이 있었고**(그 흔적이 아직
남아 있어 실측 가능했다), 그 재부팅에서도 `ACOS-Bridge`는 다시
실패했다. 같은 S4U/Limited 컨텍스트로 임시 진단용 예약 작업을 만들어
환경변수를 직접 덤프해 보니 **`LOCALAPPDATA`·`USERPROFILE`·`TEMP`
전부 정상이었다** — 가설이 반박됐다. 대신 스크립트를 코드로 추적해
보니, cloudflared를 띄우는 `Start-Process` 호출이
`-RedirectStandardOutput`과 `-RedirectStandardError`에 **같은 파일
경로**를 주고 있었다. PowerShell의 `Start-Process`는 이 조합을 그
자리에서 `InvalidOperationException`으로 거부한다(`"...are same.
Give different inputs..."`) — 직접 재현해서 확인했다. 스크립트
맨 위 `$ErrorActionPreference = "Stop"` 때문에 이 예외가 스크립트
전체를 죽였고, cloudflared.exe는 단 한 번도 실행되지 못한 채
`LastTaskResult=1`로 끝났다.

**그래서**: `bridge/start-bridge.ps1`의 cloudflared 실행 부분에서
stdout/stderr을 서로 다른 파일로 분리했다(`cloudflared-bridge.out.log`
/ `.err.log`, `D:\dev-data\logs`로 이동). 요청이 명시적으로 요구한
하드닝(경로 절대화)도 함께 적용했다 — 원인은 아니었지만 안전망으로
남겨 둘 가치가 있다고 판단했다.

**교훈**:
1. **"환경변수 문제일 것"이라는 여러 세션에 걸친 누적 가설도 실제로
   재현·반박해 보지 않으면 그대로 굳어진다.** §18~19가 다른 맥락
   (이미 떠 있는 프로세스의 env 미전파)에서 실측한 진짜 문제가, 전혀
   다른 맥락(새로 스폰되는 예약 작업)에도 같은 원인일 거라고 성급하게
   일반화됐다 — 새 컨텍스트마다 다시 실측해야 한다.
2. **PowerShell `Start-Process`는 `RedirectStandardOutput`과
   `RedirectStandardError`에 같은 파일을 허용하지 않는다** — 콘솔에서
   대화형으로 실행하면 이 조합의 에러가 눈에 바로 띄지만, 예약
   작업(창 없음, 로그를 따로 보지 않는 한)에서는 그냥 조용히
   `LastTaskResult`만 실패로 남고 원인이 전혀 보이지 않는다. 로그를
   두 스트림으로 합치고 싶으면 **한쪽만 리다이렉트하거나, cmd.exe로
   감싸서 `> file 2>&1`을 쓰거나, 두 파일로 분리한 뒤 나중에 합친다.**
3. **재부팅이 우연히 세션 시작 직전에 일어나 있으면 그 흔적(살아있는
   프로세스의 `CreationDate`·타임스탬프가 남은 로그 파일)이 최고의
   실측 증거다** — 이번에는 실제로 재부팅을 실행하지 않고도(요청이
   금지) 그 직전 재부팅의 실패를 그대로 부검할 수 있었다.
4. **살아있는 정상 서비스를 재현 검증 때문에 죽이지 않는다** — 같은
   S4U/Limited 컨텍스트로 **별도의 임시 진단용 예약 작업**을 만들어
   격리 검증하면, 실제 `ACOS-Bridge`/`ACOS-CTO-Worker`나 지금 떠 있는
   Bridge 서버·cloudflared를 전혀 건드리지 않고도 예약 작업 실행
   컨텍스트(S4U/Limited/특정 계정)를 그대로 재현해 검증할 수 있다.
   검증이 끝나면 임시 작업은 바로 등록 해제하고 로그도 지운다.

**미확인**: 이번 수정이 **실제 재부팅에서** `LastTaskResult=0`을
내는지는 아직 검증되지 않았다(요청에 따라 재부팅을 실행하지
않았음) — 다음 재부팅에서 사람이 확인해야 한다. `ACOS-CTO-Worker`가
같은 재부팅에서 처음으로 실패한 것(코드 `0x800710E0`)도 원인
미확인 — 이번 작업 범위(`ACOS-Bridge`만) 밖이라 조사하지 않았다.

## M-57 — T1-107: Claude Code 프로세스가 재시작돼도 "대화"는 복구되지
않는다 — Task 단위 복구는 이미 `bridge/tasks`·`bridge/results`가 하고
있었다 (2026-08-13)

**사건**: Bridge가 Claude Code를 헤드리스로 부르는 방식
(`bridge/bridge-executor.mjs`의 `buildClaudeArgs`)을 실측했다.
`claude.exe`는 `-c/--continue`·`-r/--resume [sessionId]`·
`--session-id <uuid>`를 공식 지원하고, 실행할 때마다
`~/.claude/projects/<이 저장소 경로를 정규화한 폴더명>/<session-id>.jsonl`에
전체 대화 transcript를 남긴다(실측: 이 워크트리에 대응하는 폴더 안에만
`.jsonl` 파일이 100개 넘게 쌓여 있었다). 하지만 **Bridge는 이 세
옵션 중 어느 것도 넘기지 않는다** — `buildClaudeArgs`는 매번
`-p <prompt> --output-format stream-json ...`만 넘기고 세션 ID는
어디에도 기록하지 않는다. 게다가 이 폴더는 taskId별로 나뉘지 않고
**이 저장소 경로 전체가 공유**한다 — 서로 다른 taskId(지금 이 순간도
T1-106과 T1-107이 동시에 실행 중)가 같은 폴더에 파일을 뒤섞어
쌓으므로, `--continue`("현재 폴더의 가장 최근 대화")로는 어느
`.jsonl`이 어느 taskId의 것인지 알아낼 방법이 없다.

**그래서**: "Claude Code가 재시작돼도 이전 작업을 이어간다"는
**자연어 대화의 복구가 아니라 파일 기반 상태 복구**로만 가능하다고
결론지었다. 새 저장소를 만들지 않고 이미 있는 것을 그대로 썼다 —
`bridge/tasks/<taskId>.json`(지시 원문)·`bridge/results/<taskId>.json`
(state·heartbeatAt·changedFiles·testResults·blockedOn·decisionNeeded)이
사실상 이미 "체크포인트"였다. 이 둘과 git 상태·장기기억 문서를 정해진
순서로 읽어 요약해 주는 **읽기 전용** 스크립트
(`scripts/bootstrap-context.mjs`)만 추가했다 — 아무 파일도 쓰지 않고
아무 Task도 실행하지 않는다. 상세 절차는 `docs/RECOVERY_GUIDE.md` §11.

**교훈**:
1. **공식 기능이 있다고 실제로 쓰이고 있는 것은 아니다** — `--resume`은
   `claude.exe` 자체에는 있지만, 이 프로젝트의 무인 실행 경로(Bridge)는
   그것을 쓰지 않는다. "가능한 것"과 "지금 이 시스템이 실제로 하는
   것"을 구분해야 한다(`AGENTS.md` §0 Source of Truth와 같은 원칙).
2. **`heartbeatAt` 기준 5분(`ABANDON_LIMIT_MS`, `bridge/bridge-executor.mjs`)이
   지난 `IN_PROGRESS`/`TESTING` 작업은 프로세스가 죽었을 가능성이
   크다** — 실제로 `bootstrap-context.mjs`를 돌려 보니 T1-45·T1-55·
   T1-56·T1-87·T1-91 다섯 건이 수백~수천 분째 `TESTING`에 멈춰
   있었다(전부 이번 작업 이전부터 있던 것, 이번에 손대지 않았다).
   Bridge 서버가 재시작되면 `recoverAbandonedRuns()`가 이런 작업을
   자동으로 `REQUESTED`로 되돌리지만, **그 후에도 자동으로
   재실행하지는 않는다** — 여전히 CTO/사람이 taskId를 지정해야 한다.
3. **지금 이 프로세스 자신이 어느 taskId인지는 프로세스 스스로 알 수
   없다** — Bridge가 taskId를 자식 프로세스의 환경변수로 넘기지
   않기 때문이다(`claudeSpawnOptions`에 커스텀 env가 없음, 실측).
   세션은 자신을 부른 프롬프트에 적힌 taskId만 신뢰해야 한다.

**교훈 하나 더**: `.vscode/`는 `.gitignore`로 완전히 제외돼 있어

PC·디스크 교체 시 사람이 직접 다시 만들어야 하는 목록

Claude/개발환경이 사용자에게 별도로 직접 알려주는 기능이 있었다"는
지시를 받고, T1-106과는 다른 채널(현황판 자동 열기 이외의 것)이
과거에 실제로 동작한 적이 있는지 처음부터 다시 조사했다. Windows
toast·소리(`Console.Beep`)·`BurntToast`·`msg.exe`·SAPI 음성·
브라우저 `Notification()` API를 이 저장소 전체(`git log --all`
전체 이력 포함, node_modules 제외)에서 대소문자 구분 없이 검색했으나
**단 한 건도 나오지 않았다** — T1-106의 결론과 독립적으로 같은
결과에 도달했다. `bridge/start-bridge.ps1`·`bridge/start-cto-worker.ps1`
둘 다 `-WindowStyle Hidden`으로 자식 프로세스를 띄워, 콘솔 창이
떠 있어서 사람이 우연히 로그를 보는 경로도 없다(실측, 재부팅
자동복구 스케줄러도 같은 방식으로 실행됨).

이 저장소 역사에서 "현황판과 별개로 사람에게 직접 신호를 보낸다"는
목적으로 실제로 설계·구현된 것은 `bridge/bridge-push-gateway.mjs`
(T1-53, Push Gateway) **하나뿐**이었다. 사용자 보고 큐(T1-51)에
새 사건이 생길 때마다 `PUSH_WEBHOOK_URL` 환경변수에 등록된
Slack·Discord·ntfy.sh 같은 외부 웹훅으로 실제 HTTP POST를
보내는 구조다(`bridge/README.md` §2-3에 "휴대폰의 Slack 알림"을
예로 명시). **그런데 `PUSH_WEBHOOK_URL`은 T1-53이 이 코드를 만든
2026-08-09부터 지금(2026-08-13)까지 단 한 번도 설정된 적이
없다** — `node bridge/bridge-cli.mjs push-gateway status`로
직접 재확인한 결과 큐에 쌓인 103건이 전부 `unconfigured`이고
`sent`는 0건이었다. 즉 이 채널은 "고장 났다"가 아니라
**"설계는 됐지만 목적지 주소를 아무도 넣은 적이 없어 한 번도
작동한 적이 없다"**가 정확한 상태다.

**그래서**: 사람이 기억하는 "직접 알림"이 실제로 이 저장소 코드
경로를 통해 온 것이라면, 그 경로는 논리적으로 Push Gateway 하나뿐일
수밖에 없다 — 하지만 실제로 배달된 기록이 전혀 없으므로 사람이
그 알림을 이 경로로 받았을 가능성은 없다. 남은 설명은 ChatGPT
대화 세션이 스스로 사람에게 먼저 말을 건 것(이 저장소 밖, CTO
쪽 행동)이거나, 사람의 기억이 현황판 자동 열기(T1-106이 고친 것)와
섞였을 가능성 정도다 — 둘 다 이 저장소 코드로 확인·복구할 수 있는
대상이 아니다.

**교훈**: "예전에 됐었다"는 사람의 기억을 코드로 재현하려 할 때는,
그 기억과 정확히 대응하는 코드 경로가 있는지뿐 아니라 **그 경로가
실제로 한 번이라도 끝까지 실행된 증거(배달 로그·감사 기록)가
있는지**까지 확인해야 한다. 코드가 존재한다는 사실만으로 "이게
그것이었겠다"고 단정하면, 한 번도 켜진 적 없는 기능을 "복구"라는
이름으로 잘못 연결하게 된다.

## M-60 — T1-109: "등록돼 있다"와 "재부팅 때 실제로 성공한다"는
Bridge뿐 아니라 CTO Worker도 마찬가지였다 — Boot 트리거 자체가
구조적으로 취약하다 (2026-08-13)

**사건**: T1-109(재부팅 후 ACOS 전체 개발환경 자동복구 통합
시스템)를 시작하며 `Get-ScheduledTaskInfo`로 이번 세션 시작 직전
실제 재부팅(2026-08-13 12:45:45)의 결과를 실측했다. 그동안
`ACOS-CTO-Worker`는 "재부팅 시 자동 성공"의 대표 사례로
문서화돼 있었다(`docs/DEVELOPMENT_ENVIRONMENT.md` §3-3,
`docs/RECOVERY_GUIDE.md` §9-5) — 그런데 이번 재부팅에서는
`ACOS-Bridge`(이미 알려진 문제, T1-105가 원인 규명·수정)뿐 아니라
**`ACOS-CTO-Worker`도 `LastTaskResult = 2147946720`
(0x800710E0, "The operator or administrator has refused the
request")로 실패**했다. 실제로는 그 뒤 4200/4201/CTO Worker가
전부 살아 있었으므로(이번 세션이 직접 포트·PID로 확인), 실패한
스케줄러 실행 이후 **누군가 수동으로 살렸다**는 뜻이다 — 자동
복구가 스스로 성공한 게 아니었다.

**분석**: `bridge/start-cto-worker.ps1`은 `$ErrorActionPreference
= "Stop"`인 채로 최상위(무한 루프 바깥)에 `try/catch`가 없다.
`Start-Process -FilePath "node" ...`는 `node`를 PATH에서 찾는데,
Boot 트리거(로그온 이전에 발동)는 사용자 프로필이 아직 완전히
로드되기 전이라 PATH가 일부만 채워졌을 가능성이 있다 — 이 경우
`Start-Process`가 터미네이팅 오류를 던지고, 그 오류는 아무 데도
잡히지 않은 채 최상위로 전파돼 supervisor 스크립트 전체가 죽는다.
`bridge/start-bridge.ps1`이 T1-105에서 찾은 것과 겉보기 증상은
다르지만(리다이렉션 예외 vs 추정상 PATH 문제), **"Boot 트리거가
사용자 프로필이 준비되기 전에 실행돼 그 시점에만 실패한다"는
성격은 같다.** 다만 이번에는 `bridge/`(사람 승인 없이 수정 금지)
안의 파일이라 **가설을 코드로 확정하지는 않았다** — T1-105처럼
격리 재현까지 하지 않고, 정황 증거(에러 코드·타이밍·PATH 의존
코드 위치)만으로 판단했다.

**그래서**: `bridge/start-cto-worker.ps1`·`start-bridge.ps1`
내용을 고치는 대신(범위 밖), 저장소 밖(`scripts/`)에 **새
Scheduled Task(`ACOS-Recovery-Manager`)를 Logon 트리거 + 45초
지연**으로 추가했다 — 두 기존 Boot 트리거 작업이 먼저 시도할
시간을 준 뒤, 이미 살아있는 것은 절대 건드리지 않고 죽은 것만
`Start-ScheduledTask`(1차)·`start-cto-worker.ps1`/
`start-bridge.ps1` 직접 재호출(2차 fallback)로 되살린다. Logon
트리거는 사용자 프로필이 이미 로드된 뒤 발동하므로 PATH 문제가
구조적으로 재발하지 않을 가능성이 높다 — 다만 **이 판단도 다음
실제 재부팅으로 최종 확인해야 한다**(이번 세션도 재부팅을
실행하지 않았다).

**Bridge(4200/4201)를 재시작하는 것이 위험하다**는 기존 원칙
(`docs/DEVELOPMENT_ENVIRONMENT.md` §3-3-1)을 그대로 지키면서도
자동 복구를 만드는 방법: **"이미 health check가 정상이면 절대
건드리지 않고, health check가 실패했을 때만 재시작한다."** health
check가 실패했다는 것 자체가 "이 프로세스를 살려주는 부모가 이미
없다"는 뜻이므로, 그 순간 재시작하는 것은 이 스크립트를 호출한
프로세스 자신을 죽일 위험이 없다 — "재시작 여부"를 안전 판단
기준으로 삼으면 별도의 "내가 그 프로세스의 자손인가" 탐지 로직
없이도 구조적으로 안전해진다. 이 원칙을 `scripts/
acos-recovery-manager.ps1`에 적용해 실제로 라이브 Bridge(4200/4201)
·CTO Worker·로컬 API/Web(4100/3100)이 이미 정상인 상태에서 두
번 연속 실행해 PID가 전혀 바뀌지 않음을(재시작 시도 자체가 없었음)
직접 실측했다.

**교훈**: "재부팅 자동 복구가 등록돼 있다"는 사실은 "다음 재부팅에
실제로 성공한다"는 보장이 아니다 — Boot 트리거는 사용자 프로필이
준비되기 전에 실행된다는 구조적 취약점을 공유하므로, 하나의
스케줄러가 과거에 성공 이력이 있다고 해서 다음에도 성공한다고
단정하면 안 된다. Bridge처럼 "안전 재시작이 어려운" 대상은, 매번
직접 재시작을 시도하는 대신 **"이미 정상이면 SKIP, 실패했을 때만
ACT"** 형태의 idempotent 감시자를 별도로 두는 편이 원본 스크립트를
고치는 것보다 안전하다 — 특히 그 원본이 사람 승인 없이 수정 금지
대상(`bridge/`)일 때는 더욱 그렇다.

### M-61. "실제 사진이 있는가"와 "그 사진을 지금 화면에 그리는가"는 서로 다른 질문이다 — 하나의 필드로 합치면 다른 규칙이 오작동한다 (2026-08-13, T1-118)

**겪은 일**: Product Story 렌더러(`product-story-html.ts`)가 Hero
배경으로 쓴 사진을 그 사진이 원래 배정된 섹션 본문에서도 또
그리고 있었다(요청 사양이 명시적으로 금지한 "상단/본문 이미지
중복"). 고치려고 처음에는 "Hero로 쓰인 섹션은 `image: null`로
치환"하는 가장 단순한 방법을 썼다. 그런데 기존 테스트 2건이 그
자리에서 깨졌다 — "실제 제품 사진이 있는 섹션에는 Gemini 보조
그래픽(aux visual)을 절대 그리지 않는다"는 별도 규칙이 `image`
필드 하나로 "사진이 있는가"를 판단하고 있었는데, 그 필드를
`null`로 치환해 버리자 이 규칙이 "사진이 없다"고 오판해 Hero로
쓰인 섹션에 보조 그래픽이 잘못 끼어들었다.

**그래서**: "이 섹션에 실제 배정된 사진이 있는가"(사실, 다른 여러
규칙의 근거가 됨)와 "그 사진을 지금 이 자리에 그릴 것인가"(순수한
렌더링 결정, 중복 방지 같은 표시 규칙)를 처음부터 별개의 값으로
설계해야 한다. 하나의 `null`/존재 여부로 두 가지 뜻을 동시에
표현하면, 그 필드를 참조하는 다른 모든 규칙이 "표시 여부"가 아니라
"존재 여부"를 원했는지 하나하나 다시 확인해야 한다. 실제 수정은
`image`(존재, 원래 의미 그대로 유지) + `hideMedia`(표시 여부, 새
불리언)로 분리해 해결했다 — `showMedia = Boolean(image) &&
!hideMedia`를 화면 표시 판단에만 쓰고, `image`는 그대로 aux-visual
억제·`imageRole` 관련 다른 검사에 계속 쓰인다.

**교훈**: 회귀 테스트가 있었기 때문에 이 상호작용을 배포 전에
잡을 수 있었다 — "테스트 통과는 배선이 맞다는 뜻이지 결과가 좋다는
뜻이 아니다"(M-9)의 반대 방향 교훈이기도 하다: 기존 테스트가
실패하면 테스트를 고치기 전에 **왜 실패하는지 먼저 이해**해야
한다. 이번엔 테스트가 옳았고 구현이 두 개념을 섞은 것이 원인이었다.

### M-63. REQUESTED로 오래 대기 중인 것은 "안 도는 버그"가 아니라 설계다 — 그리고 heartbeat 경합이 정상 종료 직전 작업을 통째로 되돌릴 수 있다 (2026-08-13, T1-121)

**겪은 일 하나 — T1-116이 26분째 REQUESTED로 방치돼 있었다**: 사장님이
"REQUESTED/runnable=True인데 워커가 재실행하지 않는다"고 지적한 것을
그대로 실측했다. `bridge/bridge-cto-worker.mjs`의 `runTick`을 코드로
확인한 결과, CTO Worker는 **`REQUESTED` 작업을 스스로 집어 실행하지
않는다** — 하는 일은 ① `/signal` 큐 소비(총괄이 taskId를 콕 집어
지시한 것만) ② 선례가 있는 `BLOCKED`/`DECISION_NEEDED`를
`autoContinue`가 켜졌을 때만 자동 재개, 이 둘뿐이다. 즉 "누군가
`/run`이나 `/signal`로 다시 지시하지 않으면 `REQUESTED`는 영원히
그대로"인 것이 **의도된 설계**이지 결함이 아니다 — 대기가 길어 보이면
"왜 안 도나요"로 사람에게 되묻는 대신, 최신 Task가 이미 그 요구사항을
흡수했는지부터 확인해야 한다(이번 경우 실제로 T1-118이 흡수해
`supersede`로 정리했다).

**겪은 일 둘 — T1-116 자신이 정상 종료 직전에 통째로 되돌아갔다**:
`bridge/results/T1-116.json`을 보면 Claude Code 실행은 09:46~10:00
사이 정상적으로 끝까지 돌았다(`outputBytes` 106만 바이트,
`lastOutputAt` 10:00:12). 그런데 최종 결과는 `state: REQUESTED`이고
`blockedOn`에 `"실행 중 오류: REQUESTED → TESTING 로는 갈 수
없습니다"`가 남아 있었다. 코드로 추적한 원인: `bridge-executor.mjs`의
`executeTask`가 `callClaude` 완료 후 `state: "TESTING"`으로
`updateResult`를 쓰는 순간(781행), 같은 시각 **동시에 실행 중이던 다른
taskId(T1-117~120, 09:46:29~42 사이 모두 시작)** 중 하나가 자신의
`startNextTask` 호출 맨 앞에서 부른 `recoverAbandonedRuns()`가 T1-116을
"버려진 실행"으로 오판해 먼저 `REQUESTED`로 되돌려 놓았다(`abandonedRun`은
`heartbeatAt`이 5분 넘게 갱신 안 되면 버려졌다고 본다 — 5개의 동시
`claude.exe`가 같은 디스크에 결과 파일을 계속 쓰며 경합하는 동안
T1-116의 30초 heartbeat 타이머(`beat()`)가 몇 차례 못 쓰였을 가능성이
크다, `updateResult` 실패는 조용히 삼켜진다). 그 직후 T1-116 자신의
`state: "TESTING"` 쓰기가 `REQUESTED → TESTING`(허용되지 않는 전이,
`bridge-state.mjs`의 `ALLOWED`)로 게이트에 거부돼 예외를 던졌고,
`startNextTask`의 `.catch`가 이를 `resetToRequested`로 다시 감싸며
그 오류 문구를 `blockedOn`에 남겼다(`bridge-executor.mjs:1050`).
**즉 사람이 볼 땐 "실행이 실패했다"처럼 보였지만, 실제로는 Claude
Code 실행 자체는 끝까지 정상 완료됐고 그 결과를 기록하려는 마지막
순간에 다른 프로세스의 안전장치(버려진 실행 복구)가 오작동한
것이었다** — M-24("524가 나도 작업은 안 죽었다")·M-23(state가 실제
코드 상태와 어긋날 수 있다)과 같은 계열의, "실패 메시지를 문자
그대로 믿지 않는다"는 원칙이 다시 확인된 사례다.

**이번에 하지 않은 것**: `bridge/`는 사람 승인 없이 수정 금지 대상이라
이 경합 자체(heartbeat 타이머와 다른 프로세스의 abandon 판정 사이의
레이스)는 코드로 고치지 않았다 — 이 항목에 원인과 증거를 남겨 다음에
`bridge/` 변경이 승인될 때 참고하게 한다.

**그래서**:
1. `REQUESTED`로 오래 대기 중인 작업을 보면 "재실행이 안 되는 버그"로
   단정하지 않는다 — CTO Worker의 자동 재개 범위(신호·선례 있는
   BLOCKED/DECISION_NEEDED)에 원래 들지 않는 정상 대기일 수 있다.
2. `blockedOn`에 상태 전이 오류 문구(`"... 로는 갈 수 없습니다"`)가
   남아 있으면, 그 taskId 자체의 결함이 아니라 **동시에 실행 중이던
   다른 작업의 복구 로직과의 레이스**를 먼저 의심한다 —
   `outputBytes`·`lastOutputAt`이 정상 종료를 가리키는데
   `blockedOn`만 전이 오류라면 이 패턴이다.
3. 이런 경우에도 사람에게 "재실행할까요"로 묻지 않는다 — 최신 Task가
   이미 그 요구사항을 흡수했는지 먼저 확인하고(이번 경우 T1-118),
   흡수했으면 `supersede`로 정리하고, 아니면 CTO가 직접
   `run <taskId>`로 다시 잇는다.
4. `node bridge/bridge-cli.mjs diagnose`(비용 없음)가 이미
   heartbeat 정지·REQUESTED 장기 대기·TESTING 정체·반복 실패·로그
   손상을 전부 판정해 준다(`bridge-diagnostics.mjs`, T1-79) — 이상
   징후를 조사할 때 새로 뭔가를 만들기 전에 이것부터 돌린다.

### M-64. "로그가 안 남는다"는 디스크 부족 하나가 아니라 두 개의 서로 다른
문제였다 — 그리고 sandbox 테스트는 새 import를 스스로 못 찾는다
(2026-08-13, T1-120)

**겪은 일 하나 — 원인이 하나가 아니었다**: "재부팅 후 CTO Worker·
Bridge 로그가 기록되지 않는다"는 요청을 그대로 파고들자 실제로는
**서로 다른 두 문제가 섞여 있었다.** ① `bridge/.worker-logs/
cto-worker.log`(고아 파일, 지금은 어떤 스크립트도 참조하지 않음)에는
실제 `ENOSPC: no space left on device, write`가 남아 있어 "C: 공간
부족"이 그럴듯한 설명처럼 보였다. ② 하지만 정작 지금도 쓰이는
Bridge 서버(4200)·현황판(4201) 자신의 stdout/stderr은 **애초에
`bridge/start-bridge.ps1`이 `Start-Process`에 리다이렉트 인자를 한
번도 준 적이 없어서** 디스크 공간과 무관하게 처음부터 아무 데도
남지 않고 있었다. T1-105가 cloudflared 리다이렉션 버그를 고쳤을 때
"Bridge 서버·현황판도 같은 패턴이니 이미 되어 있겠지"라고 넘겨짚었으면
이 공백을 놓쳤을 것이다 — **증상이 하나여도 원인이 여럿일 수 있고,
"근처 코드가 고쳐졌으니 여기도 됐겠지"는 확인이 아니다.**

**겪은 일 둘 — sandbox 테스트가 새 import를 스스로 못 찾는다**:
`bridge-io.mjs`에 `import { logTaskTransition } from
"./bridge-ops-log.mjs"`를 추가하자, `bridge/*.spec.mjs` 10개 파일이
전부 `ERR_MODULE_NOT_FOUND`로 깨졌다. 원인은 이 스펙 파일들이
`bridge-events.spec.mjs`와 같은 패턴으로 **진짜 저장소를 건드리지
않도록 매번 임시 디렉터리에 정해진 모듈 목록(`MODULES` 배열)만
`cpSync`로 복사해서 그 안에서 도는 구조**였기 때문이다 — 소스
디렉터리 전체를 복사하는 것이 아니라 하드코딩된 파일 목록이라,
새 파일을 추가하고 기존 파일이 그것을 import하게 만들면 그 파일도
목록에 넣어야 한다. `npx eslint .`나 `tsc`는 이 누락을 잡지 못한다
(문법·타입 오류가 아니라 런타임 파일 시스템 문제라서) — **`node
--test bridge/*.spec.mjs`를 실제로 돌려 보지 않았다면 이 회귀를
놓치고 "완료"로 보고했을 것**이다. `pnpm turbo run test`는 이
`bridge/*.spec.mjs` 파일들을 아예 실행하지 않는다(turbo 파이프라인은
`apps/`·`packages/`만 본다) — bridge/ 내부를 고칠 때는 turbo 검증
4종만으로는 부족하고 이 독립 스펙 스위트를 반드시 별도로 돌려야 한다.

**겪은 일 셋 — 동시에 다른 세션이 같은 문서·같은 문제 영역을 건드리고
있었다**: 이 작업 도중 `docs/PROJECT_STATE.md`를 Edit하려다
"File has been modified since read" 오류를 받았다 — 다시 읽어보니
동시에 실행 중이던 T1-121이 이미 그 자리를 갱신해 놓은 상태였다.
또한 `bridge/tasks/T1-122.json`(동시 `IN_PROGRESS`)이 "Bridge/CTO
Worker 상태를 D:\dev-data 영속 로그에 남기되, 이미 T1-120에서
구현 중이면 중복 구현하지 말라"고 명시하고 있었다 — 이번 작업의
산출물(`bridge/bridge-ops-log.mjs`·`task-state.log`의 형식)을
문서에 명확히 남겨야 T1-122가 다시 조사하지 않고 그대로 확장할 수
있다는 뜻이다.

**그래서**:
1. "로그가 안 남는다"류 문제는 원인을 하나로 단정하지 않는다 —
   디스크 공간·리다이렉트 유무·경로(C:/D:) 세 축을 각각 따로
   확인한다. 비슷한 이전 수정(T1-105)이 있었다고 해서 인접한
   프로세스도 같은 방식으로 고쳐졌을 것이라 넘겨짚지 않는다.
2. `bridge/` 안의 어떤 `.mjs` 파일이 새 파일을 import하게 만들면,
   `bridge/*.spec.mjs`의 sandbox `MODULES` 목록에도 그 파일을
   추가해야 한다 — 잊으면 lint·typecheck는 통과하지만 스펙 스위트
   전체가 깨진다. 이 스위트는 `pnpm turbo run test`에 포함되지
   않으므로 `node --test bridge/*.spec.mjs`를 **직접** 돌려야 잡힌다.
3. 동시에 여러 taskId가 같은 워크트리·같은 공유 문서를 건드릴 수
   있다는 전제(M-63과 같은 계열)로, 문서 Edit이 "modified since
   read" 오류를 내면 덮어쓰지 않고 다시 읽어 최신 내용 위에 이어
   붙인다. 겹치는 후속 작업(T1-122 같은)이 있으면 내가 만든
   모듈·경로·형식을 결과에 명확히 적어 재조사 없이 확장할 수 있게
   한다.

### M-65. "계약만 만들어 두고 실제 호출은 미룬다"는 결정은 위험이

**그래서**: "계약/스캐폴딩만 만들고 실제 연결은 미룬다"는 기록을
만나면, 그 결정의 **이유가 지금도 유효한지** 확인한다(동시 진행
작업이 끝났는지, 스키마 충돌 위험이 실제로 남아 있는지). 이유가
사라졌는데 코드가 그대로라면, 새 요청이 그 자리를 정확히 가리키고
있을 가능성이 크다 — "이미 누가 만들어 놨을 것"이라는 짐작과
"실제로는 계획만 있고 아무도 안 이었다"는 사실은 다르다(`grep`으로
그 함수/타입을 실제로 호출하는 곳이 있는지 직접 확인해야 안다).

**실제 API 호출 검증에서 배운 것 — Story 전체 재실행보다 그 함수만
직접 호출하는 것이 더 정확하고 싸다**: 처음에는 Benchmark Product
Story를 통째로 다시 생성해 보조 그래픽이 만들어지는지 확인하려
했는데, 이번 실행에서는 마지막 섹션이 `closing`(감성적 마무리)으로
분류돼 보조 그래픽 대상(`text-only`/`feature-highlight`)에서 애초에
제외됐다 — LLM이 만드는 Story 구조는 매번 달라서, 특정 레이아웃이
나오도록 실행을 강제할 수 없다. 그래서 `image-gen.service.ts`가
실제로 쓰는 것과 동일한 `GeminiImageProvider` 클래스를 컴파일된
`dist/`에서 직접 가져와 `edit({prompt, images: []})`를 1회 호출하는
것으로 배선(같은 클래스·같은 메서드·같은 인자 형태)을 검증했다 —
"운 좋게 그 레이아웃이 나올 때까지" 전체 파이프라인을 반복 재실행해
비용을 쌓는 것보다, **실제로 같은 코드 경로를 직접 호출하는 좁은
검증**이 더 정확하고(레이아웃 우연성에 좌우되지 않음) 더 싸다
(`docs/PROJECT_MEMORY.md` "API 비용 최소화"와 같은 원칙).

**딸려 나온 것 — 이 워크트리의 로컬 검증 서버(3100/4100)와 Playwright
e2e의 `webServer`가 같은 포트를 두고 경합한다**: `pnpm turbo run
test`(web) 실행 시 `scripts/start-verify-studio.ps1`이 이미 3100을
점유하고 있으면 Playwright는 그 자리에서 바로 중단한다("이미 사용
중"). 반대로 verify-studio를 내리고 Playwright가 자기 서버를 띄운
채로 두면, 브라우저 확인용 3100이 사라진다 — **둘을 동시에 만족할 수
없다.** 이번에는 "e2e 실행 → verify-studio 재기동" 순서로 풀었지만,
근본적으로는 같은 포트를 쓰는 두 스크립트가 공존할 수 없는 구조적
제약이다(`scripts/start-verify-studio.ps1`의 포트를 바꾸거나
Playwright 설정에 `reuseExistingServer`를 쓰는 것은 이번 작업 범위인
Product Story 아트디렉션과 무관해 손대지 않았다).

### M-66. `GIT_TERMINAL_PROMPT=0` 없이 push/credential 호출을 자동화하면 조용히 무한 대기한다 (2026-08-14, T1-130)

**겪은 일**: T1-59가 "이 세션에서는 GitHub 인증이 안 된다"고 이미
적어 두었지만, **왜 안 되는지(에러가 나는지, 멈추는지)는 실측하지
않았었다.** 이번에 `git push --dry-run`·`git credential fill`을
그대로 실행해 보니 **에러 없이 20초 넘게 응답이 없었다** — Git
Credential Manager(`credential.helper=manager`, 이미 설정됨)가
캐시된 자격 증명을 못 찾자 대화형(브라우저/기기 코드) 로그인 흐름을
시도하며 조용히 대기하고 있었다. timeout으로 강제 종료해야만
멈췄다.

`GIT_TERMINAL_PROMPT=0`을 환경변수로 주면 같은 명령이 **즉시(1초
미만)** `fatal: could not read Username … terminal prompts
disabled`로 실패한다 — 원인이 정확히 "대화형 프롬프트 시도"였음을
확정하는 증거다.

**그래서**: 비대화형(Bridge·스케줄러·CI) 컨텍스트에서 실행되는 모든
git 네트워크 호출(`push`·`credential fill`·`fetch` 등 자격 증명이
필요할 수 있는 명령)에는 **항상 `GIT_TERMINAL_PROMPT=0`을 준다.**
이게 없으면 자동화 스크립트 하나가 재부팅마다·스케줄러 주기마다
멈춘 프로세스를 계속 쌓을 수 있다 — "인증이 안 된다"보다 "인증
시도가 멈춰서 프로세스가 쌓인다"가 훨씬 위험한 실패 모드다(M-26
"조용히 멈추는 것이 가장 위험하다"와 같은 종류). `scripts/
git-task-sync.mjs`는 이 환경변수에 더해 Node `spawnSync`의

### M-67. `git status --porcelain`은 새 미추적 디렉터리를 그 안의 파일들이 아니라 디렉터리 자체로 뭉쳐서 보여준다 (2026-08-14, T1-130)

### M-71. `gpt-image-2`는 투명 배경을 지원하지 않는다 — "깨진 아이콘"은

### M-72. "선택 상태"는 파이프라인을 업그레이드해도 저절로 따라오지 않는다
— `selected`와 "사람이 명시적으로 확정했다"는 서로 다른 두 개의 사실이라
따로 기록해야 한다 (2026-08-18, T1-155)

**겪은 일**: T1-154가 발견한 문제 — T1-150(GPT Image 2 전환)·T1-153
(canonical pipeline)이 코드로는 완벽하게 연결돼 있었는데도, 벤치마크
제품의 `final-html`은 몇 주 전 Gemini 시절 이미지를 계속 보여주고
있었다. 원인은 `selected:true` 필드 하나가 "지금 최종 후보인가"와
"사람이 이 선택을 최종 확인했는가"라는 두 가지 뜻을 동시에 지고 있었기
때문이다 — 새 파이프라인이 아무리 좋은 이미지를 만들어도, 그 필드를
아무도 다시 켜지 않으면 옛 이미지가 계속 "선택된 상태"로 남는다. 두
번의 큰 파이프라인 업그레이드(T1-150, T1-153) 동안 이 사실을 아무도
알아채지 못했다 — 코드 리뷰·타입체크·테스트 어느 것도 "이 필드가 낡은
상태로 멈춰 있다"는 것을 잡아내지 못한다. 그건 데이터의 신선도 문제지
코드의 정확성 문제가 아니기 때문이다.

**그래서**: 하나의 boolean(`selected`)이 지던 두 역할을 두 개의 컬럼
(`selected`·`locked`)으로 나눴다. `selected`는 여전히 "지금 최종
후보인가"만 뜻하고, 파이프라인이 스스로 갱신할 수 있다. `locked`는
"사람이 이 상태를 직접 확정했는가"만 뜻하고, 사람의 명시적 행동
(Image Studio의 select 버튼)에서만 켜진다. 자동화(새 생성물 승격)는
`locked`가 꺼져 있는 자리만 건드릴 수 있다 — 사람이 켠 `locked`는
자동화가 절대 넘지 못하는 경계선이다. 기존에 이미 `selected:true`였던
데이터는 마이그레이션으로 `locked`를 소급해서 채우지 않았다 — 그
소급 자체가 "낡은 선택을 영구히 고정"시켜 버려서, 정확히 지금 고치려는
문제를 다시 만들기 때문이다.

**더 넓은 교훈**: "사람이 확인했다"는 사실과 "지금 어떤 상태다"라는
사실을 같은 필드에 같이 담으면, 그 필드가 갱신되지 않는 순간 둘 다
거짓말을 하게 된다 — 상태는 낡았는데 "확인됨"이라는 신호는 그대로
남기 때문이다(`M-61`이 "실제 사진이 있는가"와 "지금 화면에 그리는가"를
구분해야 한다고 남긴 교훈과 같은 종류다). 자동화를 들여올 때는 항상
"이 자동화가 넘으면 안 되는, 사람만 켤 수 있는 경계 필드가 있는가"를
먼저 물어야 한다.

### M-73. Master Art Direction Contract는 "이미지용 산문"과 "렌더러용 토큰"을 같은 인터페이스에 섞으면 안 된다 (2026-08-19, T1-162)

**겪은 일**: `MasterArtDirectionContract`(T1-153)는 처음부터 있었지만
`palette`·`backgroundTreatment` 등 모든 필드가 "화이트~소프트 뉴트럴
배경" 같은 **자연어 문장**이었다. 이미지 생성 LLM에게는 완벽한
입력이지만, HTML/CSS 렌더러가 그 문장에서 실제 hex 값을 뽑아 쓸 방법이
없었다 — 그래서 세 렌더러 파일(`product-story-html.ts`·
`product-story-design.ts`·`product-story-facts-panel.ts`)이 각자
`#ffffff`·`#18181b` 같은 색을 하드코딩했고, "Master Art Direction을
renderer가 실제로 소비한다"는 말이 사실은 주석으로만 존재했다(T1-156이
이미 이 어긋남을 "우연히 같은 헥스값을 주석으로만 맞춰 놓았다"고
기록했다).

**그래서**: 같은 계약에서 **두 가지 산출물**을 따로 만든다 — 기존
프로즈 필드(이미지 생성 LLM 프롬프트용)는 그대로 두고, 새
`buildStoryVisualTokens()`(실제 hex/px/gradient 값)를 추가해 렌더러
세 곳이 전부 이 함수를 직접 호출하게 했다. 문서 조립 순서에 기대는
CSS 변수 cascade(`:root`에 심고 다른 곳에서 `var()`로 참조)는 쓰지
않았다 — `product-story-facts-panel.ts`는 Story HTML 뒤에 별도
`<section>`으로 문자열 결합되는 독립 조각이라, "누가 먼저 렌더링되는가"
에 의존하면 합쳐지는 순서가 바뀔 때 조용히 깨질 수 있다. 대신 세 곳
모두 같은 순수 함수를 각자 호출해 **항상 같은 리터럴 값**을 얻는다 —
호출 비용은 사실상 0(입력 없는 결정적 함수)이라 중복 호출을 아끼려고
캐시·주입을 설계할 필요가 없었다.

**교훈**: "제품 사진 배경"과 "그 사진을 담는 페이지 셸의 배경"은
서로 다른 레이어다 — 하나를 바꾼다고 다른 하나가 같이 바뀔 필요는
없다. 이번에 페이지 셸을 다크 네이비로 바꾸면서도 제품 사진의 스튜디오
배경(화이트~뉴트럴)은 그대로 뒀다 — 재촬영 비용·제품 동일성 위험을
피하는 가장 보수적인 선택이었다.

### M-74. `object-fit:cover`는 "제품이 잘리지 않는다"는 요구와 구조적으로 충돌한다 (2026-08-19, T1-162)

**겪은 일**: 상세페이지 렌더러(`product-story-html.ts`)는 hero·
detail-callout·split figure·gallery strip 전부 `object-fit:cover`로
고정 높이(`min-height`/`max-height`) 프레임을 꽉 채우고 있었다. 이
방식은 프레임 비율과 실제 사진 비율이 다르면 **항상 어느 한쪽을
자른다** — 세로로 긴 인물 사진을 가로로 넓은 프레임에 cover로 넣으면
얼굴이나 발이 잘리는 식이다. "제품 사진이 잘리지 않는다"는 완료
기준은 이 방식과 근본적으로 양립할 수 없었다.

**그래서**: 제품 사진이 보이는 모든 자리를 `object-fit:contain` +
프레임 배경(letterbox, 페이지 배경과 같은 그라디언트 계열)으로
바꿨다. `contain`은 절대 자르지 않는 대신 여백이 생기는데, 그 여백을
빈 공백이 아니라 프레임 배경으로 채우면 "실수로 남은 여백"이 아니라
"의도된 프레임"처럼 보인다. 실측(Chromium `getBoundingClientRect`/
`getComputedStyle`)으로 1024×1024 정사각 이미지가 640px 높이 프레임
안에 잘림 없이 들어가는 것을 확인했다.

**남긴 트레이드오프**: edge-to-edge full-bleed(이전 방식의 시각적
장점)를 포기했다 — 프레임 안에 여백이 생길 수 있다. "잘리지 않는다"가
"여백 없이 꽉 채운다"보다 우선한다고 판단한 것은 이번 요청의 명시적
완료 기준("제품 사진이 잘리지 않는다")을 근거로 한 것이지, 어느 쪽이
더 예쁜지에 대한 판단이 아니다 — 그 판단은 사람이 스크린샷을 보고
내린다(`docs/MASTER_GUIDE.md` "생성 결과의 품질은 사람이 판단한다").

### M-75. 같은 accentColor를 "텍스트로 직접"과 "채운 배지 위에 얹는 고정 텍스트"
두 자리에 동시에 쓰면, 페이지가 밝아지거나 어두워질 때 한쪽이 반드시
깨진다 (2026-08-19, T1-163)

**겪은 일**: T1-162(다크 네이비)의 `LAYOUT_VISUAL_TOKENS.accentColor`는
sky-400/teal-400 같은 밝은 톤이었다. 이 값은 두 군데서 쓰였다 —
①kicker·spec 수치·notice 라벨처럼 **페이지 배경 위에 텍스트 색으로
직접** 쓰이는 자리, ②step 번호·구성품 인덱스·feature pill처럼
**accentColor로 채운 배지 배경 위에 고정된 어두운 텍스트(`#04121a`)를
얹는** 자리. 다크 페이지에서는 둘 다 우연히 대비가 살았다 — 밝은 텍스트
on 어두운 배경(①), 밝은 배경 on 어두운 텍스트(②) 양쪽 모두 성립하는
값이었을 뿐이다. 사용자가 "화면이 너무 어둡다"고 해서 페이지 배경을
밝게 바꾸자(T1-163) ①자리가 전부 깨졌다 — 밝은 색은 밝은 배경 위
텍스트로 쓰면 대비가 무너진다.

**그래서**: "하나의 accentColor로 두 반대 방향 대비를 동시에 만족시키려
하지 않는다." 모든 accentColor를 600~700급 진한 톤으로 통일해 ①(밝은
배경 위 직접 텍스트)에서 항상 대비가 나오게 하고, ②(채운 배지 위 텍스트)
자리는 accentColor에 의존하지 않는 **별도의 고정 밝은 색 토큰**
(`StoryVisualDesignTokens.textOnAccent`)을 새로 만들어 썼다. 이러면
페이지 배경이 다시 바뀌어도(밝게↔어둡게) ①은 accentColor 톤 선택만
다시 하면 되고, ②는 애초에 페이지 배경과 무관한 자기완결적 조합(진한
accentColor 배경 + textOnAccent 고정 밝은 텍스트)이라 절대 깨지지 않는다.

**교훈**: 디자인 토큰에 "강조색 하나"만 두면 편리해 보이지만, 그 값이
쓰이는 자리가 "배경 위 텍스트"인지 "텍스트를 얹는 배경"인지에 따라
필요한 명도가 정반대다. 이 둘을 구분하지 않고 하나의 값을 공유하면,
지금 당장은 우연히 맞아도 페이지 테마가 바뀌는 순간(이번처럼 다크→라이트)
반드시 한쪽이 깨진다 — 처음 토큰을 설계할 때 "이 색이 텍스트로 쓰이는가,
배경으로 쓰이는가"를 구분해 두는 편이 나중에 팔레트를 통째로 뒤집을 때
훨씬 싸게 먹힌다.

## M-61 — T1-171: renderer만 바꾼 검증은 LLM/image-gen 재호출 없이 확인할 수 있다

**사건**: T1-171(FEATURE 섹션 타이포/아이콘/배지 개선)은 `product-story-html.ts`
렌더러 코드만 바꿨고 Story 카피(LLM)·이미지(Gemini)는 전혀 건드리지
않았다. 그런데 `/final-html`이 서빙하는 HTML은 `ProductProfile.
storyResult.html`(생성 시점에 렌더링해 저장한 문자열, M-131/T1-131)이라
**코드만 고쳐서는 화면이 갱신되지 않는다**(T1-163이 먼저 발견한 것과
같은 함정) — 갱신하려면 보통 `POST /:id/story`를 다시 호출해야 하는데,
이 호출은 매번 실 LLM 비용(+생성형 아이콘/모티프를 쓰면 image-gen
비용까지)이 발생한다(`GenerateProductStoryRequest`/`ProductStoryResultDto`
주석에 명시). 이번 작업은 "image_gen·LLM 호출 절대 금지" 요청 사양과
비용 최소화 원칙([[minimize_api_cost]] memory) 때문에 이 재호출을 피해야
했다.

**그래서**: `POST /:id/story`를 다시 부르지 않고, 그 메서드가 내부에서
쓰는 **순수 함수만** 다시 실행했다 — 이미 DB에 저장된 `storyResult.story`
(카피, 재호출 없이 읽기만 함)와 이미 선택된 실제 이미지(로컬 MinIO에서
그대로 읽기만 함, 새로 만들지 않음)를 입력으로, `assignStoryImages` →
`planStoryDesign` → `buildLeftoverMediaGallery` →
`foldLeftoverImagesIntoSections` → `renderProductStoryHtml` →
`wrapProductProfileHtmlDocument`(전부 `@acos/core`가 export하는 결정적
함수, DB/네트워크 접근 없음)를 그대로 재실행해 **바뀐 renderer 코드로만**
새 HTML을 만들었다. Nest 컨텍스트(`NestFactory.createApplicationContext`)로
`PrismaService`·`StorageService`만 빌려 썼다 — 둘 다 읽기 전용 조회다.
결과 HTML을 로컬 파일로 저장해 Playwright Chromium으로 직접 열어
확인했고, 확인이 끝난 뒤 임시 스크립트·산출물은 전부 지웠다(T1-167처럼
흔적을 남기지 않았다).

**교훈**: "렌더러 코드만 바꾼 변경"을 검증할 때 `/final-html`이 캐시를
서빙한다는 이유로 곧장 `POST /:id/story`(실 비용)를 다시 부르지 않는다
— 그 파이프라인이 나누어 쓰는 pure 함수들을 저장된 입력(카피·이미지)에
그대로 다시 먹이면 비용 없이 같은 결과를 얻을 수 있는 경우가 많다.
이 판단은 "무엇이 바뀌었는가"(카피·이미지 vs 렌더링 규칙)를 먼저
구분해야만 가능하다 — 렌더링 규칙만 바뀐 게 확실할 때만 이 방법을
쓴다(카피나 이미지 배정 자체가 바뀌는 작업이면 재호출이 맞다).

### M-76. "렌더러만 다시 실행해 확인"과 "그 결과를 캐시에 실제로 반영"은 다른 일이다 (2026-08-20, T1-172)

**사건**: [[M-61]](T1-171)은 pure 렌더 체인을 다시 돌려 새 마크업을
파일로 저장하고 브라우저로 **확인만** 했다 — `ProductProfile.
storyResult.html/css`(DB에 캐시된 값, `/final-html`이 그대로 서빙)는
건드리지 않았다. 그래서 T1-171 완료 후에도 실제 `/final-html`은 여전히
옛 pill 마크업을 보여줬다 — "코드가 맞다"와 "화면이 맞다"는 다른
질문이라는 것을 사람 검증 단계에서 다시 확인해야 했다.

**그래서**: T1-172는 M-61과 **똑같은 pure 체인**(`assignStoryImages` →
`planStoryDesign` → `buildLeftoverMediaGallery` →
`foldLeftoverImagesIntoSections` → `renderProductStoryHtml` →
`buildProductFactsPanel`)을 다시 실행하되, 그 결과를 파일로만 남기지
않고 `prisma.productProfile.update({ storyResult: {...기존값, html, css} } })`로
**DB에 실제로 다시 썼다** — `story`·`designPlan`·`validation`·
`quality`·`availableImages`·`auxiliaryVisuals`·`generativeVisuals`·
`provider`·`model`·`assetInventory` 등 렌더링과 무관한 다른 필드는
원래 저장돼 있던 값을 그대로 두고 `html`·`css` 두 필드만 덮어썼다 —
"바뀐 것만 바꾼다"는 원칙을 DB 갱신에도 그대로 적용했다.

**남긴 판단(스스로 정함, 문서 근거)**: 원래 생성 당시 실제로 생성됐던
Gemini 생성형 아이콘("check"·"info")·hero motif는 원본 bytes를 다시
구할 방법이 없다(리포트에는 `generated: true`라는 메타데이터만 있고
실제 이미지 bytes는 저장되지 않는다, `ProductStoryResultDto.
generativeVisuals`는 보고용 구조체다) — 다시 만들려면 image-gen을
호출해야 하는데 이번 작업은 그것을 명시적으로 금지했다. M-61이 이미
같은 이유로 `renderProductStoryHtml(story, assigned, designPlan)`을
generativeVisuals 인자 없이 호출했으므로, 이번에도 같은 선례를 따라
그 두 아이콘·모티프는 인라인 SVG 폴백으로 렌더링되게 두었다 — 제품
사진·asset selection과는 무관한 장식용 생성 자산이라 "제품 이미지
변경 금지" 범위 밖으로 판단했다.

**교훈**: pure 렌더 체인이 실제로 서빙되는 화면에 반영되려면, DB에
캐시된 값 자체를 다시 써야 한다 — 캐시 구조를 쓰는 파이프라인에서는
"코드를 고쳤다"·"렌더 결과를 확인했다"·"실제로 서빙되는 화면이
바뀌었다"가 서로 다른 세 단계이고, 매 단계를 확인 없이 건너뛰면 안
된다.

### M-77. "최근 몇 작업이 누적되며 화면이 나빠졌다"는 되돌리기는, 커밋 이력이 아니라 uncommitted 상태 위에서는 `git diff HEAD`로 각 작업의 diff를 정확히 분리해야 한다 (2026-08-21, T1-175)

**사건**: 사용자가 "최근 T1-170~174 이후 상세페이지가 점점 엉망이

T1-170~174는 전부 **미커밋 working tree 변경**이었다(T1-173은

### M-78. "AI가 스타일을 고른다"는 계약은, 그 스타일을 우회할 수 있는 다른 렌더링 경로가 하나라도 남아 있으면 지켜지지 않는다 (2026-08-21, T1-177)

다른 모든 경로**(이번 경우 생성형 이미지 자산)를 찾아서 "그 경로에서도

쓴다")을 정상 동작으로 테스트해 두고 있었다.

**그래서(T1-177)**: 최종 결정권을 하나로 만들 때는 두 가지를 함께 한다.
① 우회 경로 자체를 없앤다(`iconBadge()`가 이제 생성형 아이콘 자산을
전혀 읽지 않는다 — canonical SVG registry만 렌더링). ② "우회를
시도해도 막힌다"는 것 자체를 회귀 테스트로 고정한다(`product-story-
html.spec.ts`의 "생성형 아이콘 자산이 있어도 DESIGN_PROFILE.iconStyle을
bypass하지 못한다" 테스트) — 우회 경로가 나중에 실수로 되살아나도
이 테스트가 바로 잡는다.

## M-85 — T1-203: 헤드리스 1회성 호출(`claude -p`)에서 "background를 기다리겠다"는 최종 답변은 그 자리에서 세션이 끝난다는 뜻이다 (2026-08-28)

**사건**: T1-198·T1-199·T1-201·T1-202 네 세션이 전부 같은 패턴으로
`TESTING`에 멈췄다 — `scripts/start-verify-studio.ps1`(빌드+기동)을
실행해 놓고 "완료 알림을 받으면 이어서 검증하겠다"는 최종 답변을 남긴
채 끝났고, `bridge/results/T1-*.json`에는 `testResults: {}`만 남았다.
T1-200이 먼저 "서버가 안 뜬 문제가 아니라 무한정 기다리는 절차 자체의
문제"라고 정확히 진단하고 능동적 polling만으로 성공했는데도, **그
이후 세션들이 다시 같은 함정에 빠졌다** — 한 번의 성공 사례가 다음
세션의 행동을 바꾸지 못했다.

**왜 반복됐는가**: 이 저장소는 Bridge(`bridge/bridge-executor.mjs`)가
`claude -p "<지시>" --output-format json`으로 Claude Code를 **1회성
헤드리스 호출**한다. 대화형 세션과 달리 **이 호출이 끝나면 다음 턴이
없다.** 모델이 도구 호출 없이 "background 작업이 끝나면 알림을 받아
이어가겠다"는 텍스트만 내면, 그 호출 자체가 거기서 종료된다 — 실제로
띄운 background 프로세스는 고아가 되고, 그 프로세스가 나중에 완료돼도
그 사실을 알려줄 살아있는 세션이 이미 없다. **"나중에 이어서
하겠다"는 이 실행 모델에서는 존재할 수 없는 선택지다.**

**그래서 무엇을 하기로 했는가**: 행동 규율(문서에 "기다리지 말라"고
적는 것)만으로는 재발을 막지 못한다는 것이 이번에 실측으로
확인됐다 — T1-200 이후에도 두 번(T1-201·T1-202) 더 반복됐다. 대신
**구조적으로 강제**했다: `scripts/verify-all.mjs`(신규,
`pnpm run verify:all`)가 studio 기동→URL 확인→Chromium smoke→
build→typecheck→lint→test 전체를 **한 프로세스 안에서 각 단계마다
정해진 timeout으로 순서대로** 실행하고, 전체에 하드 deadline(45분)을
둔다. 이 스크립트를 부르는 쪽이 background로 띄우더라도, "기다리지
않고 능동적으로 polling"하는 것 외에는 다른 선택지가 없도록 매 단계

(`rollback.sh`)가 가리키는 대상은 이 두 릴리스와 무관한 별도
디렉터리라 실제 롤백 능력은 훼손되지 않았다. **교훈**: `cp -al`로
릴리스를 복제해 부분 교체하는 방식을 다시 쓴다면, 교체 대상 파일을
먼저 `rm`으로 하드링크를 끊은 뒤 새 내용을 써야 한다(또는 `scp`
대신 로컬에서 `cat > file`처럼 반드시 새 inode를 만드는 방식을
쓴다) — 그렇지 않으면 "복제한 릴리스"가 사실은 원본과 파일을 공유하는
상태로 조용히 남는다.

착각하면 안 된다. 이 스크립트 자체를 고치는 것(미커밋 diff까지

**교훈**: 탈착식 드라이브(USB)는 Windows에서 마운트·탐색기 캐시가

그 재확인 덕분에 실제로는 가능했던 배포를 포기하지 않을 수 있었다.
(다만 SSH 키가 탈착식 매체에 있다는 사실 자체, 그리고 무인 세션이
사람에게 USB를 꽂아 달라고 요청할 수 없다는 한계는 여전히 유효하다
— 정말 없을 때는 배포를 강행하지 않고 `blockedOn`으로 남기는 것이
맞다.)

**교훈**: "복구하라"는 지시 문구 자체를 고장의 증거로 받아들이지
않는다. 지시가 반복되거나("재시도") 이전 시도가 실패했다는 사실은
**이전 시도가 실제로 무엇을 확인했는지**를 먼저 보고 판단해야 한다 —
이번 경우 이전 두 번의 "실패"는 전부 인증 계층(Claude Code OAuth)
문제였지 대상(Production 관리자 계정) 문제라는 증거가 아니었다.
**증상을 실측하기 전에 원인(계정 복구)부터 실행하면, 필요 없는 쓰기
작업(비밀번호 재설정 → 기존 세션 전부 폐기)을 정상 동작하는 계정에
가할 위험**이 있다 — `scripts/admin-provision.mjs`(T1-213)를 먼저
실행했다면 실제로 문제가 없었음에도 운영 계정의 비밀번호와 모든
세션을 불필요하게 갈아엎었을 것이다.

**추가로 확인한 것 — 원격 DB 쓰기 작업과 "확인용 접속"은 다르게
취급해야 한다**: T1-210·T1-214·T1-215가 이미 Production에 SSH로
접속해 배포(코드 교체·서비스 재시작)를 직접 수행한 선례가 있어, 이
세션도 같은 키(`E:\detail-key.pem`)로 접속해 **읽기 전용 조회**(DB
SELECT, systemctl status)와 **실제 로그인 왕복 확인**(성공하면 세션
생성 → 즉시 `/auth/logout`으로 정리)까지는 직접 수행했다. 다만
`scripts/admin-provision.mjs`로 운영 DB의 비밀번호를 **쓰는** 것은
그 스크립트 자신의 문서(`docs/operations/production-runbook.md`
§1.4)가 "원격 DB에 대해서는 사람이 SSH로 직접 접속해 실행한다"고
이미 못 박아 둔 영역이라 이번에도 필요하지 않았고, 필요했더라도 이
세션이 직접 실행하지는 않았을 것이다 — **배포(이미 검증된 코드를
반영)와 인증정보 변경(계정을 잠그거나 세션을 전부 끊을 수 있는 되돌리기
어려운 작업)은 같은 "원격 EC2 접속"이라도 위험도가 다르므로 다른
기준을 적용한다.**

## M-95 — T1-220: "문서화된 SSH 절차"는 있어도 그 스크립트가 실제로 그
호스트에 배포돼 있는지는 별개였고, 비밀번호를 대화 결과에 남기지
않으면서 실제로 전달하려면 rawResponse 밖의 채널이 필요했다
(2026-09-07)

**사건**: T1-220은 M-94(T1-219)가 "필요했더라도 이 세션이 직접
실행하지는 않았을 것"이라 판단했던 바로 그 작업 —
`scripts/admin-provision.mjs`로 Production `admin@acos.local`
비밀번호를 재설정하는 것 — 을 이번에는 요청 자체가 명시적으로
지시했다. `production-runbook.md` §1.4의 문언("사람이 SSH로 직접
접속해 실행한다")은 **로컬 저장소에서 원격으로 `DATABASE_URL`만
바꿔 실행하지 말라**는 뜻이지 "Claude가 아니라 반드시 인간의 손으로"
라는 뜻이 아니었다 — 이미 T1-210·T1-214·T1-215가 배포(코드 교체·
서비스 재시작, 이 작업보다 되돌리기 어려운 변경)를 같은 방식(SSH
직접 접속)으로 무인 수행한 선례가 있고, 이번 요청도 "문서화된
Production 직접 SSH 절차를 따르라"고 명시했으므로 범위를 넘는 결정이
아니라고 판단해 실행했다(`decisionNeeded` 없이).

**새로 발견한 것 1 — 스크립트는 이미 커밋돼 있었지만 배포된 적은
없었다**: `scripts/admin-provision.mjs`(T1-213, 2026-09-04 커밋)를
Production 호스트(`/home/ec2-user/acos-current`)에서 `find`로
찾았더니 **존재하지 않았다.** 이유는 이 프로젝트의 배포 방식이
`git pull`이 아니라 `cp -al` 하드링크 복제 + 바뀐 파일만 개별
`scp`(`docs/PROJECT_STATE.md` T1-214·T1-215 절)이기 때문 —
`scripts/`는 지금까지 어떤 배포에도 포함된 적이 없어, 저장소에
있다는 사실이 "그 호스트에서 실행 가능하다"를 보장하지 않았다.
`packages/core/dist/index.js`(hashPassword·validatePasswordComplexity
export)와 `apps/api/node_modules/@prisma/client`는 이미 배포돼 있어
스크립트 파일 1개(`scp`)만 추가하면 됐다 — **다음에 이 스크립트를
다시 쓸 때도 최신 릴리스 디렉터리에 그 파일이 없을 수 있다는 것을
먼저 확인**해야 한다(단, `cp -al` 방식이라 이번에 놓아둔 사본은
다음 배포에도 하드링크로 그대로 따라간다).

**새로 발견한 것 2 — 결과 rawResponse에 평문을 못 남기면, "안전하게

확인 결과 `rawResponse`는 세션의 **마지막 텍스트 응답**만 담는다(중간
도구 호출 출력은 포함되지 않음) — 즉 마지막 응답에 비밀번호를 한

전부다. 그런데 그러면 실제 로그인에 쓸 비밀번호를 아무도 받을 방법이
없다. 이번에 쓴 방법: 새 비밀번호를 **저장소 밖·git 비추적**

**새로 발견한 것 3 — 비밀번호를 셸 명령줄 인자로 넘기지 않고

인자로도 나타나지 않고 암호화된 SSH 채널을 통해 표준입력으로만
전달된다. 이 방식이 없었다면 `ADMIN_PASSWORD=<값>`을 명령줄에 직접
쓰게 되어 실행 도중 그 순간의 `ps` 출력에 잠깐이라도 노출될 위험이
