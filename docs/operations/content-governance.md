# Content Governance (발행 거버넌스, TASK-2501 · 2601 · 2701)

> **발행되는 것을 검사합니다.**
>
> Sprint 4(TASK-0404)부터 금지어·규칙 검사는 있었지만, 그것은 **Product
> Object의 READY 전환**에만 걸려 있었습니다. 세상에 나가는 것은 Product
> Object가 아니라 **Content의 제목과 본문**이고, 그 경로의 발행 조건은
> "REVIEW 상태이며 제목과 본문이 비어 있지 않다"뿐이었습니다.
>
> 상품을 검사하고 콘텐츠를 검사하지 않는 것은 **재료를 검사하고 완성품은
> 안 보는 것**과 같습니다.

## 0. 어디에 걸리는가

```
DRAFT ──▶ REVIEW ──▶ PUBLISHED ──▶ ARCHIVED
  ▲              ▲                    │
  │              └─ 여기서만 판정이 걸립니다
  └──────────────────────────────────┘  되살리기 (TASK-2701)
```

**`PUBLISHED` 전이에만** 적용됩니다. 검토를 요청하는 것(`REVIEW`)과 보관하는
것(`ARCHIVED`)은 막지 않습니다 — 검토를 요청하는 것과 세상에 내보내는 것은
다릅니다.

`ARCHIVED`에서는 **`DRAFT`로만** 갈 수 있습니다(CTO 결정 2601-①, §5.1).
발행으로 직행하는 길은 없습니다 — 되살린 것은 `REVIEW`를 거쳐야 하고,
그래야 **판정이 다시 돕니다.**

## 1. 무엇을 검사하는가

| 검사 | id | 실패하면 |
| --- | --- | --- |
| 제목·본문 | `content-body` | **발행 차단** |
| 금지어 검사 | `banned-words` | **발행 차단** |
| 필수 고지 | `disclosures` | **발행 차단** |
| 근거 상품 연결 | `source-object` | 주의 (막지 않음) |
| 관련 규칙 검토 | `related-rules` | 주의 (막지 않음) |

판정 등급은 READY 판정과 같은 3단계입니다 — `PASS` / `WARNING` / `FAIL`.
화면이 두 어휘를 배우지 않게 하려고 같은 등급을 씁니다.

**경보와 차단은 다릅니다.** `WARNING`은 드러내되 막지 않습니다.
막는 항목은 응답의 `blocking` 필드로 밝힙니다 — 화면이 "주의인데 왜 막혔지"를
추측하지 않아야 합니다.

### 1.1 금지어

**제목과 본문을 모두** 봅니다. READY 판정은 상품의 제목·브랜드·OCR 텍스트만
봤으므로, 본문에 든 금지어는 아무도 보지 않았습니다.

스캔 규칙(부분 일치·대소문자 무시)은 **READY 판정과 같은 함수**를 씁니다 —
상품에서는 걸리는 말이 콘텐츠에서는 안 걸리면 어느 쪽 판정도 믿을 수 없습니다.

메시지는 **어디에 몇 건**인지 말합니다(`제목 1건 · 본문 2건`) — "금지어가
있습니다"만으로는 고칠 수 없습니다.

### 1.2 필수 고지

본문에 반드시 있어야 하는 문구입니다. 공백·줄바꿈 차이는 무시합니다(붙여 넣은
문구는 원문과 줄바꿈이 다르기 마련입니다).

`whenCategory`가 있으면 **그 분류의 상품에만** 요구합니다 — 모든 상품에 모든
고지를 요구하면 본문이 고지문으로 덮이고, 그러면 아무도 읽지 않습니다.

상품 분류를 알 수 없으면 **전체 적용 규칙만** 검사하고 그 사실을 말합니다
(적용 규칙 0건과 통과는 다릅니다).

### 1.3 근거 상품 연결

발행된 콘텐츠가 어느 Product Object에서 나왔는지입니다. 끊겼거나 그 상품이
`READY`가 아니면 **주의**입니다 — 본문 자체가 잘못된 것은 아니므로 막지
않지만, 발행 후 근거를 추적할 수 없다는 사실은 드러냅니다.

## 2. 규칙 등록

규칙은 Company Brain의 **GLOBAL Memory**에 둡니다. 읽는 곳은
`GovernanceRulesService` **하나**입니다 — 규칙이 두 곳에 있으면 두 곳이
갈라집니다(CTO 결정 2301-①과 같은 이유).

### 2.1 금지어

```bash
curl -X POST http://<api-host>/memory -b cookies.txt \
  -H 'content-type: application/json' \
  -d '{
    "scope": "GLOBAL",
    "key": "banned-words",
    "value": ["최고", "1위", "유일무이"],
    "description": "광고 표현 금지어"
  }'
```

값은 **문자열 배열**이어야 합니다.

### 2.2 필수 고지

```bash
curl -X POST http://<api-host>/memory -b cookies.txt \
  -H 'content-type: application/json' \
  -d '{
    "scope": "GLOBAL",
    "key": "required-disclosures",
    "value": [
      {
        "id": "wash",
        "text": "사용 후 물로 충분히 헹구세요.",
        "whenCategory": "생활용품",
        "reason": "사내 표시 규정"
      }
    ],
    "description": "필수 고지 문구"
  }'
```

| 필드 | 필수 | 뜻 |
| --- | --- | --- |
| `id` | ✅ | 규칙 식별자 — 판정 기록에 이 값이 남습니다 |
| `text` | ✅ | 본문에 있어야 하는 문구 |
| `whenCategory` | | 이 분류에만 적용 (없으면 전체) |
| `reason` | | 왜 필요한지 — **적어 두십시오.** 문구만 있으면 나중에 아무도 지우지 못하고, 왜 있는지도 설명할 수 없습니다 |

수정은 `PATCH /memory/<id>`입니다.

### 2.3 규칙을 읽지 못하면

**미설정과 형식 오류를 구분합니다.** 둘 다 판정은 `주의`(막지 않음)지만,
해야 할 일이 다릅니다.

| 상태 | 판정 | 안내 |
| --- | --- | --- |
| 등록 안 됨 | `주의` | "설정되지 않아 검사하지 못했습니다 — 등록하세요" |
| 등록됐지만 형식 오류 | `주의` | "형식이 올바르지 않아 검사하지 못했습니다 — 값을 고치세요 **(등록은 되어 있습니다)**" |

둘을 뭉개면 운영자는 등록하러 갔다가 이미 등록된 것을 발견합니다.
형식 오류는 **서버 로그에도 경고로 남습니다** — 조용히 무시하면 아무도
고치지 않습니다.

> **형식이 틀린 규칙을 빈 목록으로 읽지 않습니다.** 그러면 "위반 없음"이
> 되어 거짓 통과가 됩니다. 검사하지 못한 것은 통과가 아닙니다.

## 3. 발행 전에 확인

```bash
# 판정만 — 전이하지 않고, 기록도 남기지 않습니다
curl http://<api-host>/projects/<projectId>/contents/<contentId>/governance -b cookies.txt
```

`/admin` 화면이 아니라 **프로젝트 상세 화면의 발행 버튼 옆**에 같은 판정이
표시됩니다. 눌러 보고 막히는 것과, 무엇이 막는지 먼저 보는 것은 다릅니다.

미리보기와 발행 게이트는 **같은 판정 함수**를 부릅니다 — 화면이 "발행 가능"
이라고 했는데 누르면 막히는 상태는 구조적으로 생기지 않습니다.

응답:

| 필드 | 뜻 |
| --- | --- |
| `status` | 전체 판정 (개별 검사 중 최악 값) |
| `checks[]` | 검사별 `status` · `messages` · **`blocking`** |
| `blockers[]` | 막는 항목만 — 비어 있으면 발행할 수 있습니다 |
| `publishable` | `blockers.length === 0` |
| `appliedRules` | 판정에 실제로 쓰인 기준 (금지어 수 · 적용 고지 id) |

`appliedRules`의 값이 `null`이면 **검사하지 못한 것**입니다 — `0`이 아닙니다.

### 3.1 규칙을 켜기 전에 — Preflight Scan (TASK-2601, CTO 결정 2501-①)

규칙을 처음 등록하면 **이미 `REVIEW`에 있던 콘텐츠들이 위반을 담고 있을 수
있고, 그러면 발행이 줄줄이 막힙니다.** 하나씩 눌러 보며 발견하는 방식으로는
언제 끝날지 알 수 없습니다. 켜기 전에 세어 보십시오.

```bash
# 프로젝트 범위
curl "http://<api-host>/projects/<projectId>/governance/preflight" -b cookies.txt

# 전체 범위 (ADMIN 전용 — 프로젝트 경계를 넘습니다)
curl "http://<api-host>/governance/preflight" -b cookies.txt
```

> **이 스캔은 상태를 바꾸지 않고, 자동으로 고치지도 않습니다.**
> 판정 기록도 남기지 않습니다 — 훑어본 것을 발행 시도로 기록하면 이력이
> 사실과 어긋납니다. 화면에도 "한 번에 고치기" 버튼이 없습니다.
>
> 자동 수정을 하지 않는 이유는 원격 사본 자동 복구를 만들지 않은 것
> (CTO 결정 2201-②)과 같습니다: 금지어를 기계가 지우면 문장이 무슨 뜻이
> 되는지 아무도 확인하지 않은 채 발행되고, 고지 문구를 기계가 덧붙이면
> 맥락과 무관한 자리에 붙습니다.

### 무엇을 세는가

| 값 | 뜻 | 해야 할 일 |
| --- | --- | --- |
| `blocked` | 아직 발행되지 않았고 위반이 있음 | 발행 전에 고칩니다 |
| `publishedViolations` | **이미 발행됐는데 위반이 있음** | **막을 수 없습니다** — 내리거나 고쳐 다시 발행합니다 |
| `warned` | 막지는 않지만 주의 | 판단해서 처리합니다 |
| `clean` | 이상 없음 | — |

두 숫자를 나누어 세는 이유: **발행 게이트는 나가는 것을 막지만 이미 나간
것에는 아무 힘이 없습니다.** 섞어 세면 "위반 5건"이 무슨 뜻인지 알 수 없습니다.

`byCheck`는 검사별 집계입니다 — 금지어 때문에 막히는 것이 30건이고 고지
때문이 2건이면, 무엇을 먼저 고칠지가 분명해집니다.

### 범위와 상한

| 질의 | 기본 | 뜻 |
| --- | --- | --- |
| `?status=` | `DRAFT,REVIEW` | 아직 나가지 않은 것. **`PUBLISHED`를 넣으면 이미 나간 위반까지** 봅니다 |
| `?limit=` | 50 (최대 200) | **한 페이지** 건수 |
| `?offset=` | 0 | 건너뛸 위반 수 |

잘못된 값은 **400**입니다. 조용히 기본값으로 되돌리지 않습니다 — 무시되면
운영자는 자기가 준 값이 적용됐다고 믿고, 페이지의 경우 **다른 페이지를 보고
있는 줄도 모릅니다.**

**`summary`는 항상 전체 기준입니다** (CTO 결정 2601-④). 페이지는 `items`만
자릅니다 — 한 페이지에 2건이 보인다고 위반이 2건인 것이 아닙니다.

| 필드 | 뜻 |
| --- | --- |
| `summary.*` | **전체** 기준 집계 |
| `page.total` | **위반 전체 수** (페이지와 무관) |
| `page.offset`·`page.limit` | 지금 보고 있는 구간 |
| `page.hasMore` | 다음 페이지가 있는가 |

판정 대상은 **전량**입니다. 큰 프로젝트에서도 요약이 정확하도록 내부에서
200건씩 나눠 읽습니다(커서 기준 — `skip`으로 넘기면 읽는 도중 새 콘텐츠가
생겼을 때 한 건을 두 번 세거나 건너뜁니다).

규칙은 **스캔 한 번에 한 번만** 읽습니다 (CTO 결정 2601-⑤ Request Scope).
전역 캐시는 두지 않습니다 — 규칙을 고친 운영자가 언제 반영되는지 알 수 없게
되면 규칙을 신뢰할 수 없습니다.

## 4. 판정 기록

발행을 시도할 때마다 **막든 통과하든** 기록합니다
(`content_governance_checks`). **삭제하지 않습니다.**

```bash
curl http://<api-host>/projects/<projectId>/contents/<contentId>/governance/history -b cookies.txt
```

| 필드 | 뜻 |
| --- | --- |
| `status` | 그때의 판정 |
| `published` | **이 판정으로 실제 발행이 이뤄졌는가** — `false`면 막힌 기록 |
| `blockedBy[]` | 막은 검사의 id |
| `checks[]` | 그때의 검사 결과 전체 |
| `appliedRules` | **그때의 기준** |
| `actor` | 수행자 이메일 |
| `archivedAt` | 보관 시각 (90일 경과, §4.1) — `null`이면 현황에 남아 있습니다 |

두 가지를 남기는 이유가 각각 있습니다.

- **그때의 기준을 남기는 이유**: 규칙은 나중에 바뀝니다. 지금 통과한 콘텐츠가
  반년 뒤 기준으로는 위반일 수 있고, 그때 "왜 이게 발행됐지"에 답하려면
  판정 당시의 기준이 있어야 합니다.
- **막힌 기록을 남기는 이유**: 무엇이 막았고 언제 풀렸는지가 없으면
  "왜 이렇게 늦게 발행됐지"에 아무도 답할 수 없습니다.

### 4.1 90일 이후 보관 (TASK-2601, CTO 결정 2501-⑤)

판정 기록은 **삭제하지 않고 90일 경과 후 보관**합니다. 경보(결정 1302-④)·
Dead Letter(결정 1501-③)와 같은 정책입니다.

- 보관은 **현황 조회에서 비켜 두는 것**이고 삭제가 아닙니다. 삭제는 되돌릴
  수 없고 "그때 왜 막혔나"를 확인할 방법을 영원히 없앱니다.
- 기준은 **작성 시각**입니다 — 판정 기록에는 해소라는 개념이 없는 시점
  기록입니다(경보는 해소 시각 기준).
- 보관은 예약 정리 작업(`alert-archive`, 매일 04:00 로컬)에서 함께 돕니다.
  **작업을 새로 만들지 않았습니다** — 같은 성격의 정리가 서로 다른 시각에
  돌면 무엇이 남았는지 흐려집니다.

| 환경변수 | 기본 | 뜻 |
| --- | --- | --- |
| `GOVERNANCE_ARCHIVE_AFTER_DAYS` | `90` | 보관 유예. 해석할 수 없거나 0 이하면 기본값(잘못 적은 값 때문에 즉시 보관되는 것보다 안전합니다) |

보관된 기록은 조회에서 기본으로 빠지지만 **볼 수 있습니다**:

```bash
curl "http://<api-host>/projects/<pid>/contents/<cid>/governance/history?includeArchived=1" -b cookies.txt
```

볼 길이가 없으면 보관이 사실상 삭제가 됩니다.

지금 한 번 돌려 보려면:

```bash
curl -X POST "http://<api-host>/ops/checks/run?job=alert-archive" -b cookies.txt
```

### 4.2 예약 스캔 (TASK-2701, CTO 결정 2601-②③)

스캔은 **매일 03:50 로컬**에 자동으로 돕니다(`governance-scan` 작업).
보관 정리(04:00)보다 **앞에** 두었습니다 — 스캔이 남긴 기록을 보관이 곧바로
치우면 방금 만든 것을 못 보게 됩니다.

| 환경변수 | 기본 | 뜻 |
| --- | --- | --- |
| `OPS_CHECK_GOVERNANCE_SCAN_AT` | `03:50` | 실행 시각 (운영 서버 로컬) |

지금 한 번 돌려 보려면:

```bash
curl -X POST "http://<api-host>/ops/checks/run?job=governance-scan" -b cookies.txt
```

### 경보는 늘었을 때만 (결정 2601-③)

예약 스캔은 매일 도는데, 결과가 그대로인 동안 계속 경보하면 그 경보는 배경
소음이 됩니다. **부를 일이 아닌데 부르면 정작 불러야 할 때 오지 않습니다.**

| 상황 | 경보 | 이유 |
| --- | --- | --- |
| **첫 스캔** | 없음 (기준선) | 규칙을 처음 켠 직후에 위반이 잔뜩 있는 것은 정상입니다. 전량을 경보로 만들면 아무 뜻이 없습니다 |
| **늘었음** | **발생** (`governance-scan`) | 증가분과 무엇이 늘었는지 말합니다 |
| **같음** | 없음 | 이미 알렸습니다. 같은 결과로 반복하지 않습니다 |
| **줄었음** | 없음 (기존 경보는 유지) | 고쳐지고 있다는 뜻입니다. 좋은 일로 사람을 깨우지 않습니다 |
| **0이 됨** | 해소 | 있던 것이 없어졌을 때만 해소입니다 |

이미 나간 위반이 섞여 있으면 **심각(critical)**입니다 — 아직 막을 수 있는
것과 이미 나간 것은 급한 정도가 다릅니다.

비교 기준은 **범위별**입니다(`all` / `project:<id>`) — 프로젝트 하나가
나빠진 것과 전체가 나빠진 것을 한 경보로 뭉치면 어디를 봐야 할지 알 수
없습니다.

### 실행 이력

```bash
# 전체 범위 (ADMIN 전용)
curl "http://<api-host>/governance/scans" -b cookies.txt

# 프로젝트 범위
curl "http://<api-host>/projects/<projectId>/governance/scans" -b cookies.txt
```

**경보를 만들지 않은 실행도 남습니다.** "돌았지만 조용했다"와 "돌지 않았다"는
다르고, 그 구분이 없으면 예약이 멈춘 것을 알아챌 수 없습니다. 각 실행에
`verdict`(기준선·늘었음·줄었음·변화 없음·해소)와 `alerted`가 함께 남습니다.

## 5. 막혔을 때

`PATCH …/status`로 `PUBLISHED`를 요청하면 **400**과 함께 사유가 옵니다.

```
발행 거버넌스 판정을 통과하지 못했습니다 — 금지어 검사: 금지어 발견: 1위
(제목 0건 · 본문 1건) / 필수 고지: 본문에 없습니다 — "사용 후 물로 충분히
헹구세요." (사내 표시 규정)
```

상태는 **바뀌지 않습니다**(`REVIEW` 그대로, `publishedAt`도 그대로).

고치는 방법은 둘입니다.

1. **본문을 고칩니다** — 금지어를 빼거나 고지 문구를 넣습니다. 대부분 이쪽입니다.
2. **규칙을 고칩니다** — 규칙 자체가 잘못됐다고 판단되면 Memory를 수정합니다.
   이때는 **왜 바꿨는지 Decision에 남기십시오** — 규칙을 느슨하게 만드는
   변경은 기록 없이 하면 다음 사람이 되돌릴 수 없습니다.

### 5.1 이미 발행된 위반의 공식 절차 (CTO 결정 2601-①)

이미 나간 콘텐츠에 위반이 발견되면 발행 게이트로는 막을 수 없습니다.
공식 절차는 **`PUBLISHED` → `ARCHIVED` → 수정 → 재발행**입니다.

```bash
# 1) 내린다
curl -X PATCH …/status -d '{"status":"ARCHIVED"}'
# 2) 되살린다 (ARCHIVED에서 갈 수 있는 곳은 DRAFT뿐입니다)
curl -X PATCH …/status -d '{"status":"DRAFT"}'
# 3) 본문을 고친다
# 4) 검토 → 재발행 (여기서 거버넌스 판정이 다시 돕니다)
curl -X PATCH …/status -d '{"status":"REVIEW"}'
curl -X PATCH …/status -d '{"status":"PUBLISHED"}'
```

- **별도 상태(`SUSPENDED`)를 만들지 않았습니다.** 상태를 늘리면 화면·판정·
  이력이 모두 그 상태를 알아야 합니다.
- **`ARCHIVED` → `PUBLISHED` 직행은 없습니다.** 내린 이유를 고치지 않은 채
  곧바로 되돌아가면 내린 것이 아무 의미가 없습니다. `400`과 함께 경로를
  안내합니다.
- `publishedAt`은 **최초 발행 시각을 보존**합니다(TASK-0703 승인 ②).
  내렸다 다시 올린 이력은 감사 이력(`GET …/history`)에서 봅니다.

## 6. 하지 않기로 한 것 (CTO 결정 2501-②③④ · 2601-①③⑤)

**하지 않기로 한 일은 코드에 흔적이 없어서 나중에 누가 되살려도 아무도
모릅니다.** 그래서 없다는 사실을 문서와 테스트에 함께 남깁니다.

| 하지 않는 것 | 결정 | 그래서 어떻게 되는가 |
| --- | --- | --- |
| 금지어 **단어 경계**·예외 목록 | 2501-② | 부분 일치를 유지합니다 — `최고`를 등록하면 **`최고급`도 걸립니다.** 넓게 걸고 사람이 판단합니다. 좁히면 놓치는 쪽이 위험합니다 |
| **READY 전환 강제** | 2501-③ | READY 판정은 Advisory입니다 — 판단을 돕지만 막지 않습니다. **강제 차단은 `PUBLISHED`뿐**입니다 |
| **프로젝트·분류별 규칙 스코프** | 2501-④ | 규칙은 GLOBAL Memory 한 곳입니다. 프로젝트마다 다른 금지어를 둘 수 없습니다 |
| **자동 수정** | 2501-① | Preflight는 위반 목록만 만듭니다. 기계가 문장을 고치지 않습니다 |
| **판정 기록 삭제** | 2501-⑤ | 90일 후 보관만 합니다 |
| **별도 정지 상태(`SUSPENDED`)** | 2601-① | 되살리는 길은 `ARCHIVED` → `DRAFT` 하나입니다 |
| **같은 결과 반복 경보** | 2601-③ | 늘었을 때만 부릅니다 |
| **규칙 전역 캐시** | 2601-⑤ | 요청 1회 스냅샷만 씁니다 — 규칙을 고치면 곧바로 반영됩니다 |

`최고급`이 걸리는 것은 **버그가 아닙니다.** 그 표현을 허용하려면 금지어를
`최고 ` 처럼 더 좁게 등록하거나, 규칙 자체를 다시 판단하십시오.
