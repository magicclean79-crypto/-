# AI 비용 거버넌스 (TASK-3101 · 3201 · 3301)

단가는 **돈의 기준**입니다. 코드 한 줄을 고쳐 바로 반영하면 ⓐ 누가 왜 바꿨는지
남지 않고 ⓑ 예산·리포트의 숫자가 **어느 시점부터** 달라졌는지 아무도 설명할 수
없습니다. 그래서 CTO 정책 3101이 네 가지를 정했습니다.

| 정책 | 내용 | 코드에서 |
| --- | --- | --- |
| 3101-① | 가격표는 **검토 → 승인 → 적용** 절차를 거친다 | `PRICING_TRANSITIONS`, `POST /ops/pricing/:id/{review,approve,apply,reject}` |
| 3101-② | 비용 기록은 수정하지 않는다 (**Append Only**) | `resolvePricingAt`(시점별 대조), `pricing/append-only.spec.ts` |
| 3101-③ | Forecast는 참고자료다 — **Budget Gate는 실제 비용만** 본다 | `cost-forecast.ts`(차단 경로가 이 파일을 모른다) |
| 3101-④ | Billing Report는 운영 지표다 — **회계 청구서가 아니다** | `BILLING_DISCLAIMER` |

TASK-3201이 여기에 **자동화**를 더했습니다.

| 정책 | 내용 | 코드에서 |
| --- | --- | --- |
| 3201-① | 가격 변경은 **감지 → 승인 → 적용** | `PRICING_TRANSITIONS.DETECTED`, `POST /ops/pricing/detect`, 예약 점검 `pricing-detect` |
| 3201-② | **Production에서는 제안자와 승인자가 같을 수 없다** (Development는 허용) | `judgeSelfApproval({environment})` |
| 3201-③ | **Effective From** — 미래 시점 적용 | `pricing_proposals.effectiveFrom`, `resolvePricingAt(…, now)` |
| 3201-④ | Forecast는 **Alert만** 내고 Budget Gate에 연결하지 않는다 | `detectForecastAlerts`, 예약 점검 `cost-forecast` |
| 3201-⑤ | 가격 적용 **즉시 캐시 무효화** | `PricingCacheBus` (Redis pub/sub) |

TASK-3301이 **외부 공지**와 **2단계 승인**을 더했습니다.

| 정책 | 내용 | 코드에서 |
| --- | --- | --- |
| 3301-① | 공지 **파싱 실패는 "변경 없음"이 아니다** — 경고 + 사람 확인 | `judgePriceSource`, `price-source` 경보 |
| 3301-② | 자동 감지 제안은 운영에서 **2단계 승인** | `requiresSecondApproval`, `CONFIRMED` 단계 |
| 3301-③ | 예약 취소는 **삭제하지 않는다** — `CANCELLED` | `judgeScheduleCancel` |
| 3301-④ | 감지 주기 기본 6시간 · **Provider별만** (프로젝트별 금지) | `resolveDetectionIntervals` |

화면은 **관리자 → AI 비용 관리**(`/admin/costs`)입니다. 모두 ADMIN 전용입니다.

## 1. 가격표를 바꾸는 절차 (정책 3101-①)

```bash
# ① 제안 — 사유 없이는 등록되지 않습니다
curl -X POST "http://<api-host>/ops/pricing" -b cookies.txt \
  -H 'content-type: application/json' \
  -d '{"target":"ocr","key":"google-vision","price":{"perUnitUsd":0.002},
       "reason":"2026-07 Google Cloud Vision 단가 공지 반영"}'

# ② 검토 → ③ 승인 → ④ 적용 (순서를 건너뛸 수 없습니다)
curl -X POST "http://<api-host>/ops/pricing/<id>/review"  -b cookies.txt
curl -X POST "http://<api-host>/ops/pricing/<id>/approve" -b cookies.txt
curl -X POST "http://<api-host>/ops/pricing/<id>/apply"   -b cookies.txt

# 어느 단계에서든 반려 — 사유가 필요합니다
curl -X POST "http://<api-host>/ops/pricing/<id>/reject" -b cookies.txt \
  -H 'content-type: application/json' -d '{"reason":"공지 원문 확인 필요"}'
```

지금 무슨 단가로 계산하는지, 그 단가가 **누구의 승인으로** 적용된 것인지:

```bash
curl "http://<api-host>/ops/pricing" -b cookies.txt
```

### 규칙과 그 이유

| 규칙 | 왜 |
| --- | --- |
| **검토 없이 승인·승인 없이 적용 불가** | 단가는 돈의 기준이다 — 한 사람의 오타가 예산 전체를 흔든다 |
| **적용·반려는 끝이다** (되돌릴 수 없다) | 끝난 것을 되살리면 "무엇이 언제 적용됐는가"의 이력이 흐려진다 — 되돌리려면 **새 제안**을 낸다 |
| **사유 필수** (제안·반려 모두) | 사유가 없으면 이력이 있어도 판단을 복원할 수 없고, 제안자는 무엇을 고칠지 모른다 |
| **0은 허용, 음수는 거부** | 무료 모델·엔진은 실제로 있다. 음수 단가는 지출을 줄여 **예산 상한을 무력화**한다 |
| **적용만 계산을 바꾼다** | 승인은 "적용해도 된다"는 뜻이다. 적용 시각이 있어야 "언제부터 이 단가로 계산됐나"에 답할 수 있다 |
| 제안자 = 승인자면 **운영은 차단·개발은 경고** | 운영에서 한 사람의 오타가 예산 전체를 흔든다. 반면 개발에서 절차가 막히면 사람은 코드를 고쳐 우회하고 이력이 아예 없어진다 (정책 3201-② · §1-3) |

적용된 단가는 **이후 호출**에만 쓰입니다(발효 시각부터 — §1-4). 적용하면
**모든 인스턴스가 즉시** 새 단가로 계산합니다(§1-5).

## 1-2. 자동 감지 (정책 3201-①)

```bash
# 예약(6시간)을 기다리지 않고 지금 대조한다
curl -X POST "http://<api-host>/ops/pricing/detect" -b cookies.txt
```

감지된 변경은 `DETECTED` 제안이 되고, **감지 → 승인 → 적용**을 거칩니다
(감지가 검토를 대신합니다 — 근거가 제안에 붙어 있습니다).

### 무엇을 감지하고, 무엇을 감지할 수 없는가

**Provider의 가격 공지는 읽을 수 없습니다.** 비용은 우리가 우리 가격표로
계산해 기록하므로, 기록만 봐서는 "Provider가 단가를 올렸다"를 알 방법이
원리적으로 없습니다.

감지하는 것은 **기록과 지금 가격표의 불일치**입니다: 지금 단가가 발효된
**뒤에** 쓰인 기록이 다른 단가를 가리키면 그것은 사실이고, 원인은 셋입니다.

| 원인 | 뜻 |
| --- | --- |
| **낡은 인스턴스** | 적용은 됐는데 어느 인스턴스가 옛 가격표로 계산했다 — 정책 3201-⑤ 무효화가 닿지 않은 상태이며, **이 감지가 그 안전망**입니다 |
| **절차 우회** | 누군가 코드 기본값을 고쳐 절차 없이 단가를 바꿨다 |
| **가격표 오류** | 우리 표가 처음부터 틀렸다 |

규칙 셋이 오경보를 막습니다:

1. **발효 시각 이후 기록만** 봅니다 — 적용 직전 기록이 옛 단가인 것은 당연하고
   (Append Only), 그것을 세면 **적용할 때마다 되돌리는 제안**이 생깁니다.
2. **최근 표본이 한 값으로 모일 때만** 판단합니다 — 섞여 있으면 평균은
   *존재하지 않는 값*을 가리킵니다.
3. **최소 5건 · 차이 1% 이상**일 때만 봅니다.

**LLM은 단가를 만들지 않습니다.** 비용은 `입력×입력단가 + 출력×출력단가`이고
기록에서 미지수 둘을 가를 수 없습니다 — 표본으로 연립방정식을 세울 수는 있지만
토큰 비율이 비슷하면 *그럴듯하게 틀린* 값이 나옵니다. 그래서 **어긋났다는
사실만 알리고** 사람이 공지를 보고 직접 제안합니다.

감지는 `pricing-drift` 경보로 나갑니다(승인 대기 중이라는 사실을 알립니다).
**감지만으로 단가는 바뀌지 않고, 호출을 차단하지도 않습니다.**

### 외부 가격 공지 (정책 3301-①)

`PRICE_SOURCE_URL`에 JSON 가격표를 두면 **공지와 우리 가격표를 대조**합니다 —
이것이 "Provider가 단가를 올렸다"를 실제로 알 수 있는 유일한 경로입니다.
공지 기반 제안은 출처가 `published`이고, 근거에 **공지 주소와 공지가 밝힌 발효
시각**이 남습니다.

```json
{ "prices": [
  { "target": "ocr", "key": "google-vision", "perUnitUsd": 0.0018,
    "effectiveFrom": "2026-09-01T00:00:00.000Z" },
  { "target": "llm", "key": "gpt-4o", "inputPerMillion": 2.5, "outputPerMillion": 10 }
] }
```

**파싱 실패를 "변경 없음"으로 처리하지 않습니다.** 조용히 지나가면 화면은
"변경 없음"으로 보이고, 사람은 확인했다고 믿고, 단가는 낡은 채로 돈이 나갑니다.

| 상태 | 뜻 | 경보 |
| --- | --- | --- |
| `ok` | 전부 읽었다 | 없음 |
| `partial` | **일부만** 읽었다 — 못 읽은 항목을 목록으로 남긴다 | 있음 |
| `unparsable` | 형식이 바뀌었거나 JSON이 아니다 | 있음 |
| `unreachable` | 닿지 못했다 (네트워크·HTTP·타임아웃) | 있음 |
| `unconfigured` | 주소가 없다 — **실패가 아니다** | 있음(다른 제목) |

`ok`가 아니면 언제나 **사람의 확인이 필요**합니다(`needsHumanCheck`). 어댑터는
**재시도하지 않고**(예약 점검이 다시 부릅니다) 실패를 빈 목록으로 바꾸지
않습니다. 토큰(`PRICE_SOURCE_TOKEN`)은 헤더로만 보내고 기록에 남기지 않습니다.

> **같은 항목에 두 근거가 잡히면 공지가 남습니다.** 공지는 Provider가 밝힌
> 단가와 발효 시각을 들고 있고, 기록 불일치는 그 결과일 뿐입니다 — 순서를
> 반대로 두면 강한 근거가 약한 근거에 밀립니다.

## 1-3. 교차 확인 (정책 3201-②)

| 환경 | 제안자 = 승인자일 때 |
| --- | --- |
| `NODE_ENV=production` | **차단**(400) — "다른 ADMIN 계정으로 승인해 주세요" |
| 그 외 | 허용하고 **사실을 남긴다** — "운영에서는 차단됩니다" |

운영에서 단가는 실제 돈의 기준이므로 한 사람의 오타가 예산 전체를 흔듭니다.
반면 개발에서 절차 자체가 막히면 사람은 코드를 고쳐 우회하고, 그러면 이력이
아예 없어집니다(결정 2601-① 교훈).

> **운영에는 ADMIN 계정이 최소 둘 필요합니다.** 한 명뿐이면 단가를 적용할 수
> 없습니다 — 그것이 이 정책의 의도된 결과입니다.

감지된 제안은 제안자가 시스템(`proposedBy = null`)이라 이 판정을 통과합니다.
다만 **사람의 확인이 1회**라는 사실을 화면과 응답이 밝힙니다.

### 시스템 제안은 2단계 승인 (정책 3301-②)

```
시스템 생성 → ADMIN 승인 → 다른 ADMIN 최종 승인 → 적용
   DETECTED  →   APPROVED  →      CONFIRMED       →  APPLIED
```

**운영에서만** 강제합니다. 사람이 낸 제안은 제안자와 승인자가 이미 둘이지만
(정책 3201-②가 같은 사람을 막습니다), 시스템이 만든 제안은 승인자 **한 명이 곧
전부**이기 때문입니다.

- `APPROVED → APPLIED`는 **400**입니다 — 먼저 `confirm`을 받아야 합니다.
- **최종 승인자는 1차 승인자와 달라야** 합니다(운영 400 · 개발 경고). 같은
  사람이 두 번 누르는 절차는 단계만 늘 뿐 확인을 늘리지 않고, 오히려 "두
  사람이 봤다"는 잘못된 안심을 만듭니다.
- 개발에서는 그대로 `APPROVED → APPLIED`가 가능합니다. 더 보수적으로 가고
  싶으면 개발에서도 `confirm`을 쓸 수 있습니다.

```bash
curl -X POST "http://<api-host>/ops/pricing/<id>/confirm" -b other-admin.txt
```

## 1-4. 미래 시점 적용 (정책 3201-③)

```bash
# 9월 1일 0시부터 발효 — 결정은 오늘, 발효는 그날
curl -X POST "http://<api-host>/ops/pricing/<id>/apply" -b cookies.txt \
  -H 'content-type: application/json' \
  -d '{"effectiveFrom":"2026-09-01T00:00:00.000Z"}'
```

**적용은 결정이고 발효는 시각입니다.** 예약된 단가는 그 시각까지 어떤 계산에도
쓰이지 않고, 화면은 "예약된 변경 — 아직 계산에 쓰이지 않습니다"로 따로
보여 줍니다(발효된 것과 섞으면 이미 쓰이는 것처럼 읽힙니다).

| 규칙 | 왜 |
| --- | --- |
| **과거 시점 거부** | 이미 기록된 비용을 소급해 다시 해석하게 되고, 맞았던 기록이 불일치로 바뀝니다 (정책 3101-②가 무의미해집니다) |
| 최대 **365일** 뒤까지 | 그보다 먼 예약은 그때가 되면 아무도 이유를 모릅니다 |
| 시계 오차 **60초** 허용 | 화면이 보낸 "지금"이 서버보다 몇 초 뒤일 수 있습니다 |
| 미지정 = **즉시 발효** | 예약은 명시적으로만 합니다 |

### 예약 취소는 삭제가 아닙니다 (정책 3301-③)

```bash
curl -X POST "http://<api-host>/ops/pricing/<id>/cancel" -b cookies.txt \
  -H 'content-type: application/json' -d '{"reason":"공지가 정정되어 철회"}'
```

- **발효 전 예약만** 취소할 수 있습니다. 이미 발효된 단가를 "취소"하면 그 시각
  이후에 기록된 비용이 어떤 단가로 계산됐는지 설명할 수 없게 됩니다 — 되돌리려면
  **새 제안**을 냅니다.
- 레코드는 **`CANCELLED`로 남습니다.** 적용은 실제로 있었던 일이고, 그 결정을
  지우면 "왜 그때 그 단가가 예약됐다가 사라졌는가"에 아무도 답할 수 없습니다.
- **사유가 필요합니다** — 왜 없앴는지가 남지 않으면 이력이 반쪽입니다.
- 취소하면 캐시도 즉시 무효화합니다(다음 발효 경계가 바뀌므로).

## 1-5. 캐시 무효화 (정책 3201-⑤)

적용하면 **즉시** 캐시를 버립니다: 적용한 인스턴스는 그 자리에서, 나머지는
Redis pub/sub(`acos:pricing:invalidate`) 신호로. 캐시 수명은 30초이고, **다음
발효 시각**도 만료로 봅니다 — 예약을 지나쳐 캐시하면 발효 순간이 조용히
늦어지고, 그 사이 기록된 비용은 아무도 설명할 수 없습니다.

`REDIS_URL`이 없으면 **단일 인스턴스 모드**입니다(결정 1401-①과 같은 판단) —
프로세스 내 무효화가 곧 전체 무효화입니다. **미구성은 실패가 아닙니다.**
다만 다중 인스턴스인데 단일 모드로 돌고 있으면 그것이 사고이고, 그때는
§1-2의 감지가 사후에 그 사실을 잡습니다.

## 1-6. 감지 주기 (정책 3301-④)

기본은 **6시간**이고, **Provider별로만** 설정합니다.

```bash
PRICE_DETECT_INTERVAL_GOOGLE_VISION=12h   # OK
PRICE_DETECT_INTERVAL_PROJECT_ACME=1h     # 거부됩니다
```

**프로젝트별 설정은 지원하지 않습니다.** 단가는 Provider와의 계약이지
프로젝트의 속성이 아닙니다 — 프로젝트마다 주기를 다르게 두면 ⓐ "언제 마지막으로
봤는가"에 답이 여러 개가 되고 ⓑ 프로젝트가 늘 때마다 감지 부하가 곱해집니다.
그런 설정은 **조용히 무시하지 않고 거부 사유를 남깁니다**(무시하면 설정한
사람은 적용된 줄 압니다).

**수동 실행(`POST /ops/pricing/detect`)은 주기를 무시합니다** — 사람이 "지금
보라"고 누른 것이므로 주기 미도래로 아무것도 하지 않으면 버튼이 거짓말이 됩니다.
예약 점검은 주기를 지킵니다.

감지 실행은 **0건도, 건너뛴 것도** `price_detection_runs`에 남습니다 —
이 기록이 없으면 **"감지 0건"과 "감지를 안 돌렸다"를 구분할 수 없습니다.**
화면(감지 현황)은 Provider별 주기·마지막으로 본 시각을 함께 보여 줍니다.

## 2. 과거 기록은 다시 계산하지 않습니다 (정책 3101-②)

단가를 바꿔도 이미 기록된 `Execution.cost` · `OcrResult.cost`는 **그대로**입니다.
대신 비용 검증(`GET /llm/cost-verification`)이 **그 시점에 유효했던 단가**로
대조합니다.

그러지 않으면 단가를 한 번 바꿀 때마다 **과거 전체가 "불일치"로 보고**되고, 그런
경보는 곧 무시됩니다. 무시되는 경보는 없는 경보보다 나쁩니다.

경계는 테스트로 고정돼 있습니다(`apps/api/src/pricing/append-only.spec.ts`):
비용 컬럼을 갱신하는 코드가 생기면 테스트가 깨집니다.

## 3. 예측은 참고자료입니다 (정책 3101-③)

```bash
curl "http://<api-host>/ops/cost-forecast" -b cookies.txt
```

- 방식은 **하루 평균 × 이번 달 일수**(UTC)입니다. 정교한 모델을 쓰지 않은
  이유는 표본이 며칠뿐인 구간에서 정교한 모델이 **더 그럴듯하게 틀리기**
  때문입니다.
- 관측이 **3일**(`FORECAST_MIN_DAYS`, 고정값) 미만이면 **숫자를 만들지
  않습니다** — 이틀 관측으로 월말을 말하면 그것은 예측이 아니라 짐작이고,
  짐작을 화면에 숫자로 띄우면 사람은 그것을 사실로 다룹니다.
- 이 값으로 **호출을 막지 않습니다.** 예측으로 차단하면 아직 쓰지 않은 돈
  때문에 서비스가 멈추고, "왜 막혔나"에 답할 수도 없습니다. 차단은 실제 지출을
  보는 `assertWithinBudget`만 합니다.
- 비용이 빠진 호출(미산정)이 있으면 **추정도 실제보다 작을 수 있다**고 함께
  말합니다.

`projectedExceeds`가 true여도 그것은 **표시**입니다. 예산 상향 판단의 재료이고,
차단 여부와는 무관합니다.

### 경보는 내되 막지는 않습니다 (정책 3201-④)

예약 점검 `cost-forecast`(하루 1회, 기본 06:00 로컬)가 `cost-forecast:monthly`
경보를 냅니다. 경보 문구가 **"이 값으로 호출을 차단하지 않습니다"**를 직접
말합니다 — 알리는 것과 막는 것은 다릅니다.

표본이 부족하면(`insufficient`) 경보하지 않습니다: 짐작으로 사람을 부르면
다음 경보도 짐작으로 취급됩니다.

재알림 간격은 `ALERT_COOLDOWN_FORECAST_MS`로 조정합니다 — 하루 단위 사안이므로
`86400000` 권장입니다.

## 4. 운영 비용 리포트 (정책 3101-④)

```bash
curl "http://<api-host>/ops/billing?from=2026-07-01&to=2026-07-31" -b cookies.txt
```

기본 기간은 **이번 달**(UTC — 예산 창과 같은 경계), 최대 366일입니다. 정렬은
비용 큰 것부터입니다 — 리포트를 여는 이유는 대개 "무엇이 돈을 쓰는가"입니다.

**이 리포트는 회계 청구서를 대체하지 않습니다.** 실제 청구와 다를 수 있는
이유가 최소 넷입니다:

| 이유 | 방향 |
| --- | --- |
| **미산정** (가격표에 없는 모델·엔진 → `cost`가 null) | 우리 총액이 **작다** |
| **실패한 호출** (Provider에 따라 과금될 수 있는데 적지 않는다) | 우리 총액이 **작다** |
| **무료 구간** (반영하지 않는다 — TASK-3001) | 우리 총액이 **크다** |
| **환율·세금·단가 변동** | 청구서에는 있고 우리에게는 없다 |

그래서 응답과 화면에 **항상** 면책 문구가 붙습니다. 숫자만 있으면 누군가 그것을
청구서로 다루고, 회계와 어긋나는 순간 리포트 전체가 신뢰를 잃습니다.

미산정이 0이 아니면 "합계는 실제보다 작습니다"라고 명시합니다 — 침묵하면
작은 총액이 사실로 읽힙니다.
