# Backup Strategy — WAL Archive · PITR · Incremental 검토 (TASK-1701, Sprint 17)

> CTO 결정 1601-③에 따른 **도입 여부 검토** 문서입니다. 이번 Sprint에서
> 구현하지 않았습니다 — 현재는 전체 백업을 유지합니다.
> 실행 절차는 [disaster-recovery.md](disaster-recovery.md)를 참고하세요.

## 1. 지금 무엇을 잃는가

숫자를 먼저 확정하고 판단합니다. `/admin/operations`의 **복구 목표** 카드가
같은 값을 보여줍니다.

| 항목 | 현재 | 근거 |
| --- | --- | --- |
| 백업 주기 | 하루 1회 (03:00 로컬) | `OPS_CHECK_BACKUP_AT` |
| **최대 손실 구간 (RPO)** | **최대 24시간** | 마지막 백업 이후 전부 |
| 복원 소요 (RTO) | 측정치 — 개발 환경 기준 약 0.7초 / 30 테이블 | `restore_runs.durationMs` |
| 덤프 크기 | 약 100KB (개발) | `backup_runs.sizeBytes` |

**RTO는 걱정거리가 아닙니다. RPO가 문제입니다.** 오후 5시에 장애가 나면
그날 오전에 들어온 상품·콘텐츠·실행 이력을 전부 잃습니다.

여기서 잃는 것이 무엇인지가 판단의 핵심입니다:

- **Product / ProductObject / Content** — 사람이 다시 만들어야 합니다. 손실이
  곧 재작업입니다.
- **Execution / Alert / CheckRun** — 관측 이력입니다. 잃어도 서비스는 돌지만
  비용 정산과 사후 분석이 불가능해집니다.
- **이미지** — DB가 아니라 오브젝트 저장소에 있습니다. **DB만 되돌리면 참조가
  깨집니다**(§5).

## 2. 선택지

### 2.1 WAL Archive + PITR

PostgreSQL의 WAL(Write-Ahead Log)을 계속 보관하고, 기준 백업 + WAL 재생으로
**임의 시점**으로 되돌립니다.

| | |
| --- | --- |
| RPO | **초~분 단위** (WAL 전송 주기) |
| RTO | 기준 백업 복원 + WAL 재생 — 지금보다 **길어집니다** |
| 얻는 것 | 손실 구간이 24시간에서 분 단위로 줄어듭니다. "사고 직전"으로 되돌릴 수 있습니다 |
| 드는 것 | WAL 저장소(계속 쌓입니다) · `archive_command` 운영 · 기준 백업 주기 관리 · **복구 절차가 눈에 띄게 복잡해집니다** |

**주의**: PITR은 복구를 *더 어렵게* 만듭니다. 지금은 `pg_restore` 한 줄이지만,
PITR은 기준 백업을 고르고 `recovery_target_time`을 정하고 WAL을 순서대로
재생해야 합니다. **연습하지 않은 PITR은 없는 것보다 위험합니다** — 사고 상황에서
처음 해 보게 되기 때문입니다.

### 2.2 Incremental Backup

PostgreSQL 17의 `pg_basebackup --incremental` / `pg_combinebackup`.

| | |
| --- | --- |
| RPO | 증분 주기만큼 (예: 시간당 → 최대 1시간) |
| RTO | 기준 + 증분들을 합쳐야 하므로 **길어집니다** |
| 얻는 것 | 전체 백업보다 싸게 자주 받을 수 있습니다 |
| 드는 것 | **PostgreSQL 17 이상 필요** — 현재 운영 기준은 16입니다. 증분 사슬이 하나라도 깨지면 그 이후가 전부 무의미해집니다 |

현재 DB가 100KB 수준이라 **증분으로 아낄 것이 없습니다.** 증분은 덤프가 커서
자주 못 받을 때 쓰는 수단이지, 지금의 문제(하루 1회라서 24시간을 잃는 것)를
푸는 수단이 아닙니다. 지금은 **전체 백업을 더 자주 받는 것이 더 싸고 단순합니다.**

### 2.3 백업 주기 단축 (지금 할 수 있는 것)

`OPS_CHECK_BACKUP_AT`을 시각 지정에서 간격 기반으로 바꾸면 RPO를 바로 줄일 수
있습니다. 덤프가 100KB인 지금은 **하루 24회를 받아도 2.4MB**입니다.

| | |
| --- | --- |
| RPO | 주기만큼 (예: 1시간) |
| RTO | **변화 없음** — 복구 절차가 지금과 똑같습니다 |
| 얻는 것 | 손실 구간이 24배 줄어듭니다 |
| 드는 것 | 거의 없습니다. 덤프가 커지면 백업 중 부하를 봐야 합니다 |

## 3. 권고

**Sprint 17 시점의 권고는 다음과 같습니다.**

1. **지금 도입하지 않습니다** — WAL Archive · PITR · Incremental 모두.
   현재 데이터 규모(100KB 수준)와 트래픽에서 이들의 복잡도는 이득보다 큽니다.
   특히 PITR은 **복구를 어렵게 만들므로**, 정기 리허설을 운영에 넣을 수 있을
   때 도입해야 합니다.
2. **대신 백업 주기 단축을 먼저 검토합니다.** RPO 24시간 → 1시간을 복구 절차
   변경 없이 얻을 수 있습니다. 이것이 비용 대비 효과가 가장 큽니다.
3. **다음 조건 중 하나라도 충족되면 PITR을 다시 검토합니다:**
   - 전체 덤프가 **1GB를 넘겨** 잦은 전체 백업이 부담이 될 때
   - 전체 백업 1회가 **5분을 넘길 때**(`backup_runs.durationMs`로 관측)
   - "몇 시 몇 분 상태로 되돌려 달라"는 **요구가 실제로 생겼을 때**
   - 정기 복구 리허설이 운영 절차로 자리 잡았을 때
4. **Incremental은 PostgreSQL 17로 올린 뒤에** 다시 봅니다. 지금 조건에서는
   전체 백업을 자주 받는 편이 단순하고 안전합니다.

관측값이 판단을 대신하도록, 위 조건은 전부 **이미 기록 중인 값**(`backup_runs`)
으로 확인할 수 있습니다.

## 4. 도입한다면 — 선행 조건

권고가 뒤집혀 PITR을 도입하게 되면, 아래를 **먼저** 갖춰야 합니다.

- [ ] WAL 저장소와 보존 정책 (용량이 계속 늘어납니다)
- [ ] `archive_command` 실패 감지 — **WAL 아카이빙이 멈추면 PITR은 그 시점에서
      끝납니다.** 지금의 "예약 점검 정지 경보"와 같은 종류의 감시가 필요합니다
- [ ] 기준 백업 주기 (WAL만으로는 복구가 불가능합니다)
- [ ] **복구 리허설 절차** — 분기 1회 실제 PITR 수행, 결과 기록
- [ ] `disaster-recovery.md`의 복구 절차 전면 개정

## 5. 이미지 저장소는 별개 문제 (CTO 결정 1601-④)

**애플리케이션은 이미지를 백업하지 않습니다.** 저장소 제공자의 버전 관리·복제에
의존하며, TASK-1701부터 그 **상태를 재해 복구 체크리스트에 표시**합니다.

여기에는 PITR로도 풀리지 않는 문제가 있습니다: DB를 어제 시점으로 되돌리면
그 사이 업로드된 이미지 참조가 깨지고, 반대로 이미 삭제된 이미지의 참조가
되살아납니다. **DB와 저장소의 시점을 맞추는 문제**는 백업 방식과 무관하게 남고,
버전 관리가 켜져 있어야 손으로라도 맞출 수 있습니다.

체크리스트는 이 상태를 자동으로 판정하되, 저장소가 알려 주지 않으면
**`직접 확인`으로 남깁니다** — 모르는 것을 통과로 처리하지 않습니다.
