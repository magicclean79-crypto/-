# Recovery Guide (TASK-1202, Sprint 12)

장애가 났을 때 **무엇부터 보고, 어떻게 되돌리는지**를 정리한 문서입니다.
평상시 절차는 [production-runbook.md](production-runbook.md)를 참고하세요.

> 첫 단계는 항상 `/admin/health`(ADMIN)입니다 — 어느 구성 요소가 죽었는지
> 한 화면에서 판정됩니다. 구성 요소 점검은 **서로 독립적으로 실패**하므로,
> DB가 죽어도 저장소·Provider 상태는 그대로 볼 수 있습니다.

---

## 0. 증상별 빠른 진입점

| 증상 | 먼저 볼 곳 | 대표 원인 |
| --- | --- | --- |
| 서버가 뜨지 않음 | 기동 로그 `환경 오류 [...]` | 운영 필수 환경변수 누락·형식 오류 |
| 모든 요청 500 | `/admin/health` 구성 요소 | DB 연결 끊김 |
| 이미지 업로드만 실패 | `/admin/health` 저장소 | 버킷·자격 증명 |
| LLM 호출만 실패 | `/routing`, `/executions` | Provider 키·장애·예산 초과 |
| 갑자기 429 | `/providers` 예산 카드 | 비용 예산 초과 |
| 로그인 불가 | `/admin/health` DB · 감사 로그 | 계정 잠금·세션 만료 |
| 설정을 바꿨는데 반영 안 됨 | `/admin/console` 출처 배지 | 콘솔 오버라이드가 우선 중 |

## 1. 기동 실패 (환경 오류)

**증상**: 기동 로그에 `환경 오류 [변수명] …` 이 찍히고 프로세스가 종료됨.

운영에서는 잘못된 설정으로 뜨지 않게 **의도적으로 기동을 막습니다** —
조용히 오작동하는 서버가 더 위험하기 때문입니다.

```
[ReadinessService] 환경 오류 [S3_BUCKET] 필수 환경변수가 없습니다 — 이미지 버킷 이름.
[Bootstrap] 환경 검증에 실패해 기동을 중단합니다 …
```

**조치**: 로그에 나온 변수를 그대로 채우고 재기동합니다.
급히 확인만 하려면 `NODE_ENV`를 production이 아닌 값으로 두면 경고로만
남고 뜹니다 — **임시 확인용이며 그대로 운영하지 마세요**.

---

## 2. 데이터베이스 장애

**확인**: `/admin/health` → 구성 요소 `database` 실패, 사유가 그대로 표시됨.

1. DB 프로세스·네트워크 확인
2. `DATABASE_URL`의 호스트·자격 증명 확인
3. 커넥션 한도 초과 여부 확인

**복구 후**: `/admin/health`에서 "다시 검사" → `database` 정상,
"마이그레이션 적용" 통과 확인.

**데이터 복구가 필요한 경우**:

```bash
# 백업에서 복원 (예시 — 실제 백업 도구에 맞게)
pg_restore --clean --if-exists -d "$DATABASE_URL" backup.dump

# 복원 후 스키마 상태 확인
pnpm --filter api exec prisma migrate status
```

복원 뒤에는 **마이그레이션 상태를 반드시 확인**합니다. 백업 시점과 코드
버전이 어긋나면 미적용 마이그레이션이 남고, `/admin/health`가 배포 차단으로
잡아 줍니다.

---

## 3. 저장소(이미지) 장애

**확인**: `/admin/health` → 구성 요소 `storage` 실패.

- `버킷을 찾을 수 없습니다` → `S3_BUCKET` 이름 또는 버킷 생성 여부
- 접근 거부 → `S3_ACCESS_KEY` / `S3_SECRET_KEY`
- 연결 실패 → `S3_ENDPOINT`·네트워크

**영향 범위**: 이미지 업로드·조회만 실패합니다. 저장소가 죽어도 API 기동은
막지 않으므로(설계상 의도), 나머지 기능은 계속 동작합니다.

---

## 4. LLM Provider 장애

**확인**: `/routing` 하단 Failover 섹션 — Provider 건강 상태·전환 계측.

| 상태 | 의미 | 조치 |
| --- | --- | --- |
| 특정 Provider `불건강` | 연속 실패 임계 도달 | 자동으로 체인 뒤로 밀림 — 쿨다운 후 자동 복귀 |
| `체인 소진` 증가 | 모든 후보 실패 | Provider 상태·키·네트워크 확인 |
| `제외(예산/검증)` 증가 | 예산 초과 또는 요청 오류 | 아래 5절 / 요청 형식 확인 |

**즉시 조치** — 특정 Provider를 트래픽에서 빼려면
`/admin/console` → Provider 활성화에서 **비활성**. 라우팅·실험·Failover
후보에서 즉시 빠집니다(다음 호출부터). 마지막 하나는 끌 수 없습니다.

**복구 확인**: `GET /llm/health?provider=<name>` — Failover를 쓰지 않고
대상 Provider만 점검하므로 실제 회복 여부를 정확히 봅니다.

---

## 5. 비용 예산 초과 (429)

**증상**: LLM 호출이 429로 차단. `/providers` 예산 카드가 `초과`.

예산 초과는 **호출 전 차단**이라 Execution이 남지 않습니다(설계상 의도).

**조치** (택1):
- 기간 경과를 기다린다 (UTC 일/월 경계에서 자동 해제)
- `/admin/console` → 예산 관리에서 상한을 올린다 (감사 이력에 남음)
- 원인 파악: `/executions`에서 어떤 feature·Provider가 비용을 썼는지 확인

**주의**: 상한을 올리는 것은 근본 해결이 아닙니다. 실험이 비싼 변형에
트래픽을 보내고 있는지 `/experiments`에서 함께 확인하세요.

## 6. 실험 관련 사고

| 상황 | 조치 |
| --- | --- |
| 실험 변형이 품질을 망치고 있음 | `/experiments` → **중단**(EDITOR 이상) → 기존 라우팅으로 즉시 복귀 |
| 승격했는데 문제가 생김 | `/experiments` → **되돌리기**(ADMIN) → 직전 상태로 복원 |
| 배정이 갑자기 바뀜 | 실험 정의가 변경된 것 — `/experiments` 재배정 이력에서 사유 확인 |
| 승자 판단이 필요 | `/experiments` 분석 — 표본 부족이면 추천하지 않습니다 |

**되돌리기는 직전 상태로만** 복원합니다(무한 왕복 방지). 더 과거로 가려면
원하는 상태를 직접 지정하세요(시작/중단/승격).

## 7. 설정이 반영되지 않을 때

설정 우선순위는 **DB 오버라이드 → 환경변수 → 기본값**입니다(결정 1201-①).
배포로 환경변수를 바꿔도 **오버라이드는 자동 삭제되지 않습니다**(결정 1201-④).

**확인**: `/admin/console`에서 해당 항목의 출처 배지가 `콘솔`이면
오버라이드가 우선 중입니다. **해제**를 누르면 환경변수 값으로 돌아갑니다.

다중 인스턴스에서는 다른 인스턴스의 변경이 최대 `ADMIN_SETTINGS_TTL_MS`
(기본 10초)만큼 늦게 반영됩니다 — 그 이상 지나도 안 바뀌면 오버라이드
출처를 먼저 확인하세요.

## 8. 롤백

```bash
# 1) 이전 버전으로 배포 되돌리기 (배포 도구에 맞게)

# 2) 마이그레이션이 포함된 릴리스였다면 스키마 호환성 확인
pnpm --filter api exec prisma migrate status
```

**주의**: 이 프로젝트의 마이그레이션은 데이터 보존형으로 작성해 왔지만,
**스키마 롤백은 자동이 아닙니다**. 새 컬럼을 쓰는 코드가 사라지는 방향
(코드만 롤백)은 대체로 안전하고, 컬럼을 지우는 방향은 데이터 손실이므로
백업 확인 없이 진행하지 마세요.

롤백 후 `/admin/health`에서 배포 준비 상태를 다시 확인합니다.

## 9. 사고 후 정리

1. `/admin/console` 변경 이력에서 사고 전후 설정 변경을 확인
2. `/executions`에서 영향 범위(실패 건수·기간)를 확인
3. 임시로 올린 예산·비활성한 Provider 등 **임시 조치를 원복**
4. 재발 방지가 설정으로 가능하면 환경변수(Code-first)에 반영하고
   오버라이드는 해제 — 임시 조치가 영구 설정으로 굳지 않게
