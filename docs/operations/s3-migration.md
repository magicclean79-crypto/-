# Amazon S3 운영 전환 계획 (Sprint 21, CTO 결정 2001-⑤)

> **Sprint 21 안에 운영 저장소를 Amazon S3로 전환하는 것이 목표입니다.**
> 표준 자체는 결정 1801-④에서 정해졌고, 결정 1901-③에서 체크리스트 항목
> `storage-standard`로 승격돼 **지금은 운영에서 실패로 상시 표시**됩니다.
> 이 문서는 그 실패를 없애는 절차입니다.

## 0. 왜 지금인가

MinIO·s3rver는 **개발 전용**입니다. 기능이 부족해서가 아니라, **버전 관리·
복제 상태 조회를 지원하지 않기** 때문입니다. 그래서 개발 저장소를 운영에
그대로 쓰면 다음 두 항목이 **영원히 `직접 확인`으로 남습니다.**

- 이미지 저장소 보호 (버전 관리·복제)
- 백업 버킷 보호 (버전 관리·복제)

**확인하지 못한 것을 통과로 세지 않는다**는 규칙 때문에 이 둘은 통과로
바뀌지 않고, 결과적으로 **재해 복구 체크리스트가 끝내 초록이 되지 않습니다.**
전환은 기능 추가가 아니라 **판정을 가능하게 만드는 일**입니다.

## 1. 현재 상태

| 항목 | 지금 | 전환 후 |
| --- | --- | --- |
| `S3_ENDPOINT` | `http://localhost:9000` (s3rver) | `https://s3.<region>.amazonaws.com` |
| `storage-standard` | **실패** (운영) | 통과 |
| 이미지 저장소 보호 | `직접 확인` | 판정 가능 |
| 백업 버킷 보호 | `직접 확인` | 판정 가능 |
| 원격 사본 대조 | 동작함 (s3rver도 GET을 지원) | 그대로 동작 |

## 2. 버킷 구성

두 버킷을 **분리해서** 만듭니다 (CTO 결정 1701-②).

| 버킷 | 용도 | 공개 읽기 | Versioning | Replication |
| --- | --- | --- | --- | --- |
| `<S3_BUCKET>` | 상품 이미지 | 허용 (정책으로 `s3:GetObject`) | **필수** | 권장 |
| `<S3_BUCKET>-backups` | DB 덤프 | **금지** | **필수** | 권장 |

> **백업 버킷에 공개 읽기 정책을 걸지 마십시오.** 덤프가 공개되면
> 데이터베이스 전체가 공개되는 것과 같습니다. 애플리케이션은 백업 버킷에
> 정책을 걸지 않습니다 — 사람이 콘솔에서 거는 실수를 막아야 합니다.

Versioning은 **운영 필수**입니다 (CTO 결정 1701-③) — 꺼져 있으면 운영에서
`실패`로 판정합니다. Replication은 권장이며 꺼져 있으면 `주의`입니다.

## 3. 자격 증명

전환용 IAM 사용자(또는 역할)에 필요한 최소 권한입니다.

| 동작 | 필요한 권한 | 쓰는 곳 |
| --- | --- | --- |
| 이미지 업로드·조회 | `s3:PutObject` · `s3:GetObject` · `s3:DeleteObject` | 업로드·정리 |
| 버킷 존재 확인 | `s3:ListBucket` | 저장소 접근 점검 |
| 백업 업로드 | `s3:PutObject` (백업 버킷) | 원격 복제 |
| **원격 사본 대조** | `s3:GetObject` (백업 버킷) | 주 1회 자동 대조 (결정 2001-②) |
| **보호 상태 조회** | `s3:GetBucketVersioning` · `s3:GetReplicationConfiguration` | 체크리스트 판정 |

마지막 줄이 핵심입니다. **조회 권한이 없으면 전환해도 `직접 확인`이
그대로 남습니다** — 저장소가 S3인 것과 상태를 읽을 수 있는 것은 다릅니다.

## 4. 전환 절차

1. **버킷 2개 생성** — 이미지 버킷, 백업 버킷. 리전은 운영 DB와 같은 곳으로.
2. **Versioning 켜기** (둘 다). Replication은 대상 리전을 정한 뒤 설정.
3. **IAM 권한 부여** — §3의 표대로. 조회 권한을 빠뜨리지 마십시오.
4. **기존 객체 이관** — 이미지 버킷의 기존 객체를 복사합니다.
   백업은 이관하지 않아도 됩니다(주기가 1시간이라 하루면 새 덤프가 쌓입니다).
   다만 **이관하지 않기로 했다면 옛 백업이 남은 곳을 언제 지울지 정하십시오** —
   "나중에"는 지워지지 않습니다.
5. **환경변수 교체**:
   ```
   S3_ENDPOINT=https://s3.<region>.amazonaws.com
   S3_BUCKET=<이미지 버킷>
   BACKUP_BUCKET=<백업 버킷>
   S3_ACCESS_KEY / S3_SECRET_KEY=<IAM 자격 증명>
   S3_PUBLIC_URL=<CDN 또는 버킷 공개 URL>
   ```
6. **재기동 후 확인** — 아래 §5.

## 5. 전환 확인 (완료 판정)

`/admin/operations`에서 **네 항목이 모두 바뀌어야** 전환이 끝난 것입니다.

| 항목 | 기대 |
| --- | --- |
| `운영 저장소 표준` | **통과** — `Amazon S3 (s3.<region>.amazonaws.com)` |
| `이미지 저장소 보호` | `직접 확인` → **통과** (버전 관리 켜짐) |
| `백업 버킷 보호` | `직접 확인` → **통과** |
| `원격 사본 무결성` | 주 1회 자동 대조 후 **통과** |

세 번째가 여전히 `직접 확인`이면 **조회 권한이 빠진 것**입니다(§3).
저장소를 바꿨는데 판정이 그대로라면, 바꾼 의미의 절반이 사라진 것입니다.

```bash
# 전환 직후 한 번 직접 확인
curl -X POST "http://localhost:4000/ops/checks/run?job=remote-verify" -b cookies.txt
curl http://localhost:4000/ops/readiness -b cookies.txt
```

## 6. 되돌리기

전환이 실패하면 **환경변수만 되돌리면 됩니다** — 코드는 엔드포인트를 읽을 뿐
S3에 묶여 있지 않습니다. 다만 되돌린 뒤에는 `storage-standard`가 다시
**실패**로 표시됩니다. 그 실패는 버그가 아니라 **아직 전환하지 않았다는
사실**입니다.

  (CTO 결정 1801-⑤):

  ```bash
    -H 'content-type: application/json' \
    -d '{"trigger":"dr-change","description":"운영 저장소 Amazon S3 전환","registeredBy":"<이름>"}'
  ```
