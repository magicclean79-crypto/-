# 신뢰성 층 확대 안내

> TASK-4701, Sprint 47 — Enterprise AI Reliability Expansion
>
> TASK-4603이 만든 작업 층을 **나머지 AI 경로로 넓히고**, 토큰·비용을
> 잇고, 죽은 프로세스가 남긴 작업을 자동으로 되살리고, 라이브 검사 일부를
> CI로 옮깁니다.

## 한 줄 요약

| 지시 | 무엇이 달라졌는가 |
| --- | --- |
| 1. 층 확대 | 작업 종류가 **1개 → 4개** (OCR · 분석 · 생성 · 발행) |
| 2. 토큰 수집 | 어댑터가 캐시·생각 토큰을 **우리 뜻으로 옮겨** 담고, 작업이 자기 비용을 안다 |
| 3. 자동 이어하기 | 심장박동이 멈춘 작업을 큐가 되살린다 (기본은 **꺼짐**) |
| 4. 라이브 검사 | 15건 중 **11건을 CI에서** 돌린다 (4건은 사람 몫) |
| 5. 가격표 | 단가의 **나이와 출처**, 미산정 모델을 **이름으로** |

## 1. 층을 넓혔습니다

### 새 작업 세 가지

| 경로 | 왜 이 층에 올렸는가 |
| --- | --- |
| `POST /jobs/analysis-batch` | 이미지를 첨부한 **멀티모달 호출** — 이 저장소에서 가장 비쌉니다 |
| `POST /jobs/content-batch` | 프롬프트도 출력도 가장 깁니다 |
| `POST /jobs/publish-batch` | 과금은 없지만 **되돌리기가 가장 번거롭습니다** |

발행이 이 층에 들어온 이유는 돈이 아니라 **"어디까지 나갔는가"** 입니다.
스무 건을 발행하다 열두 번째에서 프로세스가 죽으면, 지금까지는 사람이 손으로
확인해야 했습니다.

### 기존 경로는 그대로입니다

넷 다 기존 서비스를 **부르기만** 합니다. `POST /images/:id/ocr` ·
`POST /products/:id/analysis` · `POST …/contents/generate` ·
`PATCH …/contents/:id/status`는 예전과 똑같이 동작합니다.

### 건너뛸 문제와 멈춰야 할 문제를 한자리에서 가릅니다

TASK-4603의 라이브 결함 4건 중 **2건이 이 규칙**이었습니다. 같은 모양의
작업이 넷이 되었으므로 규칙을 `judgeBatchItem()` 하나로 모았습니다 — 네
군데에 복사하면 **넷 중 하나는 반드시 다르게 씁니다.**

| 원인 | 처리 |
| --- | --- |
| 연결·시간 초과·상대 서버·DB·저장소 | **멈춘다** |
| 우리가 막음(예산·게이트) | **멈춘다** |
| **자격 증명 실패(401·403)** | **멈춘다** — 키는 항목마다 다르지 않습니다 |
| 파일 없음·형식·거버넌스 거절 | 건너뛰되 **결과에 남긴다** |
| 모름 | 건너뛴다 — 한 건 때문에 나머지를 멈추지 않습니다 |

전부 건너뛰었으면 **"결과를 얻은 항목이 하나도 없습니다"** 라고 말합니다.

## 2. 토큰과 비용

### 지금까지의 합계가 왜 틀렸는가

호출 하나를 **두 숫자**(입력·출력)로 셌습니다. 그런데 그 숫자의 뜻이
Provider마다 다르고, **틀리는 방향도 다릅니다**:

| Provider | 무엇이 어긋나는가 | 방향 |
| --- | --- | --- |
| Anthropic | `input_tokens`가 캐시를 **빼고** 온다 | 실제보다 **적게** |
| OpenAI | `prompt_tokens`가 캐시를 **포함**한다(캐시는 싸다) | 실제보다 **많이** |
| Gemini | 생각 토큰이 `candidatesTokenCount`에 **없다**(청구는 된다) | 실제보다 **적게** |

셋이 서로 다른 방향이라 **합계는 어느 쪽으로도 못 믿습니다.**

### 그래서 우리 말로 옮깁니다

| 우리 칸 | 뜻 |
| --- | --- |
| `inputTokens` | **캐시를 뺀** 새로 청구되는 입력 |
| `cachedInputTokens` | 캐시에서 읽음 (기본 입력의 **1/10**) |
| `cacheWriteTokens` | 캐시에 씀 (기본 입력의 **1.25배** — 캐시는 공짜가 아닙니다) |
| `outputTokens` | **생각 토큰까지 포함한** 청구되는 출력 |

`null`은 **"그 Provider에 그 개념이 없다"** 입니다. 어댑터는 세 칸을 모두
명시합니다 — 빠뜨리면 "몰라서 없는 것"과 구별할 수 없습니다.

### 옛 기록을 건드리지 않습니다

**상세가 하나도 없으면 예전 셈과 한 푼도 다르지 않습니다.** 새 셈을 과거에
소급하면 지금까지의 모든 기록이 "불일치"로 뜨고(비용 기록은 Append Only —
정책 3101-②), 진짜 불일치가 그 소음에 묻힙니다.

### 작업이 자기 비용을 압니다

토큰은 **원래 있었습니다** — 어댑터는 처음부터 `executions`에 적고 있었고,
없던 것은 토큰이 아니라 **작업과 호출을 잇는 선**이었습니다. 그래서 새로
재지 않고 **이미 기록된 것을 읽어 옵니다**(같은 사실에 두 개의 답을 만들지
않습니다).

묶는 근거는 **요청 id + 그 단계가 돈 시간 구간**입니다. 한계를 그대로
적습니다:

- `requestId`를 모르면 **재지 않습니다.** 시간만으로 묶으면 같은 순간
  다른 요청이 부른 호출까지 셉니다 — 그렇게 만든 비용은 짐작입니다.
- 호출이 **없었으면 0**입니다(물어봤고 답이 "없다"였습니다). 못 잰 것과
  다릅니다.
- 가격표에 없는 호출이 섞이면 합계는 **최소값**이고, 그 사실을 문장이
  말합니다.

## 3. 자동 이어하기

### 기본은 꺼짐입니다

`JOB_AUTO_RESUME=on`으로 켭니다. 기본을 꺼짐으로 둔 이유: 자동 이어하기는
**아무도 안 보는 사이에 돈이 나가는 호출**을 합니다. 켜는 것은 그 사실을
아는 사람의 결정이어야 하고, "기본값이라 켜져 있었다"는 그 결정이 아닙니다.

### 큐를 따로 만들지 않았습니다

**`job_runs` 자체가 큐**입니다. Redis 큐를 두면 같은 사실이 두 군데 살고,
언젠가 어긋납니다 — 행에는 "실패"라고 적혀 있는데 큐에는 항목이 없거나 그
반대인 상태가 생기고, 그때 어느 쪽이 맞는지 아무도 답하지 못합니다.

두 인스턴스가 같은 작업을 집는 것은 **조건부 갱신 한 번**으로 막습니다
(`updateMany` + `where`에 지금 상태). 진 쪽은 갱신 건수 0을 받고 물러납니다 —
잠금 서버 없이도 정확합니다.

### 무엇을 하지 않는가

| 규칙 | 왜 |
| --- | --- |
| 심장박동이 있으면 건드리지 않는다 | 돌고 있는 작업을 죽었다고 보고 또 돌리면 **같은 일을 두 번 산다** |
| 다시 해도 같은 실패는 자동으로 안 한다 | 예산·권한·잘못된 입력은 열 번 해도 같고 그중 일부는 매번 돈이 나간다 |
| 모르는 실패(`unknown`)도 안 한다 | 사람이 누를 때는 "한 번 더"가 성립하지만 자동은 그 판단을 한 사람이 없다 |
| 자동은 **2회**까지 (수동 3회보다 적게) | 사람이 누른 재시도와 아무도 안 본 재시도는 같은 값이 아니다 |
| 한 번에 **5건**까지 | 장애가 끝난 순간 밀린 작업이 한꺼번에 돌면 청구서도 한꺼번에 온다 |
| 상한에 닿아도 **행을 지우지 않는다** | 조용히 그만두면 아무도 못 끝낸 작업이 없는 일이 된다 |
| 하루가 지나면 안 한다 | 체크포인트와 같은 창 — 그 사이에 무엇이 바뀌었는지 모른다 |

### 죽음을 어떻게 아는가

작업이 도는 동안 **30초마다 심장박동**을 남깁니다. 90초(주기의 3배) 넘게
멈춰 있으면 그 프로세스가 죽은 것으로 보고 `interrupted`로 표시합니다.

`interrupted`는 **실패가 아니라 "끝났는지 모른다"** 입니다 — 끝난 단계는
체크포인트에 그대로 있습니다.

표시와 이어하기는 **다른 차례에** 합니다. 한 번에 "죽었다고 판단"하고
"바로 돌린다"를 같이 하면, 잘못 판단했을 때 되돌릴 틈이 없습니다.

### 화면과 API

- `GET /jobs/queue/status` — 켜졌는가 · 무엇을 이어할 줄 아는가.
  **조회는 아무것도 이어하지 않습니다.**
- `POST /jobs/queue/sweep` — 지금 한 번 훑는다 (사람이 누를 때만).

## 4. 라이브 검사를 CI로

### 왜 옮겼는가

TASK-4603에서 라이브 결함 **4건**이 나왔고 **넷 다 유닛 테스트를
통과했습니다.** 인메모리 mock은 우리가 상상한 대로 동작하고, 실제 DB는
우리가 쓴 대로 동작합니다 — 그 둘이 어긋나는 자리에서 사고가 납니다.

### 무엇이 옮겨지는지는 사람이 정하지 않습니다

`@acos/core`의 `judgeCiCoverage`가 판정합니다. 검사 목록과 각 검사가 **무엇을
필요로 하는지**가 값으로 있고, "CI에서 되는가"는 계산 결과입니다. 문서의
문장으로 두면 검사를 추가한 사람이 문장을 고치지 않아 **틀렸는데 아무도 모르는
상태**가 됩니다.

```
pnpm check:live-coverage
```

지금: **15건 중 11건(73%)이 CI에서** 돌고 4건은 사람 몫입니다.

### 사람 몫으로 남는 것

| 검사 | 왜 CI에 못 두는가 |
| --- | --- |
| 화면 문장이 사실과 맞는가 | **사람 눈** — 요약과 칸이 같은 말을 하는지는 읽어야 압니다 |
| 실 Provider가 우리 요청을 받는가 | 자격 증명 · **돈이 나가는 호출** |
| 실 Provider의 usage가 우리 가정과 같은가 | 같은 이유 — **이건 우리가 확인할 수 없습니다** |
| 운영 저장소가 실제로 보관하는가 | 통제 밖 네트워크 |

### 가장 중요한 문장

> **CI가 초록이라고 라이브 검증이 끝난 것이 아닙니다.**

CI에서 도는 검사는 **배선이 맞는가**를 증명합니다. 실제 Provider가 우리
요청을 어떻게 대하는지는 증명하지 않습니다. 둘을 같은 이름으로 부르면,
어느 날 초록을 보고 "라이브 검증 완료"라고 말하게 됩니다 — TASK-3501에서
스텁 상대 성공 기록을 "연결됨"으로 셀 뻔한 것과 같은 사고입니다.

### 사람이 돌리는 법

```
node scripts/ci-vision-stub.mjs &          # 계약 스텁
node scripts/seed-live-checks.mjs          # 최소 씨앗
node apps/api/dist/main.js &               # API
VISION_STUB_CONTROL=http://127.0.0.1:9100 pnpm live:checks
```

## 5. 가격표

### 값이 있다는 것과 맞다는 것은 다릅니다

지금까지 `DEFAULT_LLM_PRICING`은 숫자만 가지고 있었습니다. 화면의
"$0.0123"을 보고 **그 단가가 언제 것인지** 아무도 물을 수 없었습니다.
단가는 조용히 바뀌고, 바뀐 날 우리 표에는 아무 일도 일어나지 않습니다 —
그 뒤로 우리가 내는 비용 숫자는 **틀렸는데 초록색**입니다.

이제 값 옆에 **언제 확인했고 어디서 왔는지**가 있습니다(180일이 지나면
"다시 대조해 주세요"라고 말합니다). 오래된 것을 **틀렸다고 말하지
않습니다** — 오래됐다는 것은 "확인한 지 오래됐다"이지 "바뀌었다"가
아닙니다.

### 미산정 호출을 이름으로 봅니다

지금까지는 **"비용이 빠진 호출 12건"** 이었습니다. 그 문장으로 사람이 할 수
있는 일이 없습니다. 이제 `GET /llm/pricing-health`가 이렇게 말합니다:

```
가격표에 없는 모델 5종 · 호출 6건. 이만큼은 예산 상한이 걸리지 않은 채로
나갔습니다 — 지출 합계는 최소값입니다.
  gpt-5-preview  호출 2  기능 [product-analysis]  처음 2026-07-29
```

### 없는 단가를 채우지 않았습니다

표에 없는 모델을 "비슷한 모델 값"으로 채우면 경보가 사라지고 화면이 초록이
됩니다. **그 초록은 거짓말입니다.** 근거 없는 숫자로 낸 비용은 없는 것보다
나쁩니다 — 없으면 "모른다"가 보이지만, 지어내면 아무도 다시 확인하지
않습니다. 채우는 것은 사람이 근거를 들고 하는 일이며, 이 저장소에는 이미
그 절차(제안 → 검토 → 승인 → 적용)가 있습니다.
